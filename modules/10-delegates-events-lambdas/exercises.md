## Задача 1. Свои Filter/Map/Reduce  ·  ⏱ ~35 мин  ·  🟢 базовая

**Что сделать:** реализуй extension-методы `Filter` (аналог `Where`), `Map` (аналог `Select`), `Reduce` (аналог `Aggregate`) и `CountWhere` (с `Predicate<T>`). `Filter` и `Map` — ленивые (через `yield`), но проверяют аргументы сразу. Без LINQ.

**Зачем:** понять, что LINQ — это не магия, а обычные методы, принимающие делегаты. «Напиши свой Where» — частый вопрос на собеседовании, проверяющий и делегаты, и `yield`, и deferred execution.

**Файл:** `Module10.Tasks/MyEnumerable.cs`
**Тесты:** `dotnet test --filter "FullyQualifiedName~MyEnumerableTests"`

**Подумай / ответь письменно:**
1. Почему `Reduce` не ленивый, а `Filter` и `Map` — ленивые?
2. Почему в `CountWhere` нельзя просто передать переменную типа `Func<T, bool>`?

## Задача 3. Биржевой тикер с событиями  ·  ⏱ ~40 мин  ·  🟡 средняя

**Файл:** `Module10.Tasks/StockTicker.cs`
**Тесты:** `dotnet test --filter "FullyQualifiedName~StockTickerTests"`

## Задача 7. Конвейер middleware  ·  ⏱ ~50 мин  ·  ⭐ со звёздочкой

**Что сделать:** реализуй `PipelineBuilder`: `Use(Func<RequestHandler, RequestHandler>)`, `Run(RequestHandler)`, `Build()`. Первый добавленный middleware — внешний; middleware может не вызывать `next` (short-circuit); без `Run` — ответ 404; middleware, добавленные после `Build`, не влияют на собранный конвейер.

**Зачем:** именно так устроен конвейер ASP.NET Core (`app.Use(...)`), и вопрос «как работает middleware pipeline» — один из главных на собеседовании по Web API (модуль 15). Задача — отличная live coding тренировка на функции высшего порядка и замыкания.

**Файл:** `Module10.Tasks/Pipeline.cs`
**Тесты:** `dotnet test --filter "FullyQualifiedName~PipelineTests"`

**Подумай / ответь письменно:**
1. Почему конвейер собирается в обратном порядке (с последнего middleware)?
2. Где «хранится» `next` у каждого middleware после `Build`?
3. Как добавить middleware, который ловит исключения из всех последующих и ставит статус 500?
