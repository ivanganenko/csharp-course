## 1. Stack и heap — точнее, чем в модуле 02

В модуле 02 было упрощение: «value types — на стеке, reference types — в куче». Пора уточнить.

**Stack** (стек потока) — область памяти, которая есть у каждого потока (обычно 1 МБ для основного потока на Windows). Каждый вызов метода кладёт на стек **frame** (кадр): параметры, локальные переменные, адрес возврата. Метод завершился — кадр «снимается» простым сдвигом указателя. Это очень быстро и не требует GC.

**Managed heap** (управляемая куча) — общая для всех потоков область, где создаются объекты через `new` для классов, массивов, строк, делегатов. Освобождает её **garbage collector** (GC, сборщик мусора).

Правило точнее: **value type хранится там, где объявлена переменная/поле, которое его содержит.**

```csharp
public struct Point { public int X; public int Y; }

public class Shape
{
    public Point Center;          // поле value type ВНУТРИ объекта класса → лежит в куче (как часть Shape)
}

void Demo()
{
    var p = new Point();          // локальная переменная value type → на стеке (или в регистре)
    var s = new Shape();          // ссылка s — на стеке; сам объект Shape (вместе с Center) — в куче
    int[] numbers = { 1, 2, 3 };  // массив — reference type: элементы int лежат в куче
    object boxed = p;             // boxing: копия Point упакована в новый объект в куче
}
```

Когда локальная переменная value type всё-таки окажется в куче:
- она **захвачена лямбдой** (closure) — компилятор переносит её в поле сгенерированного класса (модуль 10);
- она живёт в `async`-методе через `await` или в итераторе с `yield` — переменные становятся полями state machine;
- произошёл **boxing** (приведение к `object` или интерфейсу).

> **Почему так?** Стек — это «черновик» конкретного вызова: он исчезает при выходе из метода, поэтому там можно хранить только то, что не переживёт метод. Объект класса может жить сколько угодно (на него может ссылаться кто угодно), поэтому ему нужно место с независимым временем жизни — куча. А value type — это просто «байты значения», они копируются туда, где лежит их владелец. Сама спецификация C# вообще не обещает стек: это деталь реализации CLR, и JIT может положить переменную в регистр процессора.

> 💼 **На собеседовании:** «Reference types всегда в managed heap. Value types хранятся там, где их владелец: локальная переменная — на стеке, поле класса — в куче внутри объекта, элемент массива — в куче. Исключения — closures, async/iterators и boxing: тогда value type попадает в кучу».

## 2. Как устроен garbage collector

**Garbage collector** — часть CLR, которая автоматически освобождает память объектов, на которые больше никто не ссылается.

### Аллокация — очень дешёвая

В managed heap новые объекты кладутся подряд, «сдвигом указателя» (bump pointer). `new` в .NET почти так же дёшев, как на стеке. Дорого не создать объект, а **потом его собрать**.

### Mark & compact

Упрощённо одна сборка мусора выглядит так:

1. **Пауза** — потоки приложения останавливаются (в safe points).
2. **Mark** — GC начинает с **roots** (корней): локальные переменные и параметры на стеках потоков, `static` поля, регистры, GC handles. От них проходит по ссылкам и помечает все достижимые объекты.
3. **Sweep/Compact** — всё непомеченное — мусор. Живые объекты **сдвигаются** плотнее (compaction), ссылки на них обновляются. Фрагментации нет, следующая аллокация снова — сдвиг указателя.
4. Потоки продолжают работу.

```csharp
void Run()
{
    var report = new StringBuilder();  // report — root (локальная переменная)
    report.Append("data");
    // после последнего использования report объект уже может быть собран,
    // даже если метод ещё не завершился (JIT знает, что переменная больше не нужна)
}
```

> **Почему так?** Подсчёт ссылок (reference counting, как в COM или Swift) не умеет собирать циклы (A → B → A) и требует атомарных операций на каждое присваивание. Tracing GC («найди всё живое от корней») решает циклы бесплатно, а compaction даёт быструю аллокацию и хорошую локальность данных. Цена — паузы, поэтому GC оптимизирован поколениями.

### Поколения 0, 1, 2

Наблюдение (generational hypothesis): **большинство объектов умирают молодыми** (временные строки, DTO в запросе, итераторы LINQ), а то, что прожило долго, скорее всего проживёт ещё.

| Поколение | Что там | Как часто собирается |
|-----------|---------|----------------------|
| **Gen 0** | только что созданные объекты | очень часто, быстро (маленький объём) |
| **Gen 1** | пережили одну сборку; «буфер» между молодыми и старыми | реже |
| **Gen 2** | долгоживущие: кэши, singletons, static-данные | редко, дорого (full GC) |

Объект, переживший сборку своего поколения, **продвигается** (promotion) в следующее. Сборка Gen 1 включает Gen 0, сборка Gen 2 — всё (full GC).

```csharp
var obj = new object();
Console.WriteLine(GC.GetGeneration(obj)); // вывод: 0
GC.Collect();                              // только для демонстрации!
Console.WriteLine(GC.GetGeneration(obj)); // вывод: 1 (объект жив — он продвинут)
```

> **Почему так?** Собрать маленький Gen 0 можно за доли миллисекунды, не трогая гигабайты старых объектов. Чтобы не сканировать Gen 2 в поисках ссылок «старый → молодой», CLR использует card table — отметки об изменённых участках старой памяти. Компромисс: если объекты живут «средне» (дольше Gen 0, но не вечно), они доезжают до Gen 2 и умирают там — это дорогой сценарий, называемый «mid-life crisis».

### Когда срабатывает GC

- закончился **бюджет Gen 0** (выделили достаточно памяти с прошлой сборки) — самый частый случай;
- система сообщает о нехватке физической памяти;
- явный вызов `GC.Collect()`;
- выгрузка AppDomain/завершение процесса.

GC **не** срабатывает «по таймеру» и не потому, что объект стал недостижим. Момент сборки **недетерминирован** — поэтому на GC нельзя полагаться для закрытия файлов и соединений (раздел 4).

### Почему не вызывать `GC.Collect()`

- GC сам выбирает момент по статистике аллокаций; ручной вызов ломает эту настройку.
- Full GC — пауза всего приложения.
- Живые объекты при этом **продвигаются** в старшие поколения и потом собираются дороже.

Допустимые случаи редки: бенчмарки, тесты на утечки, после разовой загрузки огромных данных в десктопном приложении.

### LOH — Large Object Heap

Объекты **от 85 000 байт** (на практике — большие массивы и строки) создаются в отдельной куче — **LOH** (Large Object Heap).
- LOH собирается только вместе с Gen 2.
- По умолчанию LOH **не компактируется** (копировать мегабайты дорого) → возможна фрагментация.
- Можно попросить разовую компакцию: `GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce`.

```csharp
var small = new byte[84_000];
var large = new byte[85_000];
Console.WriteLine(GC.GetGeneration(small)); // вывод: 0
Console.WriteLine(GC.GetGeneration(large)); // вывод: 2 (LOH логически относится к Gen 2)
```

> **Почему так?** Копирование больших блоков при каждой сборке съело бы всё преимущество compaction. Поэтому большие объекты выделяют отдельно и сразу считают «старыми». Вывод для практики: **не создавай часто большие временные массивы** — переиспользуй их через `ArrayPool<T>` (раздел 6).

Ещё есть **POH** (Pinned Object Heap, .NET 5+) — для объектов, которые нельзя двигать (переданы в нативный код).

### Режимы GC (обзорно)

- **Workstation GC** — для десктопа: меньше потоков GC, меньше памяти.
- **Server GC** — для серверов (ASP.NET Core по умолчанию): отдельная куча и поток GC на каждое ядро, больше пропускная способность, больше памяти.
- **Background GC** — сборка Gen 2 идёт параллельно с работой приложения, Gen 0/1 при этом тоже могут собираться.

> 💼 **На собеседовании:** «GC в .NET — tracing, generational, compacting. Аллокация дешёвая — сдвиг указателя. Объекты делятся на поколения 0/1/2: молодые собираются часто и быстро, старые — редко. Объекты ≥ 85 000 байт идут в LOH, он собирается с Gen 2 и по умолчанию не компактируется. `GC.Collect` вручную обычно не вызывают — это ломает эвристики и вызывает лишние паузы».

## 3. Финализаторы

**Финализатор** (finalizer, в C# — синтаксис деструктора `~ClassName()`) — метод, который GC вызывает перед освобождением памяти объекта.

```csharp
public class NativeFile
{
    private IntPtr _handle; // дескриптор ОС — GC о нём ничего не знает

    ~NativeFile()
    {
        // вызывается потоком финализации, когда-нибудь после того, как объект стал мусором
        CloseHandle(_handle);
    }

    private static void CloseHandle(IntPtr handle) { /* вызов ОС */ }
}
```

Как это работает:
1. При создании объекта с финализатором CLR регистрирует его в **finalization queue**.
2. Когда GC обнаруживает, что объект мёртв, он **не освобождает** память, а переносит объект в очередь **f-reachable** — объект снова «жив».
3. Отдельный **finalizer thread** вызывает финализаторы.
4. Только на **следующей** сборке память объекта (и всего, на что он ссылается) освобождается.

Проблемы финализаторов:
- объект переживает минимум одну лишнюю сборку и продвигается в старшее поколение;
- **порядок** финализации не определён: другие managed-объекты, на которые ты ссылаешься, могли уже финализироваться;
- выполняется в чужом потоке; исключение в финализаторе **роняет процесс**;
- нет гарантии, **когда** (и при аварийном завершении — что вообще) он вызовется.

> **Почему так?** Финализатор — последний рубеж для **unmanaged-ресурсов** (дескрипторы файлов, сокетов, память из нативных библиотек), о которых GC не знает. Но так как он медленный и непредсказуемый, его используют только как страховку, а основной путь освобождения — явный `Dispose()`.

> 💼 **На собеседовании:** «Финализатор нужен только классам, которые **напрямую** владеют unmanaged-ресурсом. Он делает сборку дороже — объект живёт на одну сборку дольше. В современном коде вместо своего финализатора используют `SafeHandle`».

## 4. `IDisposable` и полный Dispose pattern

`IDisposable` (модуль 07) — договор «у меня есть ресурс, освободи его детерминированно, вызвав `Dispose()`». GC управляет **памятью**, а `Dispose` — **всеми остальными ресурсами**: файлами, соединениями с БД, сокетами, таймерами, подписками.

Если класс владеет только managed-ресурсами (другими `IDisposable`), хватает простого варианта:

```csharp
public sealed class ReportService : IDisposable
{
    private readonly StreamWriter _writer = new("report.txt");
    public void Dispose() => _writer.Dispose(); // финализатор не нужен: StreamWriter сам о себе позаботится
}
```

**Полный Dispose pattern** — для не-sealed класса, который владеет unmanaged-ресурсом (или чьи наследники могут):

```csharp
public class ResourceHolder : IDisposable
{
    private bool _disposed;

    ~ResourceHolder() => Dispose(false);        // страховка: забыли Dispose

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);              // финализатор больше не нужен
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;                  // идемпотентность: повторный вызов безопасен
        if (disposing)
        {
            // managed-ресурсы: другие IDisposable (Stream, DbConnection)
        }
        // unmanaged-ресурсы: дескрипторы, нативная память
        _disposed = true;
    }
}
```

Разбор каждой детали:
- **`disposing == true`** — вызов из `Dispose()`: всё ещё живо, можно трогать любые объекты.
- **`disposing == false`** — вызов из финализатора: managed-объекты могли быть уже финализированы → трогаем **только** unmanaged.
- **`GC.SuppressFinalize(this)`** — убирает объект из finalization queue: он будет собран за одну сборку, без f-reachable.
- **`protected virtual`** — наследник переопределяет `Dispose(bool)`, освобождает своё и вызывает `base.Dispose(disposing)`.
- **флаг `_disposed`** — `Dispose` могут вызвать несколько раз; методы после `Dispose` бросают `ObjectDisposedException` (`ObjectDisposedException.ThrowIf(_disposed, this)`).

> **Почему так?** Один метод `Dispose(bool)` содержит всю логику освобождения, а два входа (явный и через финализатор) отличаются только тем, что безопасно трогать. Это позволяет наследникам встроиться в цепочку без дублирования.

### `SafeHandle` — современная альтернатива

`SafeHandle` (например, `SafeFileHandle`) — готовая обёртка над дескриптором ОС с надёжным финализатором. Если твой класс хранит `SafeHandle` вместо `IntPtr`, **свой финализатор не нужен**: дескриптор — это уже managed-объект, который сам себя освободит, а тебе остаётся простой `Dispose()`.

> **Почему так?** `SafeHandle` решает тонкие проблемы, которые сложно сделать правильно вручную: гонку между использованием дескриптора и его закрытием, гарантию вызова финализатора даже при аварийной выгрузке, защиту от повторного использования номера дескриптора.

`using` (модуль 07) — синтаксис, который гарантирует вызов `Dispose()` в `finally`:

```csharp
using var writer = new ReportWriter(stream, handle);
writer.WriteLine("Итого");
// Dispose() будет вызван в конце блока даже при исключении
```

## 5. Утечки памяти в .NET

«Но ведь есть GC — откуда утечки?» GC собирает только **недостижимые** объекты. Утечка в managed-коде — это объект, который тебе больше не нужен, но **на него всё ещё ведёт ссылка** от root.

Классические источники:

| Источник | Что происходит |
|----------|----------------|
| **События** | издатель (`publisher`) хранит delegate → delegate хранит ссылку на подписчика (`Target`). Долгоживущий издатель держит всех подписчиков |
| **`static` поля и коллекции** | `static` — это root на всё время жизни приложения; `static List<T>`, в который только добавляют, растёт бесконечно |
| **Кэши без ограничений** | `Dictionary` как кэш без размера/срока жизни — та же утечка |
| **Таймеры** | `System.Threading.Timer`, не остановленный и не освобождённый, держит callback и его объект |
| **Closures** | лямбда, сохранённая надолго, держит все захваченные переменные (иногда — целый `this`) |
| **Не вызванный Dispose** | не освобождаются unmanaged-ресурсы, объекты ждут финализации |

Пример утечки через событие:

```csharp
public class Dashboard
{
    public Dashboard(StockTicker ticker)
    {
        ticker.PriceChanged += OnPriceChanged; // ticker → delegate → this
    }
    private void OnPriceChanged(object? s, PriceChangedEventArgs e) { /* ... */ }
}
// ticker живёт всё приложение; каждый открытый и «закрытый» Dashboard остаётся в памяти навсегда
```

Исправление — отписка (обычно в `Dispose`):

```csharp
public void Dispose() => _ticker.PriceChanged -= OnPriceChanged;
```

Важно: отписаться можно только **тем же** delegate. `ticker.PriceChanged -= (s, e) => Update(e);` не сработает — это новая лямбда. Подписывайся методом или сохраняй лямбду в поле.

> **Почему так?** Event — это multicast delegate, а delegate хранит две вещи: метод и объект (`Target`), на котором его вызвать. Значит, подписка = сильная ссылка от издателя на подписчика. Направление ссылки всегда «издатель → подписчик», поэтому опасно, когда издатель живёт дольше.

### `WeakReference<T>`

**Weak reference** (слабая ссылка) — ссылка, которая **не мешает** GC собрать объект.

```csharp
var cache = new WeakReference<byte[]>(new byte[1000]);
if (cache.TryGetTarget(out var data))
    Console.WriteLine(data.Length);  // объект ещё жив
else
    Console.WriteLine("собран GC — надо загрузить заново");
```

Применение: кэши «если ещё в памяти — используем», weak event pattern. Для привязки данных к чужим объектам без утечки есть `ConditionalWeakTable<TKey,TValue>`.

> **Почему так?** Слабая ссылка — компромисс: мы не управляем временем жизни объекта, но и не продлеваем его. Минус — недетерминированность: результат зависит от того, была ли сборка. Поэтому в коде и тестах слабые ссылки — крайняя мера, а основное решение утечки событий — явная отписка.

### Как искать утечки на практике

- Счётчики: `dotnet-counters monitor -p <pid>` (размер кучи, число сборок по поколениям).
- Снимок кучи: `dotnet-gcdump collect -p <pid>` → открыть в Visual Studio / PerfView, посмотреть, **кто держит** объекты (path to root).
- Профилировщики: dotMemory (JetBrains), Visual Studio Diagnostic Tools.

> 💼 **На собеседовании:** «Да, утечки в .NET бывают: GC собирает только недостижимые объекты. Типичные причины — неотписанные события от долгоживущего издателя, static-коллекции и кэши без ограничений, неостановленные таймеры. Ищу через dotnet-counters и снимок кучи — смотрю, какой root держит объект».

## 6. Меньше аллокаций: `Span<T>`, `stackalloc`, `ArrayPool<T>`

Каждая аллокация — это будущая работа GC. В горячих местах (парсеры, сериализация, обработка запросов) стоит не создавать лишнего.

### `Span<T>` и `ReadOnlySpan<T>`

`Span<T>` — «окно» на непрерывный участок памяти: массив, часть строки, память на стеке, нативная память. Создание среза (`Slice`, `[a..b]`) **ничего не копирует**.

```csharp
string line = "2026-10-04;ERROR;Disk full";
ReadOnlySpan<char> span = line;
ReadOnlySpan<char> level = span.Slice(11, 5);   // окно, без новой строки
Console.WriteLine(level.SequenceEqual("ERROR")); // вывод: True
int year = int.Parse(span[..4], CultureInfo.InvariantCulture); // разбор без Substring
Console.WriteLine(year);                         // вывод: 2026
```

Сравни: `line.Substring(11, 5)` — новая строка в куче; `line.Split(';')` — массив + 3 строки.

`Span<T>` — это **`ref struct`**: он может жить только на стеке.
- нельзя положить в поле класса, в `List<T>`, нельзя упаковать (boxing);
- нельзя захватить в лямбду;
- нельзя держать через `await` и `yield` (с C# 13 `ref struct` можно объявлять в async-методах, но не использовать по разные стороны `await`).

Когда нужно сохранить «окно» в поле или передать в async-метод — используй **`Memory<T>`** / `ReadOnlyMemory<T>`: обычная struct, может жить в куче, а `.Span` даёт `Span<T>` для работы.

> **Почему так?** `Span<T>` может указывать на стек (`stackalloc`). Если бы его разрешили сохранить в куче, ссылка пережила бы кадр стека и указывала бы на «мусор». Ограничение `ref struct` позволяет компилятору доказать безопасность без проверок в runtime — поэтому `Span<T>` такой же быстрый, как указатель, но безопасный.

### `stackalloc`

Выделение небольшого буфера на стеке — без GC вообще:

```csharp
Span<char> buffer = stackalloc char[64];
bool ok = 12345.TryFormat(buffer, out int written, provider: CultureInfo.InvariantCulture);
Console.WriteLine(buffer[..written].ToString()); // вывод: 12345
```

Только для **маленьких** и ограниченных размеров (сотни байт — единицы КБ): стек всего ~1 МБ, переполнение — `StackOverflowException`, который **нельзя поймать** — процесс падает.

### `ArrayPool<T>`

Пул переиспользуемых массивов. Берёшь `Rent`, отдаёшь `Return` — в `finally`.

```csharp
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096); // может вернуть массив БОЛЬШЕ 4096
try
{
    int read = stream.Read(buffer, 0, 4096);
    // работаем только с buffer[..read]
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);
}
```

Подвохи: массив может быть **длиннее** запрошенного и содержать **старые данные**; после `Return` им пользоваться нельзя.

> **Почему так?** Пул — классический компромисс «память в обмен на скорость»: держим несколько массивов про запас, зато не нагружаем GC (и не плодим объекты в LOH для больших буферов). Цена — ручное управление временем жизни, как в C: забыл `Return` — пул создаст новый массив, вернул дважды — два владельца одного массива.

Есть и пул объектов — `Microsoft.Extensions.ObjectPool` (используется в ASP.NET Core для `StringBuilder`). Простой свой пул ты напишешь в задаче со звёздочкой.

## 7. Строки и аллокации

`string` — immutable reference type (модуль 02). Каждая «модификация» создаёт **новую** строку:

```csharp
string result = "";
for (int i = 0; i < 1000; i++)
    result += i;  // 1000 новых строк; копируется всё больше и больше → O(n²) по памяти и времени
```

Правила:
- конкатенация в цикле → `StringBuilder` (растущий буфер, одна итоговая строка в `ToString()`);
- `string.Join`, `string.Concat` для коллекций — считают итоговую длину и аллоцируют один раз;
- интерполяция `$"..."` с C# 10 компилируется в `DefaultInterpolatedStringHandler` — эффективно, но всё равно создаёт итоговую строку;
- `Substring`, `Split`, `ToUpper`, `Trim` — новые строки; в горячем коде заменяй на `Span`-операции;
- сравнение без учёта регистра — `string.Equals(a, b, StringComparison.OrdinalIgnoreCase)`, а не `a.ToLower() == b.ToLower()` (две лишние строки);
- литералы **интернируются** (один экземпляр на процесс), строки, созданные в runtime, — нет.

Измерить аллокации можно так:

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();
string s = string.Concat(Enumerable.Repeat("ab", 100));
long after = GC.GetAllocatedBytesForCurrentThread();
Console.WriteLine(after - before > 0); // вывод: True (точное число зависит от runtime)
```

Для серьёзных замеров есть BenchmarkDotNet с `[MemoryDiagnoser]` — он показывает аллокации на операцию и число сборок Gen0/1/2.

> **Почему так?** Неизменяемость делает строки потокобезопасными, позволяет интернирование и безопасное использование как ключей словаря. Цена — аллокация на каждое изменение. `StringBuilder` и `Span` — инструменты, чтобы платить эту цену один раз.

## Типичные ошибки

1. **«Value types всегда на стеке».** Поле struct внутри класса, элемент массива, захваченная переменная — в куче.
2. **Финализатор «на всякий случай»** в классе без unmanaged-ресурсов — объект живёт дольше, сборка дороже, пользы ноль.
3. **В финализаторе трогают managed-поля** (`_stream.Dispose()` при `disposing == false`) — объект мог быть уже финализирован.
4. **Забыли `GC.SuppressFinalize(this)`** в `Dispose()` — объект после явного освобождения всё равно идёт через очередь финализации.
5. **`Dispose` не идемпотентен** — второй вызов бросает исключение или освобождает ресурс повторно.
6. **Подписка лямбдой и отписка «такой же» лямбдой** — это разные delegate, отписка не срабатывает.
7. **`GC.Collect()` «чтобы освободить память»** — вредит производительности.
8. **Кэш на `static Dictionary` без ограничения размера** — медленная утечка.
9. **`ArrayPool`: использование `buffer.Length` вместо реально прочитанного количества**, забытый `Return` или использование массива после `Return`.
10. **Большой `stackalloc`** или `stackalloc` в цикле — `StackOverflowException`.

## Шпаргалка

```csharp
// где лежит
int x = 5;                         // стек (локальная)
var arr = new int[10];             // массив и его int — куча
object o = x;                      // boxing → куча

// GC
GC.GetGeneration(obj);             // 0, 1 или 2
GC.CollectionCount(0);             // сколько раз собирался Gen 0
GC.GetTotalAllocatedBytes();       // всего выделено процессом
GC.GetAllocatedBytesForCurrentThread();

// Dispose pattern
~T() => Dispose(false);
public void Dispose() { Dispose(true); GC.SuppressFinalize(this); }
protected virtual void Dispose(bool disposing) { if (_disposed) return; if (disposing) {/*managed*/} /*unmanaged*/ _disposed = true; }
ObjectDisposedException.ThrowIf(_disposed, this);

// события без утечек
source.Event += OnEvent;  /* ... */  source.Event -= OnEvent;

// меньше аллокаций
ReadOnlySpan<char> s = text; s[..4]; s.Slice(5, 3); s.IndexOf(','); s.Trim();
int.Parse(span, NumberStyles.Integer, CultureInfo.InvariantCulture);
Span<byte> small = stackalloc byte[128];
var buf = ArrayPool<byte>.Shared.Rent(n); try { } finally { ArrayPool<byte>.Shared.Return(buf); }
```

## Глоссарий

| Термин | Что значит |
|--------|-----------|
| Stack | стек потока: кадры вызовов, локальные переменные; освобождается при выходе из метода |
| Managed heap | управляемая куча: объекты reference types, освобождается GC |
| Garbage collector (GC) | сборщик мусора: находит недостижимые объекты и освобождает их память |
| Root | корень: локальная переменная, static-поле, регистр, GC handle — откуда начинается обход |
| Mark & compact | пометить живые объекты, затем уплотнить кучу |
| Generation (Gen 0/1/2) | поколение: «возраст» объекта в сборках; молодые собираются чаще |
| Promotion | продвижение пережившего сборку объекта в следующее поколение |
| LOH | Large Object Heap: объекты ≥ 85 000 байт, собирается с Gen 2, по умолчанию не компактируется |
| Finalizer | `~T()`: вызывается GC перед освобождением; страховка для unmanaged-ресурсов |
| Finalization queue / f-reachable | очереди, через которые проходят объекты с финализатором |
| Unmanaged resource | ресурс вне контроля GC: дескриптор файла/сокета, нативная память |
| Dispose pattern | `Dispose()` + `Dispose(bool)` + финализатор + `GC.SuppressFinalize` |
| SafeHandle | обёртка над дескриптором ОС с надёжным финализатором |
| Memory leak (managed) | ненужный объект остаётся достижимым от root |
| WeakReference | ссылка, не мешающая GC собрать объект |
| Span&lt;T&gt; | `ref struct`-окно на непрерывную память без копирования |
| Memory&lt;T&gt; | аналог Span, который можно хранить в куче и передавать через await |
| stackalloc | выделение буфера на стеке |
| ArrayPool&lt;T&gt; | пул переиспользуемых массивов |
| Allocation | выделение памяти под объект в куче |

## Вопросы на собеседовании

<details><summary><b>Где хранятся value types и reference types?</b></summary>

Объекты reference types всегда в managed heap, а переменная хранит ссылку. Value type хранится «там, где объявлен»: локальная переменная — на стеке (или в регистре), поле класса — в куче внутри объекта, элемент массива — в куче. В кучу value type также попадает при boxing, при захвате в closure и в async/iterator-методах (переменные становятся полями state machine). Вообще стек — деталь реализации CLR, спецификация C# её не гарантирует.
</details>

<details><summary><b>Как работает garbage collector в .NET?</b></summary>

Это tracing generational compacting GC. Он останавливает потоки, начиная от roots (стеки, static-поля, регистры) помечает достижимые объекты, остальное считает мусором, а живые объекты уплотняет и обновляет ссылки. Куча разделена на поколения: Gen 0 — новые объекты, собирается часто и быстро; выжившие продвигаются в Gen 1, затем в Gen 2. Сборка запускается в основном при исчерпании бюджета Gen 0 — момент недетерминирован.
</details>

<details><summary><b>Зачем нужны поколения?</b></summary>

Из наблюдения, что большинство объектов умирают молодыми. Собирая только Gen 0, GC обрабатывает маленький объём памяти и быстро освобождает почти всё. Долгоживущие объекты в Gen 2 не сканируются при каждой сборке, а ссылки «старый → молодой» отслеживаются через card table. Это сокращает паузы.
</details>

<details><summary><b>Что такое LOH и чем он особенный?</b></summary>

Large Object Heap — куча для объектов от 85 000 байт (большие массивы, строки). Объекты там логически сразу в Gen 2, собираются только при full GC и по умолчанию не компактируются, потому что копировать большие блоки дорого. Из-за этого возможна фрагментация. Частые большие временные массивы — плохо; решение — переиспользовать буферы через `ArrayPool<T>`.
</details>

<details><summary><b>Зачем IDisposable, если есть GC?</b></summary>

GC управляет только памятью и делает это в непредсказуемый момент. А файлы, соединения с БД, сокеты, блокировки нужно освобождать сразу и детерминированно — их мало и они держат внешние ресурсы. `Dispose()` — явное освобождение, `using` гарантирует вызов даже при исключении. Финализатор — лишь страховка для unmanaged-ресурсов.
</details>

<details><summary><b>Что такое финализатор и почему его стоит избегать?</b></summary>

Метод `~T()`, который вызывается потоком финализации после того, как GC нашёл объект мёртвым. Такой объект переживает лишнюю сборку (через f-reachable очередь) и продвигается в старшее поколение, порядок и момент финализации не определены, а исключение в финализаторе роняет процесс. Поэтому финализатор пишут только для прямого владения unmanaged-ресурсом, а лучше используют `SafeHandle`.
</details>

<details><summary><b>Расскажите про Dispose pattern. Что такое Dispose(bool disposing)?</b></summary>

`Dispose()` вызывает `Dispose(true)` и `GC.SuppressFinalize(this)`; финализатор вызывает `Dispose(false)`. При `disposing == true` освобождаем managed и unmanaged ресурсы, при `false` — только unmanaged, потому что другие managed-объекты могли быть уже финализированы. Флаг `_disposed` делает метод идемпотентным. Метод `protected virtual`, чтобы наследники могли добавить свои ресурсы и вызвать `base.Dispose(disposing)`.

```csharp
public void Dispose() { Dispose(true); GC.SuppressFinalize(this); }
```
</details>

<details><summary><b>Зачем вызывать GC.SuppressFinalize?</b></summary>

После явного `Dispose()` ресурсы уже освобождены, и финализатор не нужен. `SuppressFinalize` убирает объект из finalization queue, поэтому он будет собран за одну сборку, без продвижения в старшее поколение и без работы finalizer thread.
</details>

<details><summary><b>Бывают ли утечки памяти в .NET? Приведите примеры.</b></summary>

Да: GC собирает только недостижимые объекты, а утечка — это ненужный, но достижимый объект. Примеры: подписка на событие долгоживущего объекта без отписки (издатель держит подписчика через delegate), static-коллекции и кэши без ограничения, неостановленные таймеры, closures, которые держат большие объекты. Плюс неосвобождённые unmanaged-ресурсы. Ищут через dotnet-counters, dotnet-gcdump, dotMemory — смотрят путь до root.
</details>

<details><summary><b>Почему не стоит вызывать GC.Collect()?</b></summary>

GC сам выбирает момент сборки по статистике аллокаций; ручной вызов делает full GC с паузой всего приложения и продвигает живые объекты в старшие поколения, где их сборка дороже. Обычно это ухудшает производительность. Исключения — бенчмарки, диагностика утечек, редкие сценарии после разовой большой загрузки.
</details>

<details><summary><b>Что такое Span&lt;T&gt; и зачем он нужен?</b></summary>

Это `ref struct` — окно на непрерывную память (массив, строку, стек, нативную память) без копирования. Позволяет парсить и резать данные без аллокаций (вместо `Substring`/`Split`). Ограничения: живёт только на стеке — нельзя в поле класса, в лямбду, через `await`. Для хранения в куче есть `Memory<T>`.
</details>

<details><summary><b>Что такое WeakReference и когда её использовать?</b></summary>

Слабая ссылка не мешает GC собрать объект; `TryGetTarget` говорит, жив ли он ещё. Используется для кэшей «если ещё в памяти» и weak event pattern. Минус — недетерминированность, поэтому основная защита от утечек через события — явная отписка в `Dispose`.
</details>

<details><summary><b>Что выведет код?</b></summary>

```csharp
struct Counter { public int Value; }
class Holder { public Counter C; }

var h = new Holder();
var copy = h.C;
copy.Value = 10;
Console.WriteLine(h.C.Value);
```

Выведет `0`. `Counter` — value type, хранится внутри объекта `Holder` в куче; `var copy = h.C` копирует значение в локальную переменную. Изменение копии не меняет поле. Чтобы изменить поле — `h.C.Value = 10` (это работает, потому что `h.C` — поле, а не свойство).
</details>
