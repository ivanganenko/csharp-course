## 1. Класс и объект

**Класс** (class) — это описание (чертёж): какие данные хранит объект и что он умеет делать. **Объект** (object, instance — экземпляр) — конкретная «вещь», созданная по этому чертежу с помощью `new`.

```csharp
public class Dog                 // класс — чертёж
{
    public string Name = "";     // поле (field) — данные
    public void Bark() => Console.WriteLine($"{Name}: Woof!");  // метод — поведение
}

var rex = new Dog { Name = "Rex" };   // объект №1
var bim = new Dog { Name = "Bim" };   // объект №2 — свои данные
rex.Bark();                           // вывод: Rex: Woof!
```

Класс — это **reference type** (ссылочный тип, см. модуль 02): переменная `rex` хранит не сам объект, а **ссылку** на него в managed heap (управляемой куче).

```csharp
var a = new Dog { Name = "Rex" };
var b = a;            // копируется ССЫЛКА, объект один
b.Name = "Max";
Console.WriteLine(a.Name);   // вывод: Max
```

> **Почему так?** Объекты бывают большими (тысячи полей, коллекции), и копировать их целиком при каждом присваивании или передаче в метод было бы дорого. Передача ссылки стоит 8 байт на 64-битной системе. Обратная сторона — **aliasing** (несколько переменных указывают на один объект): изменение через одну ссылку видно через все. Именно поэтому дальше мы так заботимся об инкапсуляции и неизменяемости.

> 💼 **На собеседовании:** «Класс — это тип, описание данных и поведения. Объект — экземпляр класса в памяти, создаётся через `new`. Класс — reference type: переменная хранит ссылку, при присваивании копируется ссылка, а не объект».

### Три кита ООП (и четвёртый)

| Принцип | Суть | Модуль |
|---|---|---|
| **Encapsulation** (инкапсуляция) | скрываем внутреннее состояние, наружу — только безопасные операции | 04 |
| **Inheritance** (наследование) | новый класс получает члены базового | 05 |
| **Polymorphism** (полиморфизм) | один интерфейс — разное поведение | 05 |
| **Abstraction** (абстракция) | показываем «что делает», а не «как» | 04–05 |

## 2. Поля и свойства

**Поле** (field) — переменная внутри класса. **Свойство** (property) — пара методов `get`/`set`, которая *выглядит* как поле.

```csharp
public class Person
{
    private int _age;                 // поле: private, имя с _

    public int Age                    // свойство с явным backing field (полем-хранилищем)
    {
        get => _age;
        set
        {
            if (value < 0) throw new ArgumentOutOfRangeException(nameof(value));
            _age = value;             // value — присваиваемое значение
        }
    }

    public string Name { get; set; } = "";   // auto-property: компилятор сам создаст скрытое поле
}
```

Виды свойств:

```csharp
public string Id { get; }                 // get-only: присвоить можно только в конструкторе
public decimal Balance { get; private set; }  // читают все, меняет только сам класс
public string Email { get; init; }        // можно задать только при создании (new X { Email = ... })
public string FullName => $"{First} {Last}";  // вычисляемое (computed): ничего не хранит
```

С C# 14 (.NET 10) есть ключевое слово `field` — доступ к автоматическому полю без объявления своего:

```csharp
public string Name
{
    get;
    set => field = value?.Trim() ?? throw new ArgumentNullException(nameof(value));
}
```

> **Почему так?** Почему не делать всё публичными полями? Потому что свойство — это **методы**, и за ними можно спрятать логику: валидацию, вычисление, логирование, ленивую загрузку — **не меняя публичный API**. Если сегодня `public int Age;` — поле, а завтра понадобилась проверка, придётся превратить его в свойство, а это **breaking change** (ломающее изменение) на уровне IL: все зависимые сборки нужно перекомпилировать. Плюс многие библиотеки (сериализация JSON, data binding, EF Core) работают именно со свойствами. Поэтому правило: **поля — `private`, наружу — свойства**.

> 💼 **На собеседовании:** «Поле — это просто переменная в объекте. Свойство — синтаксический сахар над методами get_X/set_X, через него можно добавить валидацию и контролировать доступ (например, `private set`). Публичные поля — плохая практика: нарушают инкапсуляцию, и их нельзя потом превратить в свойство без перекомпиляции клиентов».

## 3. Инкапсуляция и инварианты

**Инкапсуляция** (encapsulation) — объект сам отвечает за своё состояние: данные скрыты, изменить их можно только через методы, которые соблюдают правила.

**Инвариант** (invariant) — условие, которое истинно для объекта **всегда**, между любыми вызовами методов. Для банковского счёта: «баланс не отрицательный», «история содержит все операции».

Плохо — инварианты держатся «на честном слове»:

```csharp
public class BadAccount
{
    public decimal Balance;                       // кто угодно напишет Balance = -1_000_000
    public List<string> History = new();          // кто угодно сделает History.Clear()
}
```

Хорошо — состояние защищено:

```csharp
public class Account
{
    private readonly List<decimal> _operations = new();

    public decimal Balance { get; private set; }
    public IReadOnlyList<decimal> Operations => _operations.AsReadOnly();

    public void Withdraw(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);   // guard clause
        if (amount > Balance)
            throw new InvalidOperationException("Insufficient funds");
        Balance -= amount;              // меняем состояние ТОЛЬКО после всех проверок
        _operations.Add(-amount);
    }
}
```

Правила хорошей инкапсуляции:

1. **Проверь → потом меняй.** Если метод бросает исключение, объект должен остаться в прежнем валидном состоянии.
2. **Не отдавай наружу изменяемые внутренности.** `IReadOnlyList<T>` — это только «вид» для компилятора: `(List<T>)account.Operations` вернёт оригинал. Отдавай `AsReadOnly()` (обёртку) или копию.
3. **Объект валиден с момента создания.** Проверки — в конструкторе.
4. **Tell, don't ask** («говори, а не спрашивай»): вместо `if (acc.Balance >= x) acc.Balance -= x;` снаружи — метод `acc.Withdraw(x)` внутри.

> **Почему так?** Если правило проверяется снаружи, его рано или поздно забудут проверить в одном из 20 мест вызова. Если правило внутри класса — его невозможно обойти. Инкапсуляция переносит ответственность за корректность туда, где лежат данные. Это же упрощает отладку: если баланс стал отрицательным, искать надо в одном классе, а не во всём проекте.

> 💼 **На собеседовании:** «Инкапсуляция — это сокрытие состояния и предоставление контролируемого API, чтобы объект сам поддерживал свои инварианты. Пример: у счёта `Balance { get; private set; }`, а изменить его можно только через `Deposit`/`Withdraw` с проверками».

## 4. Конструкторы и инициализация

**Конструктор** (constructor) — специальный метод, который вызывается при `new` и приводит объект в валидное начальное состояние. Имя = имя класса, нет возвращаемого типа.

```csharp
public class Rectangle
{
    public Rectangle(double width, double height)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(width);
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(height);
        Width = width;
        Height = height;
    }

    public Rectangle(double side) : this(side, side) { }   // цепочка: вызывает другой конструктор

    public Rectangle() : this(1) { }                        // и ещё одна

    public double Width { get; }
    public double Height { get; }
}
```

- Если не написать ни одного конструктора, компилятор добавит **конструктор по умолчанию** (без параметров). Как только написал свой — дефолтного больше нет.
- `this(...)` — вызов другого конструктора **этого же** класса до тела текущего. Так валидация живёт в одном месте.
- `base(...)` — вызов конструктора базового класса (модуль 05).

### Object initializer и collection initializer

```csharp
var p = new Person { Name = "Anna", Age = 30 };   // object initializer
// компилятор превращает это в: var tmp = new Person(); tmp.Name = "Anna"; tmp.Age = 30; var p = tmp;

var list = new List<int> { 1, 2, 3 };             // collection initializer (вызывает Add)
var dict = new Dictionary<string, int> { ["a"] = 1, ["b"] = 2 };
int[] arr = [1, 2, 3];                            // collection expression (C# 12)
```

### `init` и `required`

```csharp
public class User
{
    public required string Login { get; init; }   // обязательно задать при создании
    public string? Nickname { get; init; }        // можно задать только при создании
}

var u = new User { Login = "anna" };   // ок
// u.Login = "boris";                  // ошибка CS8852: init-only
// var x = new User();                 // ошибка CS9035: не задан required Login
```

> **Почему так?** Длинные конструкторы с 8 параметрами нечитаемы (`new User("a", null, null, true, 3, ...)` — что здесь что?). Object initializer читается как «имя = значение», но раньше требовал публичного `set` — то есть объект можно было изменить после создания. `init` даёт читаемость initializer'а **и** неизменяемость после создания, а `required` возвращает гарантию «без этого поля объект не создать», которую раньше давал только конструктор. Причём проверка — на этапе **компиляции**, а не в runtime.

> 💼 **На собеседовании:** «`set` — можно менять когда угодно, `init` — только при инициализации объекта (в конструкторе или object initializer), `required` — компилятор заставляет задать свойство при создании».

### Ключевое слово `this`

`this` — ссылка на текущий объект. Нужна, когда имя параметра совпадает с именем поля, чтобы передать себя в другой метод, или для цепочки конструкторов.

```csharp
public Node(int value) { this.value = value; }   // если поле без _ (у нас принято _value)
list.Add(this);                                   // передать себя
```

## 5. `static`: члены, классы, конструкторы

Обычные (instance) члены принадлежат **объекту**: у каждого экземпляра свои поля. `static`-члены принадлежат **типу**: одна копия на всё приложение (точнее — на AppDomain/процесс).

```csharp
public class Counter
{
    private static int _total;          // одно на всех
    private int _mine;                  // у каждого объекта своё

    public void Hit() { _mine++; _total++; }
    public static int Total => _total;  // static-член: вызывается через тип
}

var a = new Counter(); var b = new Counter();
a.Hit(); a.Hit(); b.Hit();
Console.WriteLine(Counter.Total);       // вывод: 3
```

- Внутри `static`-метода **нет `this`** — нельзя обращаться к instance-членам.
- **`static class`** — нельзя создать экземпляр и унаследоваться; только static-члены. Примеры: `Math`, `Console`, `File`, классы extension methods.
- **Static constructor** (статический конструктор) — `static Counter() { ... }`: без модификаторов и параметров, вызывается runtime **один раз** перед первым обращением к типу. Потокобезопасен (CLR гарантирует один вызов).

```csharp
public static class AppInfo
{
    public static readonly DateTime StartedAt;
    static AppInfo() => StartedAt = DateTime.UtcNow;   // выполнится ровно один раз
}
```

> **Почему так?** Static — для того, что не зависит от конкретного объекта: утилиты (`Math.Max`), фабрики (`Temperature.FromKelvin`), счётчики, кэши, константы. Но static-**состояние** — это глобальная переменная: его видно отовсюду, его трудно подменить в тестах, и оно требует потокобезопасности (два потока одновременно делают `_total++` → значение может потеряться). Поэтому в реальных проектах static-состояние минимизируют и заменяют на сервисы с lifetime Singleton через DI (модуль 15). Static-**методы** без состояния — нормально.

> 💼 **На собеседовании:** «Static-член принадлежит типу, а не экземпляру — одна копия на всё приложение. Static-класс нельзя инстанцировать и наследовать. Статический конструктор вызывается CLR один раз до первого обращения к типу, потокобезопасно. Минус static-состояния — глобальность, сложность тестирования и потокобезопасность».

### `const` vs `readonly` vs `static readonly`

| | `const` | `readonly` (поле) | `static readonly` |
|---|---|---|---|
| Когда известно значение | при компиляции | в runtime | в runtime |
| Где присваивается | при объявлении | при объявлении или в конструкторе | при объявлении или в static-конструкторе |
| Какие типы | примитивы, `string`, enum, `null` | любые | любые |
| Принадлежит | типу (неявно static) | экземпляру | типу |
| Копируется в другие сборки | **да** (значение «вшивается» в IL вызывающего кода) | нет | нет |

```csharp
public class Config
{
    public const int MaxUsers = 100;                         // literal, вшивается в код
    public static readonly TimeSpan Timeout = TimeSpan.FromSeconds(30);  // объект — только readonly
    private readonly Guid _instanceId = Guid.NewGuid();      // своё у каждого объекта
}
```

> **Почему так?** Ловушка версионирования: библиотека A объявляет `public const int Version = 1`, приложение B использует её. Компилятор подставил `1` прямо в IL приложения B. Обновили A до `Version = 2`, но B не перекомпилировали → B всё ещё видит `1`. С `static readonly` B читает значение из A в runtime и увидит `2`. Поэтому: `const` — для действительно вечных значений (π, количество дней в неделе, внутренние константы), `static readonly` — для всего, что может поменяться, и для не-примитивных типов.

> ⚠️ `readonly` защищает **ссылку**, а не объект: `private readonly List<int> _items = new();` — переприсвоить `_items` нельзя, но `_items.Add(1)` — можно.

## 6. Модификаторы доступа, `partial`, nested types

| Модификатор | Кто видит |
|---|---|
| `public` | все |
| `private` | только этот тип (по умолчанию для членов класса) |
| `protected` | этот тип и наследники |
| `internal` | вся текущая сборка (assembly) (по умолчанию для типов верхнего уровня) |
| `protected internal` | наследники **ИЛИ** код этой сборки (объединение) |
| `private protected` | наследники **И** только в этой сборке (пересечение) |
| `file` (C# 11) | тип виден только в этом файле (для генераторов кода) |

```csharp
public class Base
{
    private int _a;              // только Base
    protected int B;             // Base и наследники (в любой сборке)
    internal int C;              // любой код этой сборки
    protected internal int D;    // наследники где угодно + вся эта сборка
    private protected int E;     // наследники, но только из этой же сборки
}
```

Значения по умолчанию: члены класса — `private`, классы верхнего уровня — `internal`, члены интерфейса — `public`.

> **Почему так?** Принцип **наименьших привилегий**: открывай минимум. Всё `public` — это обещание (контракт) для внешних пользователей, его тяжело менять. `private`-код можно рефакторить свободно. `internal` удобен для «служебных» классов библиотеки, которые не должны торчать наружу. Поэтому дефолт — самый закрытый уровень, и тебе приходится **осознанно** открывать доступ.

### `partial`

`partial` позволяет разделить класс (или метод) на несколько файлов. Компилятор склеит их в один тип.

```csharp
// Person.cs
public partial class Person { public string Name { get; set; } = ""; }
// Person.Validation.cs
public partial class Person { public bool IsValid() => Name.Length > 0; }
```

Используется в основном **генераторами кода**: WinForms/WPF дизайнер, source generators (`[GeneratedRegex]`, `System.Text.Json`), EF Core scaffold. Сгенерированная часть в одном файле, твоя — в другом, перегенерация не затирает твой код. С C# 13–14 бывают и `partial`-свойства и конструкторы.

### Nested types (вложенные типы)

```csharp
public class LinkedList
{
    private Node? _head;
    private sealed class Node        // виден только внутри LinkedList
    {
        public int Value;
        public Node? Next;
    }
}
```

Вложенный тип имеет доступ к `private`-членам внешнего. Используй, когда тип — деталь реализации одного класса (узел списка, enumerator, builder). Если вложенный тип нужен снаружи — обычно лучше вынести его на верхний уровень.

> **Почему так?** Nested `private` тип — сильнейшая инкапсуляция: никто снаружи не может даже упомянуть `Node`, поэтому его можно менять как угодно. Но публичные вложенные типы (`Outer.Inner`) неудобны в использовании, и рекомендации .NET советуют избегать их в публичном API.

## 7. Extension methods

**Extension method** (метод расширения) — статический метод, который вызывается как метод экземпляра. Позволяет «добавить» метод к типу, который ты не можешь изменить (`string`, `int`, чужая библиотека).

```csharp
public static class StringExtensions               // 1. static-класс (не вложенный, не generic)
{
    public static bool IsPalindrome(this string s)  // 2. static-метод, 3. this перед первым параметром
    {
        var reversed = new string(s.Reverse().ToArray());
        return string.Equals(s, reversed, StringComparison.OrdinalIgnoreCase);
    }
}

Console.WriteLine("Level".IsPalindrome());   // вывод: True
// компилятор превращает это в StringExtensions.IsPalindrome("Level")
```

Важные детали:

- Нужен `using` на namespace, где лежит класс с расширениями.
- **Метод экземпляра всегда побеждает**: если у типа есть свой метод с подходящей сигнатурой, extension не вызовется.
- Extension method **не имеет доступа** к `private`-членам — он снаружи класса.
- Его **можно вызвать на `null`** — исключения не будет, пока ты сам не обратишься к параметру.
- Весь LINQ (`Where`, `Select`, `OrderBy` — модуль 11) — это extension methods для `IEnumerable<T>`.

C# 14 добавил новый синтаксис **extension members** (блоки `extension(string s) { ... }`), где можно объявлять ещё и extension-свойства. Классический синтаксис с `this` по-прежнему основной и встречается в 99% кода — его и спрашивают.

> **Почему так?** Extension methods придуманы для LINQ: нужно было добавить десятки методов ко **всем** коллекциям (`IEnumerable<T>`), не меняя интерфейс (добавление метода в интерфейс сломало бы все его реализации). Расширения дают fluent-синтаксис (`list.Where(...).Select(...)`) без наследования и без изменения исходного типа. Минус — они «магические»: глядя на `x.Foo()`, не видно, откуда `Foo`. Поэтому не злоупотребляй: расширение должно быть естественным для типа и без побочных эффектов.

> 💼 **На собеседовании:** «Extension method — static-метод в static-классе, первый параметр с `this`. Вызывается как метод экземпляра, но компилируется в обычный статический вызов. Не видит private-члены, проигрывает методу экземпляра с той же сигнатурой, может быть вызван на null. Весь LINQ построен на них».

## 8. `ToString`, `object` и value objects

Любой класс неявно наследуется от `System.Object` и получает методы `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`. По умолчанию `ToString()` возвращает полное имя типа — бесполезно в логах и отладчике.

```csharp
public sealed class Point
{
    public Point(int x, int y) { X = x; Y = y; }
    public int X { get; }
    public int Y { get; }
    public override string ToString() => $"({X}, {Y})";
}

Console.WriteLine(new Point(1, 2));   // вывод: (1, 2)   (без override: Module04.Point)
```

`Console.WriteLine`, интерполяция строк, отладчик — все вызывают `ToString()`. Для чисел и дат внутри `ToString` думай о культуре: `1.5.ToString()` на русской Windows даст `"1,5"`. Для машинного формата — `CultureInfo.InvariantCulture`.

### Value object (объект-значение)

**Value object** — объект, который определяется своими **значениями**, а не идентичностью: `Money(10, "USD")`, `DateRange`, `Email`, `Temperature`. Признаки:

- **immutable** (неизменяемый): после создания не меняется, операции возвращают новый объект;
- **самовалидирующийся**: невалидный объект нельзя создать;
- **равенство по значению**: два `Money(10, "USD")` — одно и то же (это сделаем в модуле 06).

```csharp
var price = new Money(10m, "USD");
var withTax = price.Multiply(1.2m);   // price не изменился — как string.ToUpper()
```

> **Почему так?** Неизменяемый объект можно безопасно передавать куда угодно: никто его «не испортит» у тебя за спиной (вспомни aliasing из раздела 1), он потокобезопасен без `lock`, его можно использовать как ключ словаря. `string` и `DateTime` в .NET устроены именно так. А `decimal` + валюта в одном типе защищает от классической ошибки «сложили доллары с евро» и от потери копеек на `double`.

> ⚠️ Сейчас `new Money(1, "USD") == new Money(1, "USD")` вернёт **`false`**: для классов `==` и `Equals` по умолчанию сравнивают **ссылки**. Как это исправить — тема модуля 06.

## Типичные ошибки

1. **Публичные поля** вместо свойств: `public decimal Balance;` — любой может записать что угодно.
2. **Публичный `set` у свойства, которое охраняет инвариант**: `public decimal Balance { get; set; }`. Нужен `private set` или get-only.
3. **Отдают наружу внутренний `List<T>`** (даже как `IReadOnlyList<T>`) — его можно привести обратно и изменить.
4. **Сначала меняют состояние, потом проверяют** — после исключения объект остаётся «наполовину изменённым».
5. **Валидация продублирована** в конструкторе, setter'е и фабриках — рано или поздно в одном месте её забудут поправить. Делай одну точку проверки.
6. **`const` для значений, которые могут измениться**, или для публичных констант библиотеки — ловушка версионирования.
7. **Изменяемое static-состояние без потокобезопасности** (`_count++` в конструкторе).
8. **Static-класс «Utils» на 2000 строк** — свалка несвязанных методов. Группируй по смыслу.
9. **Форматирование чисел без культуры** (`amount.ToString()`) там, где нужен стабильный формат.
10. **Проверка `NaN`/`null` забыта**: `value < min` для `NaN` даёт `false`, и проверка «пропускает» мусор.

## Шпаргалка

```csharp
public sealed class Example                      // sealed — если наследование не задумано
{
    public const int Max = 10;                   // compile-time константа
    public static readonly string Prefix = "X";  // runtime-константа типа
    private static int _count;                   // общее для всех экземпляров
    private readonly List<int> _items = new();   // ссылку не переприсвоить

    static Example() { }                         // static ctor: один раз, до первого обращения
    public Example(string name) : this(name, 0) { }   // цепочка конструкторов
    public Example(string name, int level)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(name);  // guard clause
        Name = name; Level = level;
    }

    public string Name { get; }                  // get-only — только конструктор
    public int Level { get; private set; }       // меняет только класс
    public string? Tag { get; init; }            // только при создании
    public required string Code { get; init; }   // обязательно при создании
    public string Title => $"{Prefix}{Name}";    // вычисляемое
    public IReadOnlyList<int> Items => _items.AsReadOnly();
    public override string ToString() => Title;
}

public static class Ext { public static int Twice(this int x) => x * 2; }   // 5.Twice() == 10
```

| Термин | Что значит |

| field | переменная-член класса |
| property | пара методов get/set с синтаксисом поля |
| auto-property | свойство, для которого компилятор сам создаёт скрытое поле |
| backing field | поле, в котором свойство хранит значение |
| computed property | свойство без хранения, вычисляется из других данных |

| invariant | условие, которое всегда истинно для объекта |
| guard clause | проверка аргументов в начале метода с ранним выходом/исключением |

| immutable | неизменяемый после создания |

## Вопросы на собеседовании

<details><summary><b>Чем поле отличается от свойства? Почему публичные поля — плохо?</b></summary>

Поле — переменная внутри объекта. Свойство — пара методов `get_X`/`set_X`, которая используется с синтаксисом поля. В свойство можно добавить валидацию, вычисление, разный уровень доступа к get и set (`private set`). Публичное поле нарушает инкапсуляцию: любой код может записать невалидное значение. Кроме того, замена поля на свойство — breaking change на уровне IL: клиентские сборки придётся перекомпилировать. Плюс сериализаторы и data binding работают со свойствами.
</details>

<details><summary><b>Что такое инкапсуляция? Приведите пример.</b></summary>

Инкапсуляция — это сокрытие внутреннего состояния и предоставление наружу только операций, которые сохраняют инварианты объекта. Пример: у `BankAccount` свойство `Balance { get; private set; }`, а менять баланс можно только через `Deposit`/`Withdraw`, которые проверяют, что сумма положительная и денег хватает. Так правило «баланс не отрицательный» невозможно нарушить извне. Это не только `private` — это ещё и «не отдавать изменяемые внутренности» (возвращать `AsReadOnly()`, копии).
</details>

<details><summary><b>Разница между <code>const</code>, <code>readonly</code> и <code>static readonly</code>?</b></summary>

`const` — значение известно при компиляции, только примитивы/`string`/enum, неявно static, и значение **вшивается** в IL вызывающего кода (даже в других сборках). `readonly` — поле экземпляра, присваивается при объявлении или в конструкторе, значение в runtime, может быть любого типа. `static readonly` — то же, но одно на тип, присваивается в static-конструкторе или при объявлении. Ловушка `const`: если поменять значение в библиотеке и не перекомпилировать клиента, клиент увидит старое значение. И `readonly` защищает только ссылку, а не содержимое объекта.
</details>

<details><summary><b>Какие есть модификаторы доступа? Что по умолчанию?</b></summary>

`public` — все; `private` — только этот тип; `protected` — тип и наследники; `internal` — вся сборка; `protected internal` — наследники ИЛИ своя сборка; `private protected` — наследники И только в своей сборке. Плюс `file` для типов, видимых в одном файле. По умолчанию члены класса — `private`, типы верхнего уровня — `internal`, члены интерфейса — `public`. Принцип — открывать минимум необходимого.
</details>

<details><summary><b>Что такое static-класс, static-конструктор? Когда static — плохая идея?</b></summary>

Static-класс содержит только static-члены, его нельзя создать через `new` и унаследовать (`Math`, `Console`, классы extension methods). Static-конструктор вызывается CLR один раз, потокобезопасно, перед первым обращением к типу; у него нет модификаторов доступа и параметров. Static-методы без состояния — нормально. Изменяемое static-состояние — глобальная переменная: сложно тестировать (не подменить), нужна потокобезопасность, скрытые зависимости между частями кода. В реальных приложениях вместо этого используют Singleton-сервис через DI.
</details>

<details><summary><b>Чем <code>init</code> отличается от <code>set</code> и от get-only свойства? Что делает <code>required</code>?</b></summary>

Get-only (`{ get; }`) можно присвоить только в конструкторе. `init` — в конструкторе **и** в object initializer, но после создания объекта — нельзя. `set` — когда угодно. `required` (C# 11) заставляет компилятор проверить, что свойство задано при создании (ошибка CS9035 иначе). Вместе `required` + `init` дают читаемое создание через initializer и неизменяемый объект без конструктора на 10 параметров.
</details>

<details><summary><b>Что такое extension method? Какие у него ограничения?</b></summary>

Статический метод в статическом (не generic, не вложенном) классе, у первого параметра модификатор `this`. Вызывается как метод экземпляра, но компилятор превращает вызов в обычный статический. Ограничения: нет доступа к private-членам; если у типа есть метод экземпляра с той же сигнатурой — победит он; нужен `using` на namespace. Можно вызвать на `null` без NullReferenceException. LINQ целиком построен на extension methods для `IEnumerable<T>`.
</details>

<details><summary><b>Зачем цепочка конструкторов <code>this(...)</code>?</b></summary>

Чтобы логика инициализации и валидации была в одном конструкторе, а остальные перегрузки лишь подставляли значения по умолчанию. Без этого проверки дублируются, и при изменении правил их забывают обновить в одном из конструкторов. `this(...)` выполняется **до** тела текущего конструктора. Альтернатива — optional-параметры, но у них свои проблемы с версионированием (значения по умолчанию тоже вшиваются в вызывающий код).
</details>

<details><summary><b>Что выведет код?</b>

```csharp
var a = new Box { Value = 1 };
var b = a;
b.Value = 2;
Console.WriteLine(a.Value);
class Box { public int Value { get; set; } }
```
</summary>

`2`. `Box` — класс, то есть reference type: `b = a` копирует ссылку, оба указывают на один объект. Если бы `Box` был `struct`, вывелось бы `1` (копируется значение) — это тема модуля 06.
</details>

<details><summary><b>Зачем <code>partial</code>-классы?</b></summary>

Чтобы разделить один тип на несколько файлов. Главное применение — сгенерированный код: дизайнеры WinForms/WPF, source generators, scaffold EF Core генерируют свою часть, а разработчик пишет свою в другом файле, и перегенерация её не затирает. Компилятор склеивает части в один тип, модификаторы и базовый класс должны совпадать. Делить вручную большой класс на partial-файлы обычно признак того, что класс слишком большой и его стоит разбить по ответственностям.
</details>

<details><summary><b>Почему <code>IReadOnlyList&lt;T&gt;</code> не гарантирует, что список не изменят?</b></summary>

`IReadOnlyList<T>` — это интерфейс, «вид» на объект. Если вернуть внутренний `List<T>` как `IReadOnlyList<T>`, вызывающий код может сделать `(List<T>)x` или `x as IList<T>` и изменить оригинал. Для настоящей защиты возвращают `list.AsReadOnly()` (обёртку `ReadOnlyCollection<T>`, у которой Add бросает NotSupportedException), копию (`ToArray()`) или immutable-коллекцию. Выбор — компромисс: обёртка дешёвая, но видит изменения оригинала; копия стоит памяти, зато «снимок».
</details>

<details><summary><b>Что такое value object? Почему его делают неизменяемым?</b></summary>

Объект, который определяется значениями, а не идентичностью: деньги, диапазон дат, email, координата. Делают неизменяемым, валидируют в конструкторе, операции возвращают новый объект. Неизменяемость даёт безопасность при передаче (никто не изменит у тебя за спиной), потокобезопасность без блокировок, возможность использовать как ключ словаря. Для полноценного value object нужно ещё равенство по значению — `Equals`/`GetHashCode` или `record` (модуль 06).
</details>
