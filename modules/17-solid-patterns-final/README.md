# Модуль 17. SOLID, паттерны, финальный проект и подготовка к собеседованию

> **Зачем:** на собеседовании Junior почти всегда спрашивают SOLID и 2–3 паттерна, а потом — «расскажите о своём проекте». В работе принципы проектирования отличают код, который легко менять, от кода, который страшно трогать. Этот модуль собирает весь курс воедино: рефакторинг legacy-кода, финальный проект и план подготовки к интервью. **Время:** ~12–20 ч (+ финальный проект). **Нужно:** все предыдущие модули, особенно 05, 14, 15, 16.

## Что ты будешь уметь

- Объяснять каждый принцип SOLID на примере «до/после» и находить его нарушения в коде.
- Применять DRY, KISS, YAGNI — и понимать, когда они противоречат друг другу.
- Узнавать и реализовывать паттерны Strategy, Factory Method, Decorator, Adapter, Builder, Observer, Repository/Unit of Work, Singleton (и знать, почему Singleton — через DI).
- Безопасно рефакторить legacy-код под защитой характеризационных тестов.
- Описывать слоистую/чистую архитектуру и git workflow команды (branch → PR → code review).
- Рассказывать о своём проекте по STAR и отвечать на поведенческие вопросы.

## 1. Зачем вообще «принципы проектирования»

Код читают в 10 раз чаще, чем пишут, и **меняют** постоянно: новые требования, баги, интеграции. Хороший дизайн — это не «красиво», а **дёшево менять**: правка в одном месте, не ломающая другие, и возможность проверить её тестом.

Признаки плохого дизайна («запахи кода», code smells):
- **Rigidity** (жёсткость) — простое изменение требует правок в 10 местах.
- **Fragility** (хрупкость) — правка в одном месте ломает другое, далёкое.
- **Immobility** — кусок нельзя переиспользовать, он «прирос» к остальному.
- Длинные методы, `switch` по типу, повторяющийся код, `new` и `static` внутри бизнес-логики, «магические числа».

> **Почему так?** Принципы SOLID сформулировал Роберт Мартин («Uncle Bob») как ответ на эти проблемы. Это не законы, а эвристики: их цель — **снизить связанность** (coupling — насколько классы зависят друг от друга) и **повысить связность** (cohesion — насколько содержимое класса относится к одной задаче). Слепое следование им даёт обратный эффект — переусложнение (см. KISS/YAGNI).

## 2. S — Single Responsibility Principle

**У класса должна быть одна причина для изменения** (одна ответственность перед одной «группой заказчиков»).

```csharp
// ❌ До: отчёт сам считает, форматирует и сохраняет
public class SalesReport
{
    public decimal CalculateTotal(List<Order> orders) => orders.Sum(o => o.Total);
    public string ToHtml(List<Order> orders) => "<table>...</table>";
    public void SaveToFile(string html, string path) => File.WriteAllText(path, html);
}

// ✅ После: каждое — своё
public sealed class SalesCalculator { public decimal Total(IEnumerable<Order> orders) => orders.Sum(o => o.Total); }
public sealed class HtmlReportFormatter { public string Format(SalesSummary s) => "..."; }
public sealed class FileReportStorage(string folder) { public void Save(string name, string content) { ... } }
```

Бухгалтерия поменяла формулу — правим только `SalesCalculator`; дизайнер поменял вёрстку — только форматтер.

> **Почему так?** Когда в одном классе несколько ответственностей, изменение одной рискует сломать другую, а тестировать приходится всё вместе (для проверки формулы нужен файл на диске). Маленькие классы проще понимать, тестировать и переиспользовать. Компромисс — больше файлов и «прыжков» по коду; не дроби до классов из одной строки без причины.

> 💼 **На собеседовании:** «SRP — это не "класс делает одну вещь", а "у класса одна причина меняться"». Пример: `OrderProcessor`, который и считает скидки, и шлёт email, и пишет в БД.

## 3. O — Open/Closed Principle

**Код открыт для расширения, но закрыт для изменения**: новое поведение добавляется новым кодом, а не правкой старого.

```csharp
// ❌ До: каждый новый способ доставки — правка switch (и риск сломать старые)
decimal Cost(string type, decimal weight) => type switch
{
    "courier" => 350,
    "post" => 250 + 60 * Math.Ceiling(weight - 1),
    _ => throw new ArgumentException()
};

// ✅ После: Strategy + полиморфизм
public interface IDeliveryMethod { string Code { get; } decimal CalculateCost(DeliveryContext ctx); }
public sealed class CourierDelivery : IDeliveryMethod { ... }
public sealed class DroneDelivery : IDeliveryMethod { ... }  // новый класс, старые не тронуты
```

> **Почему так?** Уже протестированный и работающий код — ценность; каждая правка в нём — риск регрессии. Расширение через новые классы (полиморфизм, модуль 05) локализует изменения. Но не делай «точки расширения» заранее везде — только там, где изменения реально происходят (YAGNI). `switch` по 2–3 стабильным вариантам — нормально.

> 💼 **На собеседовании:** классический пример — замена `switch`/`if-else` по типу на полиморфизм (Strategy). Ещё пример — middleware в ASP.NET Core: добавляешь поведение, не меняя фреймворк.

## 4. L — Liskov Substitution Principle

**Объекты подкласса должны подставляться вместо базового класса без нарушения корректности программы.** Наследник не должен усиливать предусловия, ослаблять постусловия и ломать инварианты базового типа.

```csharp
// ❌ Классика: Square : Rectangle
public class Rectangle { public virtual int Width { get; set; } public virtual int Height { get; set; } }
public class Square : Rectangle
{
    public override int Width  { set { base.Width = value; base.Height = value; } }
    public override int Height { set { base.Width = value; base.Height = value; } }
}
void Resize(Rectangle r) { r.Width = 5; r.Height = 10; Console.WriteLine(r.Width * r.Height); }
Resize(new Square()); // вывод: 100, а код, написанный для Rectangle, ожидал 50

// ❌ Ещё: наследник бросает NotSupportedException там, где база работает
public class ReadOnlyList<T> : List<T> { public new void Add(T item) => throw new NotSupportedException(); }
```

> **Почему так?** Полиморфизм работает, только если код, написанный для базового типа, может доверять **любому** наследнику. Нарушение LSP порождает `if (x is Square)` по всему коду — а это уже нарушение OCP. Признак проблемы: «является» в реальном мире (квадрат — это прямоугольник) не значит «ведёт себя как» в коде. Решение — общий интерфейс `IShape` без сеттеров или immutability.

> 💼 **На собеседовании:** Rectangle/Square + «как исправить» (отдельные классы с общим интерфейсом `IShape { double Area { get; } }`, неизменяемые фигуры). Пример из BCL: `ReadOnlyCollection<T>` реализует `IList<T>` и бросает на `Add` — спорный дизайн, который и привёл к появлению `IReadOnlyList<T>`.

## 5. I — Interface Segregation Principle

**Клиенты не должны зависеть от методов, которыми не пользуются.** Лучше несколько маленьких интерфейсов, чем один «толстый».

```csharp
// ❌ До
public interface IMultiFunctionDevice { void Print(Doc d); void Scan(Doc d); void Fax(Doc d); }
public class SimplePrinter : IMultiFunctionDevice
{
    public void Print(Doc d) { ... }
    public void Scan(Doc d) => throw new NotSupportedException();  // и LSP нарушен
    public void Fax(Doc d) => throw new NotSupportedException();
}

// ✅ После
public interface IPrinter { void Print(Doc d); }
public interface IScanner { void Scan(Doc d); }
public class SimplePrinter : IPrinter { ... }
public class OfficeCombo : IPrinter, IScanner { ... }
```

> **Почему так?** Толстый интерфейс связывает между собой несвязанных клиентов: поменяли сигнатуру `Fax` — перекомпилируются и переделываются все, кто только печатает. Маленькие интерфейсы проще мокать в тестах (модуль 14) и честнее описывают возможности. В BCL: `IEnumerable<T>` → `IReadOnlyCollection<T>` → `IReadOnlyList<T>` — пример «нарезки» по потребностям.

## 6. D — Dependency Inversion Principle

**Модули верхнего уровня не должны зависеть от модулей нижнего уровня; оба зависят от абстракций.** Бизнес-логика объявляет, *что* ей нужно (интерфейс), а инфраструктура это реализует.

```csharp
// ❌ До: бизнес-логика жёстко привязана к SMTP и статическому каталогу
public class OrderService
{
    public void Place(Order o)
    {
        var price = ProductCatalog.Prices[o.Sku];      // static — не подменить
        new SmtpClient("smtp.company.local").Send(...); // new — не подменить, в тестах шлёт письма!
    }
}

// ✅ После: зависимости — абстракции, приходят через конструктор
public sealed class OrderService(IProductCatalog catalog, INotificationSender notifier)
{
    public void Place(Order o) { var p = catalog.FindBySku(o.Sku); ... notifier.Send(o.Email, "..."); }
}
// Program.cs: builder.Services.AddScoped<INotificationSender, SmtpNotificationSender>();
```

**DIP vs DI vs IoC:** DIP — *принцип* (зависеть от абстракций). **Dependency Injection** — *техника* (передавать зависимости снаружи, обычно через конструктор). **IoC-контейнер** — *инструмент*, который автоматизирует DI (модуль 15). Можно соблюдать DIP и делать DI вручную, без контейнера.

> **Почему так?** Правило `new` и `static` внутри бизнес-логики — главная причина нетестируемого кода: нельзя подставить fake, тесты лезут в сеть и БД. Инверсия зависимостей делает ядро приложения независимым от деталей (БД, почта, внешние API) — их можно менять и подменять. Цена — больше интерфейсов; не нужно вводить интерфейс для каждого класса — только на «швах» с внешним миром и там, где нужна подмена.

> 💼 **На собеседовании:** не путай DIP и DI — это частая ловушка. Пример: сервис заказов зависит от `IPaymentGateway`, в тестах — fake, в проде — Stripe-адаптер.

## 7. DRY, KISS, YAGNI

- **DRY** (Don't Repeat Yourself) — каждое *знание* (правило, формула) должно быть в одном месте. Не путать с «одинаковыми строками кода»: две похожие проверки с разным смыслом объединять не нужно — когда одно правило поменяется, придётся «расклеивать».
- **KISS** (Keep It Simple, Stupid) — самое простое решение, которое работает. Три `if` понятнее, чем фабрика стратегий с рефлексией.
- **YAGNI** (You Aren't Gonna Need It) — не пиши код «на будущее». Абстракция без второго использования — лишняя сложность.

> **Почему так?** Эти принципы уравновешивают SOLID: SOLID тянет к гибкости (больше абстракций), KISS/YAGNI — к простоте. Хорошее правило: «правило трёх» — абстрагируй, когда видишь третий похожий случай, а не первый. Неправильная абстракция обходится дороже дублирования.

> 💼 **На собеседовании:** «Когда DRY вредит?» — когда объединяешь случайно похожий код с разными причинами изменения (нарушая SRP).

## 8. Паттерны проектирования для Junior

**Паттерн** (design pattern) — типовое решение типовой проблемы проектирования с общепринятым названием (книга «Банды четырёх», GoF, 1994). Название — главное: «здесь Strategy» экономит абзац объяснений на code review.

### Strategy (поведенческий)
Семейство взаимозаменяемых алгоритмов за общим интерфейсом; выбор — в рантайме. Пример: `IDeliveryMethod`, `IDiscountPolicy`, `IComparer<T>` в BCL. → **Задачи 2, 3**

### Factory Method / Simple Factory (порождающий)
Создание объекта вынесено в метод/класс, вызывающий код не знает конкретный тип.
```csharp
public static class NotifierFactory
{
    public static INotificationSender Create(string channel) => channel switch
    {
        "email" => new EmailSender(), "sms" => new SmsSender(),
        _ => throw new ArgumentException($"Unknown channel {channel}")
    };
}
```
Классический GoF Factory Method — виртуальный метод `CreateX()` в базовом классе, переопределяемый наследниками. В современном .NET роль фабрик часто выполняет DI-контейнер или `IHttpClientFactory`, `ILoggerFactory`.

### Decorator (структурный)
Обёртка, реализующая тот же интерфейс и добавляющая поведение до/после вызова внутреннего объекта. Пример: `CappedDiscountPolicy`, кэширующий репозиторий поверх обычного, `BufferedStream` поверх `FileStream`, middleware в ASP.NET Core по сути — цепочка декораторов. → **Задача 3**
```csharp
public sealed class CachedCatalog(IProductCatalog inner, IMemoryCache cache) : IProductCatalog
{
    public Product? FindBySku(string sku) => cache.GetOrCreate(sku, _ => inner.FindBySku(sku));
}
```

### Adapter (структурный)
Приводит чужой интерфейс к ожидаемому. Пример: обёртка над SDK платёжной системы, реализующая твой `IPaymentGateway`. → **Задача 5**

### Builder (порождающий)
Пошаговое создание сложного объекта с fluent API. В .NET: `StringBuilder`, `WebApplication.CreateBuilder`, `UriBuilder`, `DbContextOptionsBuilder`. → **Задача 4**

### Observer (поведенческий)
Объект уведомляет подписчиков об изменениях. В C# встроен как `event` (модуль 10), а также `IObservable<T>`/`IObserver<T>`.

### Repository и Unit of Work
**Repository** — коллекцие-подобный интерфейс к хранилищу (`Add`, `GetById`, `Find`), скрывающий детали доступа к данным. **Unit of Work** — группирует изменения и сохраняет их одной транзакцией. Оговорка: `DbContext` *уже* является UoW, а `DbSet<T>` — репозиторием; поэтому generic `Repository<T>` поверх EF Core часто лишний слой, который прячет полезные возможности (`Include`, проекции, `IQueryable`). Свой репозиторий оправдан, когда он выражает **доменные** операции (`GetActiveLoansForMember`) или нужно абстрагироваться от хранилища.

### Singleton (порождающий)
Ровно один экземпляр на приложение. Классическая реализация — `private` конструктор + `static Instance` (потокобезопасно — `Lazy<T>`):
```csharp
public sealed class AppClock
{
    private static readonly Lazy<AppClock> _instance = new(() => new AppClock());
    public static AppClock Instance => _instance.Value;
    private AppClock() { }
}
```
**Почему сегодня через DI:** классический Singleton — это глобальное состояние и скрытая зависимость (`AppClock.Instance` внутри метода не видно в конструкторе), его нельзя подменить в тестах, жизненным циклом не управляет никто. `services.AddSingleton<IClock, SystemClock>()` даёт тот же «один экземпляр», но зависимость явная и подменяемая.

> **Почему так?** Паттерны — это словарь и набор проверенных компромиссов, а не цель. Типичная ошибка Junior — применить паттерн «потому что можно». Сначала — проблема (switch растёт, класс не протестировать, чужой API неудобен), потом — паттерн, который её решает.

> 💼 **На собеседовании:** назови 3–4 паттерна с **примером из .NET или своего кода**: Strategy (`IComparer<T>`), Decorator (`Stream`, middleware), Builder (`StringBuilder`, `WebApplicationBuilder`), Observer (`event`), Singleton через DI. Вопрос «чем плох Singleton?» — глобальное состояние, скрытые зависимости, тестируемость, потокобезопасность.

## 9. Рефакторинг legacy-кода

**Рефакторинг** — изменение структуры кода **без изменения поведения**. Без тестов это не рефакторинг, а «переписывание с надеждой».

Безопасный цикл:
1. **Зафиксировать поведение** характеризационными тестами (characterization tests): тесты, описывающие то, что код делает *сейчас* (даже если это странно). В starter они уже есть.
2. **Маленькие шаги**: выделить метод → выделить класс → ввести интерфейс → внедрить через конструктор. После каждого шага — `dotnet test`.
3. **Коммит после каждого зелёного шага** — всегда можно откатиться.
4. Сначала **структура**, потом **поведение**: не исправляй баги и не добавляй фичи в том же коммите, что и рефакторинг.

Приёмы: Extract Method, Extract Class, Replace Conditional with Polymorphism, Introduce Parameter Object, Replace Magic Number with Constant, Inject Dependency (вместо `new`/`static`).

> **Почему так?** Legacy-код — «код без тестов» (Майкл Физерс). Характеризационные тесты дают страховочную сетку: если после шага они красные — ты изменил поведение, и это видно сразу, а не в продакшене. Маленькие шаги делают каждую ошибку дешёвой.

→ **Задача 1** и далее

## 10. Слои и чистая архитектура (обзорно)

Типичный Web API делят на слои:

```
Api (Presentation)      — endpoints/controllers, DTO, валидация входа, HTTP
Application             — сценарии (use cases): «оформить заказ», интерфейсы для инфраструктуры
Domain                  — сущности, бизнес-правила, value objects — без зависимостей от фреймворков
Infrastructure          — EF Core, email, внешние API — реализации интерфейсов Application/Domain
```

**Чистая (Clean/Onion/Hexagonal) архитектура** — зависимости направлены **внутрь**: Domain ни от кого не зависит, Infrastructure зависит от Application (реализует его интерфейсы) — это DIP на уровне проектов. В маленьких сервисах часто достаточно **vertical slices** (папка на фичу) или одного проекта с папками — не создавай 4 проекта для CRUD из трёх эндпоинтов.

> **Почему так?** Бизнес-правила живут дольше фреймворков и БД: Domain без зависимостей можно тестировать быстро и без инфраструктуры, а замена БД или почтового сервиса не трогает логику. Цена — больше церемоний и маппинга; архитектура должна соответствовать сложности задачи.

## 11. Git workflow в команде

```bash
git switch -c feature/123-order-discounts     # ветка под задачу (из main)
git add -p                                     # добавлять осознанно, по кусочкам
git commit -m "Extract delivery strategies from OrderProcessor"
git push -u origin feature/123-order-discounts
# → Pull Request (GitHub) / Merge Request (GitLab) → CI (сборка + тесты) → code review → merge
git switch main && git pull                    # обновиться
git rebase main   # или merge main — подтянуть свежие изменения в ветку (как принято в команде)
```

- Маленькие PR (до ~300–400 строк) ревьюят быстро и качественно.
- Сообщение коммита: *что* и *зачем* в повелительном наклонении («Add…», «Fix…»).
- **Code review** — не экзамен, а обмен знаниями: отвечай на замечания по существу, объясняй «почему», не принимай критику кода как критику себя. Ревьюя чужой код — спрашивай, а не приказывай.
- Не коммить секреты, `bin/`, `obj/` (для этого `.gitignore`).

> **Почему так?** Ветки и PR изолируют незаконченную работу, CI ловит сломанную сборку до merge, ревью распространяет знания по команде и ловит ошибки, которые автор не видит. На собеседовании спрашивают «как вы работали с git?» — нужен ответ про этот процесс, а не только «git add, commit, push».

> 💼 **На собеседовании:** «merge vs rebase?» — merge сохраняет историю как есть (merge-коммит), rebase переписывает коммиты ветки поверх новой базы (линейная история; не делай rebase опубликованных общих веток). «Что делаешь при конфликте?» — разбираюсь, какие изменения нужны обе, собираю, прогоняю тесты.

## 12. Как рассказывать о проекте: STAR

Вопрос «Расскажите о своём проекте / о сложной задаче» — почти гарантирован. Структура **STAR**:

- **S**ituation — контекст: что за проект, для кого, какой стек (1–2 предложения).
- **T**ask — твоя задача / проблема.
- **A**ction — что **ты** сделал и **почему** так (главная часть — 60% ответа).
- **R**esult — результат, по возможности измеримый, и что ты вынес.

> «(S) Делал учебный Web API "Библиотека" на ASP.NET Core и EF Core. (T) Эндпоинт списка книг отвечал 2 секунды на 500 книгах. (A) Включил логирование SQL и увидел 501 запрос — классический N+1: для каждой книги отдельно грузился автор. Заменил на проекцию в DTO с одним JOIN, добавил индекс по AuthorId и интеграционный тест, который считает SQL-команды. (R) Время ответа — 40 мс, а тест не даст проблеме вернуться. Вывод: всегда смотреть на SQL, который генерирует ORM».

Подготовь 3–4 такие истории: техническая сложность, ошибка и что ты из неё вынес, конфликт/разногласие, чему научился сам.

> **Почему так?** Интервьюер оценивает не проект, а **тебя**: как ты рассуждаешь, принимаешь решения и учишься. STAR не даёт утонуть в деталях и заставляет говорить о своих действиях и их причинах — это и есть «объяснять почему».

## 13. Типичный ход собеседования Junior .NET и план подготовки

**Ход (60–90 минут):**
1. Знакомство, «расскажите о себе» (2 минуты: кто ты, что изучал, что сделал, почему .NET).
2. Теория C#/.NET: типы, ООП, коллекции, LINQ, async, GC, исключения.
3. ASP.NET Core / EF Core / SQL.
4. Live coding или «что выведет код» (FizzBuzz-подобное, работа со строками/коллекциями, LINQ-запрос, SQL-запрос).
5. Проектирование: SOLID, паттерны, «как бы вы сделали…».
6. Поведенческие вопросы, твои вопросы к компании.

**План последних 2–3 недель:**

| Неделя | Что делать |
|---|---|
| 1 | Финальный проект доведён до README и зелёных тестов; `/interview 01-06` и разбор слабых тем |
| 2 | `/interview 07-12`, 10–15 задач live coding (строки, коллекции, LINQ, SQL); SQL-тренажёр |
| 3 | `/interview 13-17`, `/interview all`; 3–4 истории STAR; вопросы к работодателю; пробные собеседования |

**Поведенческие вопросы**, к которым стоит подготовиться: «Почему .NET?», «Расскажите о сложной задаче», «Как вы учитесь новому?», «Что делаете, если застряли?» (сам ищу ~30–60 минут → формулирую вопрос с тем, что уже попробовал → спрашиваю), «Как реагируете на критику кода?», «Где видите себя через год?».

**Вопросы к работодателю** (показывают зрелость): как устроен процесс разработки и code review, есть ли тесты и CI, кто будет наставником, какой стек и версии .NET, как измеряют успех на испытательном сроке.

> **Почему так?** Junior-собеседование проверяет три вещи: базу (знаешь ли фундамент), мышление (умеешь ли рассуждать и объяснять «почему») и обучаемость (как ты реагируешь на незнакомое). Честное «не знаю, но рассуждал бы так…» лучше уверенной выдумки.

## Типичные ошибки

| Ошибка | Последствие | Как правильно |
|---|---|---|
| Рефакторинг без тестов | незаметно меняется поведение | сначала характеризационные тесты |
| Рефакторинг + новая фича в одном коммите | невозможно понять, что сломало | разделяй коммиты |
| Интерфейс на каждый класс «по SOLID» | лишняя сложность, «прыжки» по коду | абстракции на швах и там, где нужна подмена |
| Паттерн ради паттерна | переусложнение | сначала проблема, потом паттерн |
| `static`/`new` зависимостей в бизнес-логике | нетестируемо, жёсткая связанность | внедрение через конструктор |
| Классический Singleton со статическим `Instance` | глобальное состояние, скрытые зависимости | `AddSingleton` в DI |
| DRY для случайно похожего кода | связка несвязанного, сложные правки | «правило трёх» |
| Путать DIP и DI | минус балл на интервью | принцип vs техника vs контейнер |
| Рассказ о проекте «мы сделали…» без своей роли | интервьюер не понимает твой вклад | STAR, фокус на «я сделал и почему» |

## Шпаргалка

| Принцип | Одной фразой | Признак нарушения |
|---|---|---|
| SRP | одна причина изменения | класс «и швец, и жнец», методы на 100+ строк |
| OCP | расширяй, не изменяя | растущий `switch` по типу |
| LSP | наследник заменяет базу | `NotSupportedException` в override, `if (x is Derived)` |
| ISP | маленькие интерфейсы | пустые/бросающие реализации методов |
| DIP | зависеть от абстракций | `new`/`static` инфраструктуры в бизнес-логике |

| Паттерн | Суть | В .NET |
|---|---|---|
| Strategy | взаимозаменяемые алгоритмы | `IComparer<T>`, политики |
| Decorator | обёртка с тем же интерфейсом | `BufferedStream`, middleware |
| Adapter | чужой интерфейс → наш | обёртки над SDK |
| Builder | пошаговая сборка | `StringBuilder`, `WebApplicationBuilder` |
| Factory | создание без знания типа | `IHttpClientFactory`, DI |
| Observer | подписка на события | `event`, `IObservable<T>` |
| Repository/UoW | доступ к данным / транзакция изменений | `DbSet<T>` / `DbContext` |
| Singleton | один экземпляр | `AddSingleton` |

## Вопросы на собеседовании

<details><summary><b>Расскажите про SOLID.</b></summary>

SRP — у класса одна причина для изменения. OCP — расширяем поведение новым кодом, не меняя рабочий (полиморфизм вместо switch). LSP — наследник должен подставляться вместо базы без нарушения ожиданий (Rectangle/Square). ISP — несколько узких интерфейсов лучше одного толстого. DIP — бизнес-логика зависит от абстракций, а не от инфраструктуры; реализации внедряются через конструктор. Цель всех пяти — снизить связанность и упростить изменения и тестирование.
</details>

<details><summary><b>Чем DIP отличается от DI и IoC-контейнера?</b></summary>

DIP — принцип: модули зависят от абстракций. DI — техника: зависимости передаются снаружи (конструктор, свойство, параметр метода). IoC-контейнер — инструмент, который по регистрациям сам создаёт объекты и внедряет зависимости (`IServiceCollection` в .NET). DI можно делать вручную, без контейнера; а DI без абстракций не даёт инверсии зависимостей.
</details>

<details><summary><b>Приведите пример нарушения LSP и как его исправить.</b></summary>

`Square : Rectangle` с переопределёнными сеттерами: код, который ставит ширину 5 и высоту 10 и ожидает площадь 50, получит 100. Или наследник, бросающий `NotSupportedException` в методе базового класса. Исправление — не наследовать по принципу «является в жизни», а выделить общий интерфейс по поведению (`IShape.Area`) и сделать фигуры неизменяемыми.
</details>

<details><summary><b>Какие паттерны вы знаете и применяли?</b></summary>

Strategy — взаимозаменяемые алгоритмы за интерфейсом (расчёт доставки, `IComparer<T>`). Decorator — обёртка с тем же интерфейсом (кэширующий репозиторий, middleware). Adapter — приведение чужого API к своему интерфейсу. Builder — пошаговая сборка (`StringBuilder`, `WebApplication.CreateBuilder`). Observer — `event`. Repository/Unit of Work — `DbSet`/`DbContext`. Singleton — через `AddSingleton`, а не статическое поле. Важно привести пример из своего кода.
</details>

<details><summary><b>Чем плох паттерн Singleton? Как его делают в современном .NET?</b></summary>

Классический Singleton (статическое свойство Instance) — глобальное изменяемое состояние, скрытая зависимость, его нельзя подменить в тестах, нужно отдельно думать о потокобезопасности инициализации (`Lazy<T>`). В .NET используют DI: `services.AddSingleton<IService, Impl>()` — один экземпляр, но зависимость явная, внедряется через конструктор и легко подменяется. Сам объект всё равно должен быть потокобезопасным.
</details>

<details><summary><b>Strategy vs Decorator — в чём разница?</b></summary>

Strategy подменяет **алгоритм целиком**: клиент выбирает одну из реализаций интерфейса. Decorator **оборачивает** существующую реализацию тем же интерфейсом и добавляет поведение до/после неё; декораторы можно вкладывать. Например, `TierDiscountPolicy` — стратегия скидки, `CappedDiscountPolicy(inner)` — декоратор, ограничивающий результат любой стратегии.
</details>

<details><summary><b>Нужен ли свой Repository поверх EF Core?</b></summary>

`DbContext` уже реализует Unit of Work, а `DbSet<T>` — репозиторий. Generic `IRepository<T>` с `GetAll/Add/Update` поверх EF часто только прячет полезные возможности (Include, проекции, IQueryable) и добавляет код. Свой репозиторий оправдан, когда он выражает доменные операции (`GetOverdueLoans`), изолирует домен от инфраструктуры в чистой архитектуре или когда хранилищ несколько. Хороший ответ — «зависит», с аргументами.
</details>

<details><summary><b>Что такое DRY, KISS, YAGNI? Когда DRY вредит?</b></summary>

DRY — каждое знание в одном месте; KISS — самое простое работающее решение; YAGNI — не писать код на будущее. DRY вредит, когда объединяют случайно похожий код с разными причинами изменения: при изменении одного правила общий метод обрастает флагами и ломает другое использование. Помогает «правило трёх».
</details>

<details><summary><b>Как безопасно отрефакторить legacy-код без тестов?</b></summary>

Сначала написать характеризационные тесты, фиксирующие текущее поведение через публичный интерфейс. Затем маленькими шагами (extract method/class, внедрение зависимостей вместо `new`/`static`, замена условий полиморфизмом), прогоняя тесты после каждого шага и коммитя зелёные состояния. Не смешивать рефакторинг с изменением поведения в одном коммите.
</details>

<details><summary><b>Как устроен ваш git workflow? Merge или rebase?</b></summary>

Ветка под задачу от main → небольшие осмысленные коммиты → push → Pull Request → CI (сборка и тесты) → code review → merge. Merge сохраняет историю и создаёт merge-коммит; rebase переносит коммиты ветки поверх новой базы и даёт линейную историю, но переписывает коммиты — нельзя делать для общих опубликованных веток. Выбор — соглашение команды.
</details>

<details><summary><b>Расскажите о своём проекте.</b></summary>

По STAR: ситуация и стек (1–2 предложения), задача, **свои** действия с объяснением решений (архитектура, почему EF Core и какие проблемы решал, как тестировал), результат и выводы. Подготовь рассказ на 2–3 минуты и будь готов к углублению в любую деталь: «почему Scoped?», «как обрабатываете ошибки?», «что бы переделали?».
</details>
