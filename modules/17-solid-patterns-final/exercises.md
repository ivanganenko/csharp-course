# Модуль 17 — задачи

> Код пишется в `starter/Module17.Tasks/`. Тесты: `cd modules/17-solid-patterns-final/starter && dotnet test`.

**Рефакторинг-ката «Обработка заказов».** В `OrderProcessor.cs` — работающий, но плохо спроектированный legacy-код: один метод на ~130 строк, `switch` по типу доставки, статический каталог, `new SmtpEmailClient()` внутри, `Console.WriteLine` и `DateTime.Now`. Его поведение зафиксировано в `OrderProcessorCharacterizationTests` — **эти тесты зелёные с самого начала и должны оставаться зелёными после каждого шага**. Менять их нельзя.

Для целевого дизайна уже даны абстракции (`IDeliveryMethod`, `IDiscountPolicy`, `IProductCatalog`, `IOrderRepository`, `INotificationSender`) и каркасы классов с `NotImplementedException` — их проверяют отдельные тесты.

**Правила рефакторинга:**
1. Маленькие шаги. После каждого — `dotnet test`. Зелёное — `git commit`.
2. Не менять поведение: если характеризационный тест покраснел — откатись к последнему коммиту, а не «чини тест».
3. Публичный фасад `OrderProcessor` (конструктор без параметров, `Process`, `GetOrder`) сохраняется.
4. Можно (и нужно) добавлять свои классы и файлы.

## 🏁 Финальный проект

Сделай с нуля небольшой, но «настоящий» Web API, который не стыдно показать на собеседовании и положить на GitHub. Это твоя главная история для вопроса «расскажите о проекте».

### Тема (выбери одну)
- **«Личный бюджет»** — счета, категории, операции (доход/расход), отчёт по категориям за месяц, бюджет-лимиты.
- **«Библиотека»** — книги, авторы, читатели, выдачи/возвраты с правилами (как в модуле 16), поиск и отчёты.
- Своя идея сопоставимого размера (согласуй с преподавателем через `/lesson`).

### Обязательные требования
1. **ASP.NET Core Web API** (.NET 10), Minimal APIs или Controllers; правильные HTTP-методы и status codes; DTO на вход и выход.
2. **EF Core** + SQLite (или PostgreSQL в Docker); **миграции** (`dotnet ef migrations add Initial`), а не `EnsureCreated`; минимум 3 сущности и связи 1-N (N-N — плюс).
3. **Валидация** входных данных → 400 ValidationProblem; **глобальная обработка ошибок** → ProblemDetails.
4. **DI**: сервисы бизнес-логики за интерфейсами, осознанные lifetimes.
5. **Минимум 2 бизнес-правила** с инвариантами (например, «нельзя уйти в минус по счёту», «не больше 3 книг на руках»).
6. **Пагинация и фильтрация** хотя бы одного списка на `IQueryable`.
7. **Тесты:** unit-тесты бизнес-логики (xUnit, NSubstitute где нужно) + интеграционные тесты API через `WebApplicationFactory` (SQLite in-memory). Минимум 15 тестов.
8. **README.md** проекта: что это, как запустить (команды), примеры запросов, архитектурные решения и **почему** они такие.
9. **Git:** осмысленная история коммитов, работа через ветки (хотя бы для 2–3 фич — PR в свой же репозиторий), `.gitignore`.

### Будет плюсом
OpenAPI-документ (`Microsoft.AspNetCore.OpenApi`); `IOptions` для настроек; логирование со structured logging; Docker-файл; CI в GitHub Actions (`dotnet test` на каждый push); аутентификация (JWT) — только если остаётся время.

### Этапы
| # | Этап | Результат |
|---|---|---|
| 1 | Проектирование (1–2 ч) | список сущностей и эндпоинтов, бизнес-правила — в README |
| 2 | Каркас (2 ч) | `dotnet new webapi`, `dotnet new xunit`, `.slnx`, git, первый эндпоинт + интеграционный тест |
| 3 | Данные (3–4 ч) | DbContext, конфигурация, миграция, CRUD |
| 4 | Бизнес-логика (4–6 ч) | сервисы, правила, unit-тесты |
| 5 | Качество (2–3 ч) | валидация, ProblemDetails, пагинация, логи |
| 6 | Оформление (1–2 ч) | README, чистка кода, финальное ревью `/code-review` |

### Критерии оценки (на `/check` финального проекта)
- Работает: `git clone` → команды из README → API запускается, `dotnet test` зелёный.
- Код: SOLID без фанатизма, тонкие эндпоинты, нет N+1, нет `.Result`, нет секретов в репозитории.
- Тесты проверяют поведение (а не реализацию), включая граничные случаи.
- Ты можешь за 3 минуты рассказать о проекте по STAR и ответить «почему» на любой вопрос о своих решениях.
