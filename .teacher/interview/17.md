> Используй как финальное mock interview. Часть A — SOLID и паттерны, часть B — 10 «лучших» сквозных вопросов по всему курсу (`/interview all` бери отсюда и из `.teacher/interview/NN.md`), часть C — поведенческие.

## Часть A. SOLID и паттерны

### 1. Расскажите про принципы SOLID с примерами.
**Уровень:** junior
**Хороший ответ:** SRP — одна причина изменения: `OrderProcessor`, который и считает скидки, и шлёт письма, разделяем на политику скидок, отправителя и т.д. OCP — расширение без изменения: `switch` по типу доставки заменяем стратегиями, новый способ — новый класс. LSP — наследник подставляется вместо базы: `Square : Rectangle` нарушает. ISP — узкие интерфейсы вместо одного толстого (`IPrinter`, `IScanner`). DIP — зависимость от абстракций: сервис зависит от `INotificationSender`, реализация внедряется через конструктор. Общая цель — низкая связанность и простота изменений и тестирования.
**Глубже (для junior+):** SOLID — эвристики, а не законы; перебор абстракций нарушает KISS/YAGNI. SRP по Мартину — про «акторов» (группы заказчиков изменений).
**Follow-up:**
- «Какой принцип вы чаще всего видите нарушенным?» — SRP/DIP: god-классы и `new` инфраструктуры в логике.
- «Нужно ли на каждый класс делать интерфейс?» — нет, на швах и точках расширения.
**Красные флаги:** заученные определения без примеров; путает буквы; «SOLID — это когда всё через интерфейсы».

### 2. Что такое Dependency Inversion? Чем отличается от Dependency Injection?
**Уровень:** junior
**Хороший ответ:** DIP — принцип: модули верхнего уровня (бизнес-логика) и нижнего (БД, почта) зависят от абстракций; абстракцию «владеет» верхний уровень. DI — техника: передаём зависимости снаружи, чаще всего через конструктор. IoC-контейнер — инструмент, автоматизирующий DI. Можно делать DI вручную, а можно использовать контейнер и всё равно нарушать DIP, если зависеть от конкретных классов инфраструктуры.
**Follow-up:**
- «Какие виды внедрения бывают?» — конструктор (предпочтительно — зависимости обязательны и явны), свойство, параметр метода.
- «Что такое Service Locator и почему это антипаттерн?» — класс сам достаёт зависимости из контейнера → они скрыты, тестировать сложнее.
**Красные флаги:** «DIP и DI — одно и то же».

### 3. Найдите проблемы в коде.
**Уровень:** junior
```csharp
public class ReportService
{
    public string Build(int userId)
    {
        var db = new SqlConnection("Server=prod;Password=123");
        var orders = db.Query<Order>($"SELECT * FROM Orders WHERE UserId = {userId}");
        var total = 0.0;
        foreach (var o in orders) total += o.Price * 1.2;
        File.WriteAllText("C:\\reports\\r.txt", total.ToString());
        return total.ToString();
    }
}
```
**Хороший ответ:** DIP/тестируемость — `new SqlConnection` и `File` внутри; секрет в коде; SQL injection через интерполяцию (нужны параметры); соединение не диспозится (`using`); `double` для денег (нужен `decimal`); магическое число 1.2 (НДС — константа/настройка); SRP — и запрос, и расчёт, и запись в файл; `ToString()` без культуры; захардкоженный путь Windows.
**Follow-up:**
- «С чего начнёте рефакторинг?» — с тестов на текущее поведение, затем выделить `IOrderRepository`, калькулятор, хранилище отчётов.
**Красные флаги:** видит только 1–2 проблемы, не замечает SQL injection.

### 4. Какие паттерны проектирования вы знаете? Где применяли?
**Уровень:** junior
**Хороший ответ:** Strategy — взаимозаменяемые алгоритмы (способы доставки, `IComparer<T>`). Decorator — обёртка с тем же интерфейсом (кэширующий каталог, `BufferedStream`, middleware-цепочка). Adapter — чужой API к своему интерфейсу (обёртка над SDK почты). Builder — пошаговая сборка (`StringBuilder`, `WebApplicationBuilder`, свой `OrderRequestBuilder`). Observer — `event`. Factory — создание без знания конкретного типа (`IHttpClientFactory`). Repository/Unit of Work — `DbSet`/`DbContext`. Singleton — через DI.
**Follow-up:**
- «Strategy vs Decorator?» — замена алгоритма vs обёртка вокруг существующего.
- «Adapter vs Facade?» — Adapter приводит один интерфейс к другому; Facade упрощает доступ к сложной подсистеме.
**Красные флаги:** перечисляет названия без единого примера.

### 5. Чем плох Singleton? Как сделать «один экземпляр» правильно?
**Уровень:** junior
**Хороший ответ:** Классический Singleton со статическим `Instance` — глобальное состояние, скрытая зависимость (её не видно в конструкторе), невозможность подменить в тестах, вопросы потокобезопасной инициализации. В .NET регистрируют `services.AddSingleton<IClock, SystemClock>()`: экземпляр один, но зависимость явная и подменяемая. Сам singleton-сервис должен быть потокобезопасным и не зависеть от scoped-сервисов.
**Follow-up:**
- «Как сделать потокобезопасный ленивый Singleton вручную?» — `static readonly Lazy<T>` или статический readonly-инициализатор.
**Красные флаги:** «Singleton — для всего, что нужно в одном экземпляре, через static».

### 6. Нужен ли Repository поверх EF Core?
**Уровень:** junior+
**Хороший ответ:** `DbContext` — уже Unit of Work, `DbSet<T>` — репозиторий. Generic-репозиторий с `GetAll/Add/Update` поверх EF часто прячет полезное (Include, проекции, IQueryable) и порождает либо N+1, либо утечку `IQueryable` наружу. Оправдан доменный репозиторий с осмысленными методами (`GetActiveLoans(memberId)`), изоляция домена в чистой архитектуре, несколько хранилищ. Ответ «зависит от проекта» с аргументами — правильный.
**Красные флаги:** «всегда нужен», «никогда не нужен» без аргументов.

### 7. Live coding: замените switch на Strategy
**Уровень:** junior+
**Задача:**
```csharp
decimal Fee(string method, decimal amount) => method switch
{
    "card" => amount * 0.02m,
    "sbp" => 0m,
    "crypto" => amount * 0.01m + 50m,
    _ => throw new ArgumentException(method)
};
```
**Хороший ответ:**
```csharp
public interface IPaymentFee { string Method { get; } decimal Calculate(decimal amount); }
public sealed class CardFee : IPaymentFee { public string Method => "card"; public decimal Calculate(decimal a) => a * 0.02m; }
public sealed class SbpFee : IPaymentFee { public string Method => "sbp"; public decimal Calculate(decimal a) => 0m; }
public sealed class CryptoFee : IPaymentFee { public string Method => "crypto"; public decimal Calculate(decimal a) => a * 0.01m + 50m; }

public sealed class FeeCalculator(IEnumerable<IPaymentFee> fees)
{
    private readonly Dictionary<string, IPaymentFee> _fees = fees.ToDictionary(f => f.Method, StringComparer.OrdinalIgnoreCase);
    public decimal Fee(string method, decimal amount) =>
        _fees.TryGetValue(method, out var fee) ? fee.Calculate(amount) : throw new ArgumentException($"Unknown method {method}");
}
// DI: services.AddSingleton<IPaymentFee, CardFee>(); ... services.AddSingleton<FeeCalculator>();
```
Хорошо, если кандидат сам говорит: «для трёх стабильных вариантов switch тоже нормален; Strategy окупается, когда способы часто добавляются или у каждого своя сложная логика/зависимости».
**Красные флаги:** создаёт стратегии через `new` в switch (переносит проблему); не знает, как их зарегистрировать в DI.

### 8. Как безопасно рефакторить код без тестов?
**Уровень:** junior+
**Хороший ответ:** Сначала характеризационные тесты через публичный API, фиксирующие текущее поведение (включая странное). Потом маленькие шаги — extract method/class, внедрение зависимостей вместо `new`/`static`, замена условий полиморфизмом — с прогоном тестов и коммитом после каждого шага. Не смешивать рефакторинг и изменение поведения.
**Красные флаги:** «перепишу с нуля, так быстрее».

## Часть B. 10 сквозных вопросов по курсу (финальный mock interview)

### B1. Value type vs reference type; что такое boxing? (модули 02, 06, 12)
**Уровень:** junior
**Хороший ответ:** Value type (struct, int, enum) хранит значение; присваивание копирует данные. Reference type (class, string, массивы) хранит ссылку на объект в managed heap; присваивание копирует ссылку. Value type — не обязательно стек: поле внутри класса живёт в куче вместе с объектом. Boxing — упаковка value type в объект в куче при приведении к `object`/интерфейсу; unboxing — обратно с проверкой типа. Boxing — аллокация и нагрузка на GC, поэтому generics лучше `ArrayList`.
**Follow-up:** «Что выведет: `object a = 1; object b = 1; Console.WriteLine(a == b);`?» — `False`: сравнение ссылок двух разных «коробок».
**Красные флаги:** «value types всегда на стеке».

### B2. `virtual`/`override` vs `new` — что выведет код? (модуль 05)
**Уровень:** junior
```csharp
class A { public virtual string M() => "A"; public string N() => "A"; }
class B : A { public override string M() => "B"; public new string N() => "B"; }
A x = new B();
Console.WriteLine(x.M() + x.N());
```
**Хороший ответ:** `BA`. `override` — полиморфизм, вызывается метод реального типа объекта (B). `new` скрывает метод: вызов определяется статическим типом переменной (A).
**Красные флаги:** `BB` или `AA` без объяснения.

### B3. Equals и GetHashCode — зачем переопределять вместе? (модули 06, 09)
**Уровень:** junior
**Хороший ответ:** `Dictionary`/`HashSet` сначала по `GetHashCode` выбирают бакет, затем сравнивают `Equals`. Контракт: равные объекты обязаны иметь равные хэш-коды. Переопределил только `Equals` — объект не найдётся в словаре. Хэш должен зависеть от тех же неизменяемых полей. `record` генерирует оба автоматически.
**Красные флаги:** «GetHashCode — уникальный идентификатор объекта».

### B4. `throw;` vs `throw ex;`, `finally`, `using` (модуль 07)
**Уровень:** junior
**Хороший ответ:** `throw;` пробрасывает исключение, сохраняя исходный stack trace; `throw ex;` сбрасывает его на текущую строку — теряется место ошибки. `finally` выполняется всегда (кроме краха процесса) — для освобождения ресурсов. `using` — синтаксический сахар для try/finally с `Dispose()`.
**Красные флаги:** «разницы нет».

### B5. Как устроен Dictionary и какова сложность операций? (модуль 09)
**Уровень:** junior
**Хороший ответ:** Хэш-таблица: массив бакетов, индекс = хэш-код по модулю размера; коллизии — цепочки записей. Поиск/вставка/удаление — O(1) в среднем, O(n) в худшем (плохой хэш). При заполнении — увеличение и перехэширование (амортизированно O(1)). Ключ должен быть неизменяемым с корректными `Equals`/`GetHashCode`.
**Красные флаги:** «O(log n), как дерево».

### B6. Deferred execution в LINQ; IEnumerable vs IQueryable (модули 11, 16)
**Уровень:** junior
**Хороший ответ:** Большинство LINQ-операторов ленивые: запрос выполняется при перечислении (`foreach`, `ToList`, `Count`), и каждое перечисление выполняет его заново. `IQueryable` строит expression tree, которое провайдер (EF Core) переводит в SQL — фильтрация в БД; `IEnumerable` — в памяти.
**Follow-up:** «Что выведет?» `var list = new List<int>{1,2}; var q = list.Where(x => x > 1); list.Add(3); Console.WriteLine(q.Count());` → `2`.
**Красные флаги:** не знает, когда выполняется запрос.

### B7. async/await: что происходит и почему `.Result` опасен? (модуль 13)
**Уровень:** junior
**Хороший ответ:** `async` метод компилируется в state machine; `await` незавершённой задачи возвращает управление вызывающему и освобождает поток, продолжение выполнится по завершении. Для IO-операций поток не занят ожиданием — сервер обслуживает больше запросов. `.Result`/`.Wait()` блокируют поток; при наличии SynchronizationContext (UI, старый ASP.NET) — deadlock; в ASP.NET Core — голодание ThreadPool. `async void` — только для обработчиков событий: исключения нельзя поймать.
**Красные флаги:** «async создаёт новый поток».

### B8. Как работает Garbage Collector? (модуль 12)
**Уровень:** junior
**Хороший ответ:** Managed heap, сборка по поколениям 0/1/2: большинство объектов умирают молодыми, поэтому gen0 собирается часто и быстро; выжившие продвигаются. Фазы — mark (от корней: стек, статические поля, регистры) и compact. Крупные объекты (≥ 85 000 байт) — в LOH, собираются с gen2, не компактируются по умолчанию. GC освобождает только управляемую память; неуправляемые ресурсы — через `IDisposable`. `GC.Collect()` вручную вызывать не нужно.
**Красные флаги:** «GC подсчитывает ссылки»; «Dispose освобождает память объекта».

### B9. DI lifetimes и middleware в ASP.NET Core (модуль 15)
**Уровень:** junior
**Хороший ответ:** Singleton — один на приложение, Scoped — на HTTP-запрос (DbContext), Transient — каждый раз новый; нельзя внедрять Scoped в Singleton (captive dependency). Middleware — цепочка компонентов, обрабатывающих запрос до/после следующего; порядок важен (обработчик исключений первым, аутентификация до авторизации).
**Красные флаги:** путает Scoped с «на пользователя».

### B10. Проблема N+1 и AsNoTracking (модуль 16)
**Уровень:** junior
**Хороший ответ:** N+1 — запрос за списком + запрос на каждый элемент; решается Include, проекцией, загрузкой одним запросом; обнаруживается по SQL-логам. AsNoTracking — для read-only запросов: без change tracker, быстрее; изменения таких сущностей не сохраняются.
**Красные флаги:** не может объяснить, как найти N+1.

### C3. Что вы делаете, когда застряли?
**Уровень:** junior
**Хороший ответ:** Сначала разбираюсь сам ограниченное время (30–60 минут): читаю ошибку и stack trace, дебажу, ищу в документации, воспроизвожу на минимальном примере. Затем задаю вопрос коллеге — с контекстом: что делаю, что ожидаю, что уже попробовал. Не сижу молча днями и не спрашиваю, не попробовав.
**Красные флаги:** «сразу спрашиваю» или «никогда не спрашиваю».

### C4. Как вы относитесь к code review и критике вашего кода?

**Красные флаги:** обида, «мой код и так работает».
