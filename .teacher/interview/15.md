# Интервью: модуль 15 — ASP.NET Core Web API

### 1. Какие lifetimes есть у сервисов в DI-контейнере ASP.NET Core?
**Уровень:** junior
**Хороший ответ:** Три: Singleton — один экземпляр на всё приложение; Scoped — один на scope, в веб-приложении scope создаётся на каждый HTTP-запрос; Transient — новый экземпляр при каждом запросе к контейнеру. Singleton подходит для stateless-сервисов и кэшей и должен быть потокобезопасным. Scoped — для `DbContext` и всего, что составляет «единицу работы» запроса. Transient — для лёгких сервисов без состояния.
**Глубже (для junior+):** Контейнер диспозит созданные им `IDisposable`-сервисы в конце их scope (Singleton — при остановке приложения). Transient `IDisposable`, резолвнутый из корневого провайдера, удерживается до конца жизни приложения — утечка. Keyed services (.NET 8) — регистрация нескольких реализаций под ключами.
**Follow-up:**
- «Что будет, если Singleton зависит от Scoped?» — captive dependency; в Development — исключение при валидации scopes; решение — `IServiceScopeFactory`.
- «Почему `DbContext` Scoped?» — не потокобезопасен, отслеживает изменения в рамках одной операции; Singleton дал бы гонки и бесконечный рост change tracker.
- «Как получить Scoped-сервис в фоновом `BackgroundService`?» — создать scope через `IServiceScopeFactory.CreateScope()`.
**Красные флаги:** «Scoped — один на пользователя/сессию»; «Transient — самый быстрый, поэтому всё Transient»; не знает, что Singleton должен быть потокобезопасным.

### 2. Что такое middleware? Как устроен pipeline?
**Уровень:** junior
**Хороший ответ:** Middleware — компонент, через который проходит каждый запрос; он получает `HttpContext` и делегат `next`, может выполнить код до и после следующего middleware или прервать цепочку. Вместе они образуют pipeline: запрос проходит сверху вниз в порядке регистрации, ответ — в обратном. `Use` — обычный middleware, `Run` — терминальный, `Map` — ветвление по пути. Порядок важен: обработчик исключений — в начале, `UseAuthentication` до `UseAuthorization`.
**Глубже (для junior+):** Middleware-класс создаётся один раз, поэтому scoped-зависимости передают в `InvokeAsync`; есть `IMiddleware` (factory-based), который резолвится из DI на каждый запрос. Short-circuit — middleware не вызывает `next` (кэш, статика, 401).
**Follow-up:**
- «Чем middleware отличается от фильтров?» — фильтры работают внутри MVC/endpoint и знают про action и модель; middleware — для всех запросов, ничего не знает о контроллерах.
- «Можно ли изменить заголовок после `next`?» — только если ответ ещё не начался; надёжно — `Response.OnStarting`.
**Красные флаги:** не может объяснить «до/после next»; считает, что порядок регистрации не важен.

### 3. Что выведет этот код при запросе `GET /`?
**Уровень:** junior
```csharp
app.Use(async (ctx, next) => { Console.Write("1"); await next(ctx); Console.Write("2"); });
app.Map("/admin", admin => admin.Run(ctx => { Console.Write("A"); return Task.CompletedTask; }));
app.Use(async (ctx, next) => { Console.Write("3"); await next(ctx); Console.Write("4"); });
app.Run(ctx => { Console.Write("5"); return Task.CompletedTask; });
```
**Хороший ответ:** `13542`. Ветка `/admin` не срабатывает для `/`, запрос проходит первый middleware, третий, терминальный `Run`, затем возвращается через «после» в обратном порядке. Для `/admin` было бы `1A2`.
**Follow-up:**
- «Что если во втором `Use` забыть вызвать `next`?» — `Run` не выполнится, ответ — пустой 200 (short-circuit).
**Красные флаги:** `12345` — не понимает обратный путь ответа.

### 4. Чем PUT отличается от POST и PATCH? Что такое идемпотентность?
**Уровень:** junior
**Хороший ответ:** POST создаёт новый ресурс в коллекции (сервер выдаёт id), возвращает 201 + Location; не идемпотентен — два одинаковых POST создадут два ресурса. PUT полностью заменяет ресурс по известному адресу, идемпотентен — повтор даёт то же состояние. PATCH — частичное изменение. Идемпотентность важна для повторов (retry) при сетевых сбоях.
**Глубже (для junior+):** Для безопасного retry POST используют idempotency key в заголовке. GET/HEAD — safe (не меняют состояние).
**Follow-up:**
- «Какой код вернуть после DELETE?» — 204 (или 200 с телом); повторный DELETE → 404, но состояние то же — идемпотентность про состояние, не про код.
- «401 vs 403?» — не аутентифицирован vs нет прав.
**Красные флаги:** «PUT для создания, POST для обновления — без разницы»; всё возвращает 200.

### 5. Как в ASP.NET Core организована конфигурация? Что такое Options pattern?
**Уровень:** junior
**Хороший ответ:** `IConfiguration` собирается из провайдеров: appsettings.json, appsettings.{Environment}.json, user secrets, переменные окружения, аргументы командной строки — более поздние перекрывают ранние. Options pattern связывает секцию с классом: `services.Configure<MyOptions>(config.GetSection("My"))`, затем внедряем `IOptions<MyOptions>`. Это типобезопасно, валидируемо и легко подменяется в тестах.
**Глубже (для junior+):** `IOptionsSnapshot<T>` — Scoped, перечитывает на каждый запрос; `IOptionsMonitor<T>` — Singleton, актуальное значение + `OnChange`. `ValidateDataAnnotations().ValidateOnStart()` — упасть при старте, а не на первом запросе.
**Follow-up:**
- «Как задать вложенный ключ через переменную окружения?» — `Section__Key` (двойное подчёркивание).
- «Где хранить секреты?» — не в git: user secrets для разработки, env vars / Key Vault в проде.
**Красные флаги:** читает настройки через `File.ReadAllText("appsettings.json")`; пароли в репозитории — «нормально».

### 6. Как ты обрабатываешь ошибки в Web API?
**Уровень:** junior
**Хороший ответ:** Централизованно: `AddProblemDetails()`, `AddExceptionHandler<T>()` и `app.UseExceptionHandler()` в начале pipeline (или свой middleware с try/catch вокруг `next`). Обработчик сопоставляет типы исключений со статусами (NotFound → 404, конфликт → 409, остальное → 500), отдаёт ProblemDetails, логирует 5xx с исключением. Детали исключения наружу не отдаются — только `traceId` для поиска в логах. Ожидаемые ситуации (не найдено, невалидно) часто возвращают явно, без исключений.
**Глубже (для junior+):** Исключения дороги (stack trace) и скрывают поток управления — для частых «ожидаемых» ошибок лучше Result-тип. Developer exception page — только в Development.
**Follow-up:**
- «Почему не try/catch в каждом эндпоинте?» — дублирование, легко забыть, разный формат.
- «Что такое ProblemDetails?» — стандарт RFC 9457: type, title, status, detail, instance + extensions.
**Красные флаги:** возвращает `ex.ToString()` клиенту; глотает исключения `catch {}`; 200 с `{error: ...}`.

### 7. Что такое model binding? Откуда берутся параметры обработчика?
**Уровень:** junior
**Хороший ответ:** Фреймворк сам заполняет параметры из запроса: route values (`{id}`), query string, тело JSON, заголовки, форма; сервисы — из DI; специальные типы — `HttpContext`, `CancellationToken`. В Minimal APIs источник выводится по соглашениям, явно — атрибутами `[FromRoute]`, `[FromQuery]`, `[FromBody]`, `[FromHeader]`, `[FromServices]`. Если привязка не удалась (невалидный JSON, `?page=abc`) — 400.
**Follow-up:**
- «Что такое over-posting и как защититься?» — клиент присылает лишние поля (`IsAdmin`), если привязываем прямо в сущность; защита — входные DTO.
- «Зачем `CancellationToken` в параметрах?» — отмена работы, если клиент отключился.
**Красные флаги:** парсит `Request.Query` вручную везде; не знает, что тело читается в сложный тип.

### 8. Controllers vs Minimal APIs — что выберешь?
**Уровень:** junior
**Хороший ответ:** Оба поверх одного pipeline и routing. Controllers — классы с атрибутами и соглашениями (`[ApiController]` даёт автоматический 400 при невалидной модели), MVC filters, их больше в существующих проектах. Minimal APIs — меньше кода и накладных расходов, `TypedResults`, route groups, endpoint filters. Выбор зависит от команды и проекта; я умею оба.
**Follow-up:**
- «`IActionResult` vs `ActionResult<T>`?» — второй типизирован, можно вернуть `T` напрямую, лучше для OpenAPI.
**Красные флаги:** «Minimal API только для прототипов» или наоборот «контроллеры устарели» без аргументов.

### 9. Как протестировать Web API?
**Уровень:** junior / junior+
**Хороший ответ:** Логику (валидаторы, сервисы) — unit-тестами без HTTP. Интеграционно — `WebApplicationFactory<Program>`: приложение поднимается в памяти (TestServer), `HttpClient` проходит весь pipeline — routing, binding, middleware, DI, сериализацию. Зависимости подменяются через `WithWebHostBuilder(b => b.ConfigureTestServices(...))`. Для top-level Program нужен `public partial class Program {}` (в .NET 10 уже не обязателен).
**Глубже (для junior+):** Реальная БД в тестах — Testcontainers (Docker); изоляция данных между тестами — новая фабрика/транзакция/очистка; аутентификация — тестовый `AuthenticationHandler`.
**Follow-up:**
- «Почему не только unit-тесты?» — не ловят ошибки склейки: порядок middleware, регистрации DI, маршруты, JSON-формат.
**Красные флаги:** «тестирую через Postman вручную» как единственный способ.

### 10. Зачем DTO, если можно вернуть сущность?
**Уровень:** junior
**Хороший ответ:** DTO — контракт API, отделённый от внутренней модели: можно рефакторить сущность, не ломая клиентов; не утекают лишние поля (хэш пароля, внутренние флаги); нет проблем сериализации навигационных свойств EF (циклы, ленивая загрузка); входные DTO защищают от over-posting. Цена — код маппинга.
**Follow-up:**
- «Ручной маппинг или AutoMapper?» — ручной прозрачнее и ловит ошибки компилятором; библиотеки экономят код, но прячут логику.
**Красные флаги:** «DTO — лишний код, всегда отдаю сущности».

### 11. Почему structured logging и как правильно логировать?
**Уровень:** junior
**Хороший ответ:** `ILogger<T>` из DI, шаблоны с плейсхолдерами: `logger.LogInformation("Order {OrderId} shipped", id)`. Значения сохраняются как поля — по ним можно искать в Seq/Elastic. Интерполяция теряет поля и аллоцирует строку даже при выключенном уровне. Уровни: Trace, Debug, Information, Warning, Error, Critical; минимальный уровень — в конфигурации по категориям.
**Follow-up:**
- «Что логировать на уровне Error?» — неожиданные сбои, требующие внимания; ошибки клиента (400/404) — не Error.
- «Что нельзя логировать?» — пароли, токены, персональные данные.
**Красные флаги:** `Console.WriteLine` в сервисах; логирование паролей.

### 12. Live coding: напиши middleware, который добавляет заголовок `X-Elapsed-Ms` со временем обработки запроса
**Уровень:** junior+
**Хороший ответ:**
```csharp
public sealed class ElapsedMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var start = Stopwatch.GetTimestamp();
        context.Response.OnStarting(() =>
        {
            var ms = Stopwatch.GetElapsedTime(start).TotalMilliseconds;
            context.Response.Headers["X-Elapsed-Ms"] = ms.ToString("0", CultureInfo.InvariantCulture);
            return Task.CompletedTask;
        });
        await next(context);
    }
}
// app.UseMiddleware<ElapsedMiddleware>();
```
Ключевое — понимать, что после `await next` заголовки могут быть уже отправлены, поэтому `OnStarting`. `Stopwatch`, а не `DateTime.Now` (монотонные часы, точность).
**Follow-up:**
- «Куда в pipeline поставишь?» — в начало, чтобы измерить максимум.
- «Что будет, если в `OnStarting` бросить исключение?» — ответ сломается; callback должен быть простым.
**Красные флаги:** ставит заголовок после `await next` и не видит проблемы; `DateTime.Now` для замеров.

### 13. Что будет выведено/возвращено? (DI)
**Уровень:** junior+
```csharp
builder.Services.AddScoped<Counter>();
app.MapGet("/", (Counter a, Counter b) => { a.Inc(); b.Inc(); return b.Value; });
```
**Хороший ответ:** Каждый запрос вернёт `2`: в рамках одного запроса Scoped — один и тот же экземпляр, но новый на следующий запрос. С Transient было бы `1`, с Singleton — `2, 4, 6, …`.
**Follow-up:**
- «Как сделать Singleton-счётчик потокобезопасным?» — `Interlocked.Increment`.
**Красные флаги:** путает Scoped и Singleton.
