# Интервью: модуль 13 — Асинхронность и многопоточность

### 1. Чем отличаются процесс и поток?
**Уровень:** junior
**Хороший ответ:** Процесс — запущенная программа с изолированным адресным пространством и ресурсами. Поток — единица выполнения внутри процесса; потоки одного процесса делят общую память (кучу), у каждого свой стек. Переключением потоков на ядрах управляет ОС. Создание потока дорогое (память под стек, системные вызовы), поэтому в .NET используют ThreadPool.
**Follow-up:**
- «Что общего у потоков процесса?» → managed heap, static-поля; поэтому нужна синхронизация.
- «Что такое thread pool starvation?» → все потоки пула заняты (часто — блокирующим ожиданием), новые задачи ждут.
**Красные флаги:** «поток = ядро процессора»; «у потоков отдельная память».

### 2. Task vs Thread
**Уровень:** junior
**Хороший ответ:** Thread — поток ОС. Task — объект, представляющий будущий результат операции. Task может выполняться на потоке пула через Task.Run, а при асинхронном IO вообще не занимает поток, пока идёт ожидание. Task поддерживает результат, исключения, отмену, композицию (WhenAll/WhenAny) и await. Создавать Thread вручную нужно редко.
**Follow-up:**
- «Всегда ли Task выполняется в другом потоке?» → нет: `Task.FromResult`, IO-задачи, синхронно завершённые async-методы.
- «Что такое TaskCompletionSource?» → способ создать Task, которым управляешь вручную (обёртка над событиями/колбэками).
**Красные флаги:** «Task — это лёгкий поток»; «каждый Task создаёт поток».

### 3. Что делает await?
**Уровень:** junior
**Хороший ответ:** Компилятор превращает async-метод в state machine. Метод выполняется синхронно до первого await незавершённой задачи; тогда регистрируется продолжение, вызывающему возвращается Task, и поток освобождается. Когда операция завершится, остаток метода выполнится в захваченном SynchronizationContext (если он есть) или на потоке пула. Исключения сохраняются в Task и выбрасываются при await.
**Глубже (для junior+):** awaiter pattern (`GetAwaiter`, `IsCompleted`, `OnCompleted`, `GetResult`); state machine — struct, которая «боксится» в кучу только при реальной приостановке.
**Follow-up:**
- «Если задача уже завершена?» → продолжение выполняется сразу, синхронно.
- «Где выполнится код после await в консольном приложении?» → на потоке пула (контекста нет).
**Красные флаги:** «await создаёт новый поток»; «await блокирует поток до завершения».

### 4. Почему .Result/.Wait() приводят к deadlock?
**Уровень:** junior
**Хороший ответ:** В средах с SynchronizationContext (WinForms/WPF, классический ASP.NET) продолжение после await по умолчанию хочет выполниться в исходном потоке. Если этот поток заблокирован в .Result, продолжение не выполнится, а .Result ждёт его — взаимная блокировка. Решения: async all the way; ConfigureAwait(false) в библиотеках. В ASP.NET Core контекста нет, но блокировка тратит потоки пула и под нагрузкой ведёт к starvation.
**Follow-up:**
- «А `GetAwaiter().GetResult()`?» → та же блокировка; отличие только в том, что исключение не обёрнуто в AggregateException.
- «Как вызвать async из синхронного Main?» → с C# 7.1 `static async Task Main`.
**Красные флаги:** «.Result — нормальный способ получить значение»; не знает про SynchronizationContext вовсе.

### 5. Зачем ConfigureAwait(false)?
**Уровень:** junior / junior+
**Хороший ответ:** Чтобы продолжение после await не возвращалось в захваченный SynchronizationContext, а шло на любом потоке пула. Даёт меньше переключений и защиту от deadlock, если вызывающий блокирует поток. Используют в библиотеках. В UI-коде нельзя, если после await обращаемся к элементам интерфейса. В приложении ASP.NET Core эффекта почти нет — контекста там нет.
**Follow-up:**
- «Нужно ли писать ConfigureAwait(false) в контроллерах ASP.NET Core?» → не нужно, но и не вредно.
**Красные флаги:** «ConfigureAwait(false) запускает код в фоне»; «ускоряет любой код в разы».

### 6. Почему async void — плохо?
**Уровень:** junior
**Хороший ответ:** Нет Task — вызывающий не может дождаться завершения и узнать об ошибке. Исключение выбрасывается в SynchronizationContext/пул и обычно роняет процесс; try/catch вокруг вызова его не поймает. Сложно тестировать. Допустимо только для обработчиков событий, где сигнатура void навязана.
**Follow-up:**
- «Что с лямбдой `list.ForEach(async x => await SaveAsync(x))`?» → это async void-лямбда (`Action<T>`): ForEach не ждёт, исключения теряются.
**Красные флаги:** «async void — то же, что async Task, только без возврата».

### 7. CPU-bound vs IO-bound. Когда Task.Run?
**Уровень:** junior
**Хороший ответ:** CPU-bound — вычисления, поток нужен постоянно; IO-bound — ожидание сети/диска/БД, поток нужен только до и после. Для IO используют настоящие async-API без Task.Run. Task.Run — чтобы увести CPU-работу с потока, который нельзя блокировать (UI). В ASP.NET Core Task.Run в обработчике запроса ничего не ускоряет — тот же пул. Для параллельных вычислений над коллекцией — Parallel.For/ForEach.
**Follow-up:**
- «Что плохого в `await Task.Run(() => File.ReadAllTextAsync(p))`?» → лишняя обёртка, лишний переход в пул.
**Красные флаги:** «Task.Run делает метод асинхронным, его надо всегда использовать».

### 8. Как отменить асинхронную операцию?
**Уровень:** junior
**Хороший ответ:** Через CancellationToken: вызывающий создаёт CancellationTokenSource, передаёт Token; код периодически вызывает ThrowIfCancellationRequested и передаёт токен во вложенные вызовы. Отмена кооперативная — код сам решает, где безопасно остановиться. Результат отмены — OperationCanceledException. Для таймаута — CancelAfter или WaitAsync; для нескольких причин — CreateLinkedTokenSource.
**Follow-up:**
- «Почему не Thread.Abort?» → прерывал код в любом месте (оставлял сломанные инварианты), в .NET Core не поддерживается.
- «В ASP.NET Core откуда токен?» → `HttpContext.RequestAborted`, параметр `CancellationToken` в action.
**Красные флаги:** не знает про CancellationToken.

### 9. Что такое race condition? Как защититься?
**Уровень:** junior
**Хороший ответ:** Ситуация, когда результат зависит от порядка выполнения потоков, работающих с общими данными. Пример — `count++` из нескольких потоков теряет инкременты, потому что это чтение, изменение и запись. Защита: lock для критических секций (особенно check-then-act), Interlocked для атомарных операций над одной переменной, concurrent-коллекции, отказ от общего изменяемого состояния (immutable данные, сообщения).
**Follow-up:**
- «volatile решает проблему?» → нет: volatile про видимость, а не про атомарность.
- «Что такое deadlock в многопоточности?» → два потока держат по замку и ждут замок друг друга; профилактика — единый порядок захвата.
**Красные флаги:** «гонки бывают только в C++».

### 10. lock vs SemaphoreSlim vs Interlocked
**Уровень:** junior / junior+
**Хороший ответ:** lock (Monitor) — взаимное исключение для блока кода, привязан к потоку, внутри нельзя await. Interlocked — атомарные операции над одной переменной без блокировок, самый быстрый. SemaphoreSlim — ограничение на N одновременных входов, умеет WaitAsync, не привязан к потоку — поэтому подходит для async-кода; `SemaphoreSlim(1,1)` — async-аналог lock.
**Follow-up:**
- «Почему нельзя `lock(this)`?» → внешний код может заблокироваться на том же объекте.
- «Почему Release в finally?» → иначе исключение «съест» слот навсегда.
**Красные флаги:** путает SemaphoreSlim и Semaphore (именованный межпроцессный) без понимания разницы — допустимо; «в lock можно await» — красный флаг.

### 11. Какие потокобезопасные коллекции вы знаете?
**Уровень:** junior
**Хороший ответ:** ConcurrentDictionary, ConcurrentQueue, ConcurrentStack, ConcurrentBag, BlockingCollection, Channel&lt;T&gt; для async producer/consumer, immutable-коллекции. Важно: каждая операция атомарна, но последовательность «проверил, потом добавил» — нет; поэтому используют GetOrAdd, TryAdd, AddOrUpdate. Фабрика в GetOrAdd может вызваться несколько раз.
**Follow-up:**
- «Как сделать, чтобы фабрика вызвалась один раз?» → хранить `Lazy<T>` в словаре.
**Красные флаги:** «Dictionary потокобезопасен для записи, если не мешают друг другу».

### 12. Что выведет код?
**Уровень:** junior
```csharp
static async Task Main()
{
    try
    {
        Fire();
        await Task.Delay(100);
        Console.WriteLine("OK");
    }
    catch (Exception)
    {
        Console.WriteLine("Caught");
    }
}

static async void Fire()
{
    await Task.Yield();
    throw new InvalidOperationException();
}
```
**Хороший ответ:** «Caught» не напечатается. Исключение из async void выбрасывается на потоке пула (контекста нет), не проходит через try/catch вызывающего и, как необработанное, роняет процесс — скорее всего, ещё до «OK». Если бы Fire был `async Task` и мы сделали `await Fire()`, вывелось бы «Caught».
**Красные флаги:** «Caught», потому что «try/catch же вокруг».

### 13. Что выведет код?
**Уровень:** junior
```csharp
var sw = Stopwatch.StartNew();
var tasks = new List<Task>();
for (var i = 0; i < 3; i++)
    tasks.Add(Task.Delay(1000));
await Task.WhenAll(tasks);
Console.WriteLine(sw.Elapsed.TotalSeconds < 2);
```
**Хороший ответ:** `True` — все три задержки идут одновременно, общее время ~1 секунда. `Task.Delay` не занимает поток — это таймер. Если в цикле написать `await Task.Delay(1000)`, было бы ~3 секунды.

### 14. Мини live coding: параллельно, но не больше N
**Уровень:** junior / junior+
**Задание:** «Есть `Task<Product> GetProductAsync(int id)`. Загрузите 500 товаров, не больше 10 запросов одновременно, отменяемо».
**Хороший ответ:**
```csharp
public static async Task<Product[]> LoadAsync(IEnumerable<int> ids, CancellationToken ct)
{
    using var gate = new SemaphoreSlim(10);
    var tasks = ids.Select(async id =>
    {
        await gate.WaitAsync(ct);
        try { return await GetProductAsync(id, ct); }
        finally { gate.Release(); }
    }).ToArray();
    return await Task.WhenAll(tasks);
}
```
Альтернатива — `Parallel.ForEachAsync(ids, new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct }, async (id, token) => ...)` с `ConcurrentBag` для результатов.
**Follow-up:**
- «Почему WaitAsync до try?» → если ожидание отменено, Release вызывать нельзя — мы не захватили слот.
- «Что будет при ошибке одного запроса?» → остальные продолжат, WhenAll бросит первое исключение.
**Красные флаги:** `Wait()` вместо `WaitAsync`; Release не в finally; последовательный цикл.

### 15. Что такое ValueTask и IAsyncEnumerable?
**Уровень:** junior+
**Хороший ответ:** ValueTask&lt;T&gt; — struct-вариант Task&lt;T&gt; без аллокации, когда результат часто готов синхронно (кэш); ждать его можно только один раз. IAsyncEnumerable&lt;T&gt; — асинхронная последовательность: пишется через async + yield return, читается через await foreach; позволяет стримить данные (страницы API, строки БД) без загрузки всего в память. Отмена через `[EnumeratorCancellation]` и `WithCancellation`.
**Красные флаги:** «ValueTask всегда быстрее, надо везде использовать».
