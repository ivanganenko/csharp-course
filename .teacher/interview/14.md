# Интервью: модуль 14 — Unit-тестирование

### 1. Зачем нужны unit-тесты?
**Уровень:** junior
**Хороший ответ:** Защита от регрессий: изменения не ломают уже работающее. Возможность безопасно рефакторить. Документация поведения, которая не устаревает. Быстрая обратная связь — секунды, без запуска приложения. Тестируемость подталкивает к хорошему дизайну: явные зависимости, маленькие классы.
**Follow-up:**
- «Когда тесты не окупаются?» → одноразовые скрипты, прототипы; но для продакшен-кода почти всегда окупаются.
- «Кто должен писать тесты — разработчик или QA?» → unit-тесты пишет разработчик вместе с кодом.
**Красные флаги:** «тесты нужны, чтобы было покрытие»; «тестированием занимаются тестировщики».

### 2. Unit vs integration vs E2E. Пирамида тестов
**Уровень:** junior
**Хороший ответ:** Unit — единица логики в изоляции, зависимости подменены, быстро и детерминированно. Integration — с реальными компонентами (БД, HTTP, файловая система), медленнее, проверяет «швы». E2E — сценарий пользователя через всю систему, самый медленный и хрупкий. Пирамида: много unit, меньше integration, мало E2E — баланс цены и уверенности.
**Глубже (для junior+):** «testing trophy» (больше интеграционных тестов); в ASP.NET Core — `WebApplicationFactory`, Testcontainers для реальной БД.
**Follow-up:**
- «Тест репозитория с SQLite in-memory — unit или integration?» → интеграционный: проверяет взаимодействие с EF Core и провайдером БД.
**Красные флаги:** не различает уровни; «интеграционный — это когда тестов много».

### 3. Что такое AAA и как вы называете тесты?
**Уровень:** junior
**Хороший ответ:** Arrange — подготовка, Act — одно действие, Assert — проверка. Имя `Method_Condition_ExpectedResult`, например `Withdraw_AmountExceedsBalance_ThrowsInvalidOperation`. Так по упавшему тесту сразу понятно, какое правило нарушено. Один тест — одно поведение.
**Follow-up:**
- «Можно ли несколько Assert в тесте?» → да, если они проверяют одно поведение (например, несколько свойств результата).
**Красные флаги:** имена `Test1`, `TestMethod`; несколько Act в одном тесте.

### 4. Fact vs Theory. Как передать decimal в Theory?
**Уровень:** junior
**Хороший ответ:** `[Fact]` — тест без параметров, `[Theory]` — параметризованный, данные из `[InlineData]`, `[MemberData]`, `[ClassData]`. InlineData — аргументы атрибута, туда можно только константы примитивов, строки, enum, Type; decimal и DateTime нельзя. Для них — `[MemberData(nameof(Cases))]` со статическим `TheoryData<...>`.
**Follow-up:**
- «Как в NUnit/MSTest?» → `[Test]`/`[TestCase]` и `[TestMethod]`/`[DataRow]` — идеи те же.
**Красные флаги:** не знает Theory; копипастит одинаковые Fact.

### 5. Mock vs stub (vs fake)
**Уровень:** junior
**Хороший ответ:** Stub возвращает заданные данные, чтобы SUT мог работать; проверяем результат SUT. Mock — объект, по которому проверяем взаимодействие: вызван ли метод, сколько раз, с какими аргументами. Fake — упрощённая рабочая реализация (in-memory репозиторий). Ещё есть dummy (заполнитель) и spy (запоминает вызовы). Общее название — test doubles.
**Follow-up:**
- «В NSubstitute `Returns` — это stub или mock?» → настройка ответа — stub-поведение; `Received` — mock-проверка. Один объект может играть обе роли.
**Красные флаги:** «mock и stub — одно и то же»; «мок — это фейковые данные в JSON».

### 6. Как протестировать код, использующий DateTime.Now?
**Уровень:** junior
**Хороший ответ:** Вынести время в зависимость: свой `IClock` или встроенный `TimeProvider` (.NET 8+), передавать через конструктор. В production — системная реализация, в тестах — fake с фиксированным временем (`FakeTimeProvider` из Microsoft.Extensions.TimeProvider.Testing). Тогда можно проверить граничные моменты и «перематывать» время.
**Follow-up:**
- «А если нельзя менять конструктор?» → передать время параметром метода; в крайнем случае — перегрузка/фабрика; но не shims/статические подмены.
- «Как тестировать код с Task.Delay/таймерами?» → тоже через `TimeProvider` (у него есть таймеры), FakeTimeProvider умеет Advance.
**Красные флаги:** «запущу тест в пятницу»; «поставлю Thread.Sleep».

### 7. Что мокать, а что нет?
**Уровень:** junior / junior+
**Хороший ответ:** Мокаю внешние границы: БД/репозитории (в unit-тестах сервисов), HTTP-клиенты, почту, очереди, время, файловую систему. Не мокаю value objects, DTO, чистую логику — их проще использовать настоящими. Не перепроверяю каждое внутреннее взаимодействие — это делает тесты хрупкими. EF Core `DbContext` лучше не мокать, а тестировать интеграционно (SQLite in-memory или контейнер).
**Глубже (для junior+):** London vs Classical (Detroit) школы; «managed vs unmanaged dependencies» по Хорикову.
**Follow-up:**
- «Почему не мокать DbContext?» → поведение LINQ-провайдера (трансляция в SQL) мок не воспроизведёт; тест будет зелёным, а запрос упадёт в реальной БД.
**Красные флаги:** «мокаю всё, включая тестируемый класс».

### 8. Что такое dependency injection и как оно связано с тестируемостью?
**Уровень:** junior
**Хороший ответ:** Класс не создаёт зависимости сам, а получает их снаружи — обычно через конструктор и в виде интерфейсов. В production зависимости собирает DI-контейнер, в тестах — мы, подставляя test doubles. Так зависимости явные и заменяемые, и класс можно тестировать в изоляции. Связано с принципом Dependency Inversion из SOLID.
**Follow-up:**
- «Constructor injection vs property injection?» → конструктор делает зависимости обязательными и видимыми; property — для необязательных.
**Красные флаги:** «DI — это библиотека Autofac»; не связывает DI с тестами.

### 9. Что такое TDD? Используете ли вы его?
**Уровень:** junior
**Хороший ответ:** Цикл red-green-refactor: сначала падающий тест на следующее требование, потом минимальный код для прохождения, потом рефакторинг при зелёных тестах. Плюсы — тест гарантированно способен упасть, код тестируемый и минимальный, сразу есть страховка. Честный ответ: не всегда пишу строго по TDD, но для багфиксов всегда сначала пишу тест, воспроизводящий баг.
**Follow-up:**
- «Зачем видеть тест красным?» → чтобы убедиться, что он вообще что-то проверяет и падает по нужной причине.
**Красные флаги:** «TDD — это когда тесты пишут тестировщики»; «сначала пишу весь код, потом тесты — это и есть TDD».

### 10. Жизненный цикл тестов в xUnit. Fixtures
**Уровень:** junior / junior+
**Хороший ответ:** xUnit создаёт новый экземпляр тест-класса для каждого теста: конструктор — setup, `IDisposable.Dispose` — teardown, для async — `IAsyncLifetime`. Общий дорогой ресурс на класс — `IClassFixture<T>`, на несколько классов — `ICollectionFixture<T>` с `[Collection]`. Классы из разных коллекций выполняются параллельно.
**Follow-up:**
- «Чем отличается от NUnit?» → в NUnit один экземпляр на класс и атрибуты `[SetUp]/[TearDown]`; можно случайно делить состояние между тестами.
- «Почему тесты, использующие static-поле, могут падать случайно?» → static общий, тесты идут параллельно и в произвольном порядке.
**Красные флаги:** «тесты выполняются по порядку сверху вниз, можно на это полагаться».

### 11. Что такое code coverage? Какой процент нужен?
**Уровень:** junior
**Хороший ответ:** Доля строк/ветвлений, выполненных тестами (coverlet, dotnet-coverage, dotCover). Показывает непокрытые места, но не качество проверок — можно выполнить код без Assert. 100% — не цель; важнее покрытие бизнес-логики, ветвлений и граничных случаев. Ориентир для доменной логики — 70–90%.
**Красные флаги:** «у нас 100%, значит багов нет».

### 12. Что выведет / как поведёт себя тест?
**Уровень:** junior
```csharp
public class DiscountTests
{
    private static readonly List<string> Log = new();

    [Fact] public void A() { Log.Add("A"); Assert.Single(Log); }
    [Fact] public void B() { Log.Add("B"); Assert.Single(Log); }
}
```
**Хороший ответ:** Один из тестов упадёт: `Log` — static, общий для всех экземпляров класса; второй тест увидит два элемента. Какой именно упадёт — зависит от порядка, который не гарантирован. Это пример flaky/зависимых тестов. Решение — instance-поле (новый экземпляр на тест).
**Красные флаги:** «оба пройдут, потому что xUnit создаёт новый экземпляр» — не учитывает static.

### 13. Что не так с этим тестом?
**Уровень:** junior
```csharp
[Fact]
public async Task SendReminders_Works()
{
    var sender = Substitute.For<IEmailSender>();
    var service = new PaymentReminderService(new SystemClock(), sender);
    var order = new Order { CustomerEmail = "a@example.com", Status = OrderStatus.PaymentFailed,
                            CreatedAt = DateTimeOffset.UtcNow.AddDays(-1) };
    await service.SendRemindersAsync(new[] { order }, CancellationToken.None);
    await sender.ReceivedWithAnyArgs().SendAsync(default!, default!, default!, default);
}
```
**Хороший ответ:** (1) Используется реальное время (`SystemClock` + `UtcNow`) — граница «ровно сутки» зависит от миллисекунд между созданием заказа и проверкой: тест может мигать. Нужен fake clock с фиксированным «сейчас». (2) Имя `Works` ничего не говорит. (3) `ReceivedWithAnyArgs()` без количества и без проверки получателя/темы — слабая проверка.
**Красные флаги:** не видит проблему со временем.

### 14. Мини live coding: напишите тест
**Уровень:** junior
**Задание:** «Есть `class BankAccount { public decimal Balance { get; } public void Withdraw(decimal amount); }` — снятие больше баланса бросает `InvalidOperationException`, не меняя баланс. Напишите тесты».
**Хороший ответ:**
```csharp
public class BankAccountTests
{
    [Fact]
    public void Withdraw_AmountWithinBalance_DecreasesBalance()
    {
        var account = new BankAccount(initialBalance: 100m);

        account.Withdraw(30m);

        Assert.Equal(70m, account.Balance);
    }

    [Fact]
    public void Withdraw_AmountExceedsBalance_ThrowsAndKeepsBalance()
    {
        var account = new BankAccount(initialBalance: 100m);

        Assert.Throws<InvalidOperationException>(() => account.Withdraw(100.01m));
        Assert.Equal(100m, account.Balance);
    }

    [Fact]
    public void Withdraw_WholeBalance_LeavesZero()
    {
        var account = new BankAccount(initialBalance: 100m);
        account.Withdraw(100m);
        Assert.Equal(0m, account.Balance);
    }
}
```
**Follow-up:**
- «Какие ещё случаи?» → отрицательная/нулевая сумма (`ArgumentOutOfRangeException`), граница «ровно баланс», параллельные снятия (уже не unit-логика, а потокобезопасность).
**Красные флаги:** только «счастливый путь»; нет проверки, что баланс не изменился при исключении.

### 15. Почему курс использует xUnit v2, если вышел v3? Чем отличаются фреймворки?
**Уровень:** junior+
**Хороший ответ:** xUnit, NUnit и MSTest решают одно и то же; xUnit популярен в новых проектах и в самом .NET. v3 — новая версия (тесты как исполняемые файлы, Microsoft Testing Platform, новые API), но большинство существующих проектов и материалов — на v2, API атрибутов и Assert почти совпадает, переход несложный. Для собеседования важно знать концепции, а не версию.
**Красные флаги:** путает фреймворк тестирования с mocking-библиотекой.
