# Интервью: модуль 05 — наследование, полиморфизм, интерфейсы

### 1. Что такое полиморфизм? Приведите пример из реального кода.
**Уровень:** junior
**Хороший ответ:** Возможность работать с объектами разных типов через общий базовый тип или интерфейс, при этом каждый объект выполняет свою реализацию. Пример: `List<Shape>`, у каждой фигуры свой `Area()`; или `ILogger`, за которым может быть консоль, файл или Seq. В C# runtime-полиморфизм реализуется через `virtual`/`override` и интерфейсы; выбор метода — в runtime по типу объекта. Также бывает ad-hoc (перегрузка) и параметрический (generics).
**Глубже (для junior+):** vtable и interface dispatch; девиртуализация JIT для `sealed`.
**Follow-up:**
- «Перегрузка — это полиморфизм?» → да, ad-hoc, но compile-time.
- «Как полиморфизм помогает тестированию?» → подменяем реализацию интерфейса на fake/mock.
**Красные флаги:** «полиморфизм — это когда много методов с одним именем» (только перегрузка).

### 2. `virtual`, `override`, `new` — в чём разница?
**Уровень:** junior
**Хороший ответ:** `virtual` разрешает переопределение. `override` заменяет реализацию — вызов через базовую ссылку идёт в наследника (late binding). `new` скрывает метод базового класса — это отдельный метод, вызов определяется типом переменной (early binding). Без модификатора при совпадении имени — то же, что `new`, но с warning CS0108.
**Глубже (для junior+):** `override` переиспользует слот vtable, `new` (или `new virtual`) создаёт новый слот; `sealed override`.
**Follow-up:**
- «Можно ли переопределить невиртуальный метод?» → нет, только скрыть.
- «Можно ли override поменять модификатор доступа?» → нет (исключение — protected internal из другой сборки становится protected).
**Красные флаги:** «new и override одно и то же»; «new создаёт новый объект».

### 3. Что выведет код?
```csharp
class Animal { public virtual string Speak() => "..."; public string Name() => "Animal"; }
class Dog : Animal { public override string Speak() => "Woof"; public new string Name() => "Dog"; }

Animal a = new Dog();
Console.WriteLine($"{a.Speak()} {a.Name()} {((Dog)a).Name()}");
```
**Уровень:** junior
**Хороший ответ:** `Woof Animal Dog`. `Speak` виртуальный — вызывается версия реального типа `Dog`. `Name` скрыт через `new` — для переменной типа `Animal` вызывается `Animal.Name`, после приведения к `Dog` — `Dog.Name`.
**Follow-up:**
- «Что если убрать `new`?» → вывод тот же, только warning.
- «Что если `Name` в Animal сделать virtual, а в Dog — override?» → `Woof Dog Dog`.
**Красные флаги:** `Woof Dog Dog` для исходного кода.

### 4. Порядок вызова конструкторов при наследовании. Что выведет код?
```csharp
class Base { public Base() { Console.Write("B "); Show(); } protected virtual void Show() => Console.Write("Base.Show "); }
class Derived : Base
{
    private readonly int _x = 5;
    private int _y;
    public Derived() { _y = 7; Console.Write("D "); }
    protected override void Show() => Console.Write($"Derived.Show {_x} {_y} ");
}
new Derived();
```
**Уровень:** junior+
**Хороший ответ:** `B Derived.Show 5 0 D `. Сначала инициализаторы полей `Derived` (`_x = 5`), затем конструктор `Base`, который вызывает виртуальный `Show` — объект уже `Derived`, поэтому вызывается override; `_y` ещё 0, так как тело конструктора `Derived` не выполнялось. Потом тело `Derived`. Поэтому виртуальные вызовы в конструкторах — антипаттерн.
**Follow-up:**
- «А в Java?» → инициализаторы полей после `super()`, там `_x` был бы 0.
- «Как избежать?» → не вызывать virtual из ctor; фабричный метод / отдельный `Initialize`; `sealed`.
**Красные флаги:** «Base.Show», «сначала конструктор Derived».

### 5. Abstract class vs interface
**Уровень:** junior
**Хороший ответ:** Abstract class — частично реализованный базовый класс: состояние, конструкторы, любые модификаторы, abstract и обычные методы; наследовать можно один. Interface — контракт без состояния экземпляра; класс реализует несколько; с C# 8 могут быть default-реализации и static-члены. Интерфейс — «умеет» (can-do) и основа DI/моков; abstract class — «является» (is-a) и общий код. Часто комбинируют.
**Глубже (для junior+):** default interface methods не дают состояния и вызываются только через интерфейс; эволюция API библиотеки: добавление abstract-члена ломает наследников, добавление метода в интерфейс без default — ломает реализации.
**Follow-up:**
- «Если есть default methods, зачем abstract class?» → состояние, конструкторы, protected-члены, Template Method с невиртуальным алгоритмом.
- «Что выберете для репозитория?» → интерфейс для потребителей, возможно базовый класс для реализаций.
**Красные флаги:** «интерфейс — это abstract class без методов»; не знает про множественную реализацию.

### 6. Почему в C# нет множественного наследования классов?
**Уровень:** junior
**Хороший ответ:** Из-за проблемы ромба: если два базовых класса имеют одинаковый член или общего предка, неясно, какую реализацию и какую копию состояния получит наследник. C# выбрал простоту: один базовый класс + сколько угодно интерфейсов. Для default interface methods при конфликте компилятор требует явной реализации.
**Follow-up:**
- «Как переиспользовать код из двух источников?» → композиция: держать оба объекта как поля и делегировать.
**Красные флаги:** «можно, через интерфейсы» без оговорки, что интерфейсы не дают состояния/реализации класса.

### 7. Что такое явная реализация интерфейса и зачем?
**Уровень:** junior+
**Хороший ответ:** Реализация `ReturnType IInterface.Member(...)` без модификатора доступа. Член доступен только через ссылку на интерфейс. Нужно для конфликта одинаковых сигнатур из разных интерфейсов и чтобы скрыть член из публичного API класса.
**Follow-up:**
- «Можно ли сделать явную реализацию virtual?» → нет; если нужно, явная реализация вызывает protected virtual метод.
- «Пример из BCL?» → `List<T>` и необобщённый `IList`, `Dictionary` и `ICollection<KeyValuePair<,>>.Add`.
**Красные флаги:** путает с «explicit operator».

### 8. Upcast/downcast. `is`, `as`, приведение — когда что?
**Уровень:** junior
**Хороший ответ:** Upcast к базовому типу — неявный и безопасный. Downcast — явный, может бросить `InvalidCastException`. `as` возвращает null при неудаче (для reference/nullable). `is` проверяет тип, `is T x` — проверка + переменная. Предпочтительно `is T x`. Частые downcast'ы — запах дизайна: поведение лучше вынести в виртуальный метод.
**Follow-up:**
- «Почему `as` нельзя с `int`?» → int не может быть null; можно `as int?`.
**Красные флаги:** везде прямые касты в try/catch.

### 9. Что такое LSP? Пример.
**Уровень:** junior
**Хороший ответ:** Liskov Substitution Principle: наследник должен быть заменяем на базовый тип без нарушения корректности. Нельзя усиливать предусловия, ослаблять постусловия, ломать инварианты, бросать неожиданные исключения. Пример: `Square : Rectangle` с сеттерами — код, рассчитывающий на независимость ширины и высоты, ломается. Решение — неизменяемые фигуры или общий базовый `Shape`.
**Follow-up:**
- «Нарушение LSP в BCL?» → `ReadOnlyCollection<T>` реализует `IList<T>`, но `Add` бросает `NotSupportedException` (компромисс ради совместимости).
**Красные флаги:** путает LSP с «любой наследник можно положить в переменную базового типа» (это просто компилируемость, а не поведение).

### 10. Композиция или наследование?
**Уровень:** junior
**Хороший ответ:** По умолчанию композиция. Наследование — сильнейшая связь: наследник зависит от деталей базы, иерархию сложно менять, нельзя заменить поведение в runtime. Наследование уместно при настоящем is-a с соблюдением LSP и когда нужен полиморфизм через базу. Плохой пример — `class Stack : List` (появляются лишние операции).
**Follow-up:**
- «Какие паттерны основаны на композиции?» → Strategy, Decorator, Composite.
**Красные флаги:** наследует ради одного вспомогательного метода.

### 11. Что такое default interface methods? Где их использовать?
**Уровень:** junior+
**Хороший ответ:** С C# 8 интерфейс может содержать реализацию метода. Классы, реализующие интерфейс, могут её не переопределять. Метод вызывается только через ссылку на интерфейс. Основное назначение — эволюция публичных интерфейсов библиотек без поломки реализаций.
**Follow-up:**
- «Чем отличается от extension method для интерфейса?» → default method можно переопределить в реализации, extension — нет; extension виден на переменной класса.
**Красные флаги:** «теперь интерфейсы = abstract classes».

### 12. Что такое `sealed`? Влияет ли на производительность?
**Уровень:** junior
**Хороший ответ:** `sealed class` запрещает наследование, `sealed override` — дальнейшее переопределение. Используется, когда класс не спроектирован для расширения. JIT может девиртуализировать вызовы у sealed-типов и ускорить проверки типов — небольшой выигрыш.
**Красные флаги:** «sealed — значит нельзя создать экземпляр» (путает с abstract/static).

### 13. Live coding: замените switch по типу полиморфизмом
**Уровень:** junior
**Задание интервьюера:**
```csharp
decimal Shipping(string kind, decimal weight) => kind switch
{
    "standard" => 5 + weight * 1,
    "express" => 15 + weight * 2,
    "pickup" => 0,
    _ => throw new ArgumentException(nameof(kind)),
};
```
«Отрефакторьте так, чтобы новый способ доставки не требовал менять существующий код».
**Хороший ответ:**
```csharp
public interface IShippingMethod { decimal Cost(decimal weight); }
public sealed class Standard : IShippingMethod { public decimal Cost(decimal w) => 5 + w; }
public sealed class Express : IShippingMethod { public decimal Cost(decimal w) => 15 + w * 2; }
public sealed class Pickup : IShippingMethod { public decimal Cost(decimal w) => 0; }

public sealed class Checkout(IShippingMethod shipping)
{
    public decimal Total(decimal subtotal, decimal weight) => subtotal + shipping.Cost(weight);
}
```
Интервьюер ждёт: интерфейс или abstract class, Open/Closed, упоминание Strategy, где теперь выбирается реализация (фабрика / DI / словарь `string → IShippingMethod` на границе системы).
**Follow-up:**
- «Где теперь switch по строке из запроса?» → в одном месте на границе (фабрика), а не по всему коду.
- «Когда switch лучше?» → закрытый, стабильный набор вариантов; операции над данными, которые меняются чаще, чем набор типов.
**Красные флаги:** перенёс switch в другой метод и считает, что задача решена.

### 14. Какие методы есть у `object`? Какие виртуальные?
**Уровень:** junior
**Хороший ответ:** `ToString`, `Equals(object)`, `GetHashCode` — virtual; `GetType` — не virtual; `MemberwiseClone` — protected (поверхностная копия); static `Equals(a, b)` и `ReferenceEquals`; `Finalize` (protected, через синтаксис деструктора). Чаще всего переопределяют `ToString`, `Equals` + `GetHashCode` (модуль 06).
**Красные флаги:** не знает, что `GetType` возвращает runtime-тип.
