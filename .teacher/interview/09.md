# Interview: модуль 09 — Коллекции и сложность

### 1. Как устроен Dictionary внутри?
**Уровень:** junior
**Хороший ответ:** Это хэш-таблица. Есть массив бакетов и массив записей. При добавлении вычисляется `GetHashCode` ключа, по нему — индекс бакета. Если в бакете уже есть ключи (коллизия), они связываются в цепочку, и поиск сравнивает ключи через `Equals`. При заполнении таблица увеличивается (до следующего простого числа) и элементы перераспределяются. Поиск, вставка, удаление — O(1) в среднем.
**Глубже (для junior+):** худший случай — O(n), если все ключи дают один хэш (плохой `GetHashCode` или атака на хэш-функцию; для строк .NET использует рандомизированный хэш). Порядок перечисления не гарантирован. Удаление оставляет «дырки» в массиве записей, которые переиспользуются.
**Follow-up:**
- «Что будет, если ключ изменить после добавления?» — новый хэш укажет на другой бакет, элемент не найдётся.
- «Почему `string` — хороший ключ?» — неизменяемый, корректно переопределены `Equals`/`GetHashCode`.
- «Что быстрее: `ContainsKey` + `dict[key]` или `TryGetValue`?» — `TryGetValue`, один поиск.
**Красные флаги:** «Dictionary — это список пар, ищет перебором»; не знает, зачем `GetHashCode`.

### 2. Контракт Equals/GetHashCode. Что будет при нарушении?
**Уровень:** junior
**Хороший ответ:** Если `a.Equals(b)`, то хэш-коды обязаны совпадать. Обратное необязательно: разные объекты могут иметь одинаковый хэш (коллизия). Если переопределить `Equals` без `GetHashCode`, равные объекты попадут в разные бакеты — `HashSet.Contains` и `Dictionary.ContainsKey` вернут `false`, появятся «дубликаты» в HashSet. Хэш должен быть стабильным, пока объект лежит в коллекции.
**Follow-up:**
- «`GetHashCode() => 0` — корректен?» — формально да, но всё в одном бакете, O(n).
- «Как правильно написать `GetHashCode`?» — `HashCode.Combine(X, Y)` или `record`, который генерирует его сам.
**Красные флаги:** «GetHashCode возвращает уникальный id объекта».

### 3. List vs массив vs LinkedList — когда что?
**Уровень:** junior
**Хороший ответ:** Массив — фиксированный размер, минимальные накладные расходы. `List<T>` — динамический массив: индекс O(1), `Add` амортизированно O(1) за счёт удвоения capacity, вставка/удаление в начале O(n). `LinkedList<T>` — двусвязный список: O(1) вставка/удаление по известному узлу, но нет индекса, больше памяти, плохая cache locality. По умолчанию — `List<T>`; `LinkedList` — в специфичных случаях вроде LRU.
**Follow-up:**
- «Почему `List` быстрее `LinkedList` даже при вставках в середину небольших коллекций?» — копирование соседних элементов в памяти очень быстрое (memmove), а обход узлов — промахи кэша.
**Красные флаги:** «LinkedList всегда быстрее для вставки».

### 4. Какая сложность у основных операций коллекций?
**Уровень:** junior
**Хороший ответ:** `List`: индекс O(1), `Add` O(1)*, `Insert(0)`/`RemoveAt(0)` O(n), `Contains` O(n), `Sort` O(n log n). `Dictionary`/`HashSet`: Add/Remove/Contains O(1) в среднем. `SortedDictionary`/`SortedSet`: O(log n). `Queue`/`Stack`: O(1). `PriorityQueue`: Enqueue/Dequeue O(log n).
**Follow-up:**
- «Что такое амортизированная сложность?» — средняя стоимость в длинной серии операций.
- «Сложность `BinarySearch`?» — O(log n), только на отсортированных данных.
**Красные флаги:** путает O(log n) и O(n log n); не может оценить вложенные циклы.

### 5. Чем IEnumerable отличается от ICollection и IList? Что возвращать из метода?
**Уровень:** junior
**Хороший ответ:** `IEnumerable<T>` — только перебор, может быть ленивым. `ICollection<T>` — + `Count`, `Add`, `Remove`, `Contains`. `IList<T>` — + индекс, `Insert`. Принимать стоит самый общий нужный интерфейс (`IEnumerable<T>`), возвращать — read-only (`IReadOnlyList<T>`, `IReadOnlyCollection<T>`), чтобы не нарушить инкапсуляцию.
**Глубже (для junior+):** `IReadOnlyList<out T>` ковариантен, `IList<T>` — нет. Read-only — это view, не immutable.
**Follow-up:**
- «Почему не возвращать `IEnumerable<T>` всегда?» — вызывающий не знает, материализован ли результат; возможна multiple enumeration.
**Красные флаги:** не видит проблемы в публичном `List<T>` свойстве с внутренним состоянием.

### 6. Что такое yield return? Когда выполняется код итератора?
**Уровень:** junior / junior+
**Хороший ответ:** `yield return` превращает метод в итератор: компилятор генерирует класс-state machine, реализующий `IEnumerable`/`IEnumerator`. Код выполняется лениво: при вызове метода ничего не происходит, при каждом `MoveNext` — до следующего `yield return`. Можно делать бесконечные последовательности. Каждый новый `foreach` запускает тело заново.
**Глубже (для junior+):** проверки аргументов в итераторе тоже ленивые — поэтому валидацию выносят во внешний метод без `yield` (так устроен LINQ). `finally` в итераторе выполняется при `Dispose` enumerator-а (например, при `break` из foreach).
**Follow-up:**
- «Как сделать, чтобы ArgumentNullException вылетел сразу?» — внешний метод + локальная функция-итератор.
**Красные флаги:** «yield return возвращает список».

### 7. Что выведет код?
```csharp
static IEnumerable<int> Numbers()
{
    Console.WriteLine("start");
    yield return 1;
    yield return 2;
}

var numbers = Numbers();
Console.WriteLine(numbers.Count());
Console.WriteLine(numbers.First());
```
**Уровень:** junior+
**Хороший ответ:** `start`, `2`, `start`, `1`. Каждое перечисление (`Count()` и `First()`) запускает итератор заново — тело выполняется дважды. Это multiple enumeration: если внутри был бы запрос к БД или чтение файла, работа удвоилась бы.
**Follow-up:**
- «Как избежать?» — материализовать один раз: `var list = Numbers().ToList();`.
**Красные флаги:** «start выведется один раз».

### 8. Почему нельзя изменять коллекцию в foreach? Как удалить элементы?
**Уровень:** junior
**Хороший ответ:** Коллекции хранят версию, которая меняется при изменении; enumerator проверяет её на каждом `MoveNext` и бросает `InvalidOperationException`. Это fail-fast защита от пропуска элементов. Удалять — `RemoveAll(predicate)`, обратным циклом `for`, или перебирать копию.
**Follow-up:**
- «А в Dictionary можно удалять во время foreach?» — с .NET Core 3.0 `Remove` разрешён, но лучше не полагаться.
**Красные флаги:** предлагает `try/catch` вокруг foreach.

### 9. HashSet vs List для проверки вхождения
**Уровень:** junior
**Хороший ответ:** `HashSet.Contains` — O(1) в среднем, `List.Contains` — O(n). Для частых проверок — HashSet. Минусы HashSet: нет индекса, порядок не гарантирован, больше памяти на элемент. `HashSet.Add` возвращает `bool` — удобно для «впервые встретили?».
**Follow-up:**
- «Как удалить дубликаты, сохранив порядок?» — HashSet + List, один проход.
**Красные флаги:** «разницы нет, оба ищут».

### 10. Когда SortedDictionary, а когда Dictionary + сортировка?
**Уровень:** junior+
**Хороший ответ:** `SortedDictionary` (красно-чёрное дерево) поддерживает порядок постоянно — O(log n) на операцию. Нужен, если данные часто меняются и отсортированный вид нужен постоянно (расписание, стакан заявок). Если сортировка нужна один раз в конце — дешевле `Dictionary` (O(1)) + одна сортировка O(n log n). `SortedList` — массивы: компактнее, но вставка O(n).
**Красные флаги:** считает, что `Dictionary` хранит элементы отсортированными.

### 11. Стабилен ли PriorityQueue? Как сделать FIFO среди равных?
**Уровень:** junior+
**Хороший ответ:** Нет, это двоичная куча; равные элементы выходят в произвольном порядке. Решение — составной приоритет `(priority, sequence)`, где sequence увеличивается при каждом добавлении; кортежи сравниваются лексикографически.
**Follow-up:**
- «Как в PriorityQueue сделать max-heap?» — передать компаратор `Comparer<int>.Create((a, b) => b.CompareTo(a))` или инвертировать приоритет.
**Красные флаги:** не знает, что такое куча; думает, что PriorityQueue хранит отсортированный список.

### 12. Live coding: Two Sum
```
Дан массив int[] nums и target. Верни индексы двух элементов, сумма которых равна target.
```
**Уровень:** junior
**Хороший ответ:** сначала назвать brute force O(n²), затем:
```csharp
static (int, int)? TwoSum(int[] nums, int target)
{
    var seen = new Dictionary<int, int>();
    for (int j = 0; j < nums.Length; j++)
    {
        if (seen.TryGetValue(target - nums[j], out int i)) return (i, j);
        seen.TryAdd(nums[j], j);
    }
    return null;
}
```
Сложность O(n) по времени, O(n) по памяти. Важно: поиск до добавления (иначе элемент сложится сам с собой).
**Follow-up:**
- «А если массив отсортирован?» — два указателя, O(n) и O(1) памяти.
- «А если нужны все пары?» — словарь значение → список индексов или счётчик.
**Красные флаги:** не может объяснить, почему словарь ускоряет; не называет сложность.

### 13. Live coding: LRU-кэш (junior+)
**Уровень:** junior+
**Хороший ответ:** `Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>>` + `LinkedList`. Get: найти узел, перенести в начало. Put: если есть — обновить и перенести; если нет и полон — удалить `Last` из списка и его ключ из словаря; добавить в начало. Всё O(1). Ключ в узле нужен для удаления из словаря при вытеснении.
**Follow-up:**
- «Почему не `List<TKey>` для порядка?» — `Remove` O(n).
- «Потокобезопасно?» — нет; `lock` или специализированные решения.
**Красные флаги:** вытеснение «первого добавленного» (FIFO) вместо LRU; не понимает, зачем LinkedList.
