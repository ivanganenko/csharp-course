# Интервью: модуль 16 — EF Core и SQL

### 1. Что такое DbContext? Какой у него lifetime и почему?
**Уровень:** junior
**Хороший ответ:** DbContext — центральный класс EF Core: содержит DbSet-ы, change tracker и метод SaveChanges; по сути реализует паттерны Unit of Work и Repository. Он короткоживущий и не потокобезопасный, поэтому в ASP.NET Core регистрируется как Scoped — один на HTTP-запрос. Долгоживущий контекст копит отслеживаемые сущности, отдаёт устаревшие данные и ломается при параллельном использовании.
**Глубже (для junior+):** `AddDbContextPool` переиспользует экземпляры (сбрасывая состояние) для снижения аллокаций; `IDbContextFactory<T>` — для Blazor/фоновых задач, где scope не совпадает с операцией.
**Follow-up:**
- «Можно ли выполнить два запроса параллельно через `Task.WhenAll` на одном контексте?» — нет, будет исключение; нужен отдельный контекст на каждую задачу.
- «Что будет, если внедрить DbContext в Singleton?» — captive dependency.
**Красные флаги:** «DbContext лучше сделать Singleton для производительности»; «держу один контекст на всё приложение».

### 2. Что такое проблема N+1? Как обнаружить и решить?
**Уровень:** junior
**Хороший ответ:** Один запрос загружает список, а затем для каждого элемента выполняется ещё по запросу — например, в цикле или неявно через lazy loading. При 1000 элементов — 1001 round-trip к БД. Решения: eager loading через `Include`, проекция в DTO с нужными полями (один SQL), загрузка деталей одним запросом через `Contains(ids)`. Обнаруживают по логам SQL (`LogTo`, `EnableSensitiveDataLogging` в dev), профайлерам, APM.
**Глубже (для junior+):** cartesian explosion при нескольких Include коллекций → `AsSplitQuery`; проекция лучше Include для чтения — меньше колонок, нет tracking.
**Follow-up:**
- «Почему lazy loading опасен?» — обращение к свойству незаметно делает запрос; N+1 не виден в коде.
- «Как убедиться, что проблема решена?» — посчитать SQL-команды в логе/тесте.
**Красные флаги:** не может привести пример; «решается добавлением индекса».

### 3. IEnumerable vs IQueryable — что выведет / сколько данных загрузится?
**Уровень:** junior
```csharp
IEnumerable<Book> books = db.Books;
var count = books.Count(b => b.Year > 2000);
```
**Хороший ответ:** Загрузится вся таблица Books (`SELECT * FROM Books`), а подсчёт выполнится в памяти, потому что статический тип переменной — `IEnumerable<Book>`, и `Count` — это LINQ to Objects. С `IQueryable<Book>` (или `db.Books.Count(...)` напрямую) EF сгенерировал бы `SELECT COUNT(*) ... WHERE Year > 2000`. IQueryable хранит expression tree, которое провайдер переводит в SQL.
**Follow-up:**
- «Что делает `AsEnumerable()` в середине запроса?» — всё после него выполняется в памяти.
- «Что будет, если в Where вызвать свой C#-метод?» — EF Core 3+ бросит «could not be translated».
**Красные флаги:** «разницы нет, это просто интерфейсы».

### 4. Tracking vs AsNoTracking. Что делает SaveChanges?
**Уровень:** junior
**Хороший ответ:** Обычный запрос регистрирует сущности в change tracker и запоминает исходные значения; `SaveChanges` находит изменения (состояния Added/Modified/Deleted), генерирует INSERT/UPDATE/DELETE и выполняет их в транзакции. `AsNoTracking` отключает отслеживание — быстрее и экономнее для чтения, но изменения таких объектов не сохранятся без `Update`/`Attach`.
**Глубже (для junior+):** identity resolution — tracked-запрос возвращает тот же экземпляр для той же строки; `AsNoTrackingWithIdentityResolution`; `ExecuteUpdate/ExecuteDelete` (EF7+) обходят change tracker.
**Follow-up:**
- «Какие состояния сущности бывают?» — Detached, Unchanged, Added, Modified, Deleted.
- «Чем `Update(entity)` отличается от изменения свойства tracked-сущности?» — Update помечает все свойства Modified → UPDATE всех колонок.
**Красные флаги:** путает AsNoTracking с «не загружать навигации».

### 5. Как загрузить связанные данные в EF Core?
**Уровень:** junior
**Хороший ответ:** Eager loading — `Include`/`ThenInclude` (в том же запросе через JOIN); explicit loading — `db.Entry(x).Collection(...).LoadAsync()`; lazy loading — через proxies и virtual-навигации (выключено по умолчанию); проекция `Select` — загрузить только нужные поля, включая данные связанных таблиц. Без этого навигации остаются null/пустыми.
**Follow-up:**
- «Что такое filtered include?» — `Include(a => a.Books.Where(b => b.Year > 2000).OrderBy(...))`, EF Core 5+.
- «Что такое split query?» — несколько SQL вместо одного большого JOIN для нескольких коллекций.
**Красные флаги:** «включу lazy loading везде».

### 6. Что такое миграции? Как применять в продакшене?
**Уровень:** junior
**Хороший ответ:** Миграции — версионируемые изменения схемы БД, сгенерированные из разницы между моделью и последним снимком (`dotnet ef migrations add Name`). Применяются `dotnet ef database update`, `Database.Migrate()` или SQL-скриптом (`dotnet ef migrations script --idempotent`) в pipeline деплоя. История — в таблице `__EFMigrationsHistory`. Миграцию обязательно читают: EF может интерпретировать переименование как удаление + добавление столбца.
**Глубже (для junior+):** миграции должны быть обратно совместимы при rolling deploy (старая версия приложения работает с новой схемой): сначала добавить столбец, потом начать использовать, потом удалить старый.
**Follow-up:**
- «EnsureCreated vs Migrate?» — первое создаёт схему без миграций (тесты), второе применяет миграции.
- «Что делать, если два разработчика создали миграции параллельно?» — пересоздать/упорядочить, снимок модели — частый конфликт в git.
**Красные флаги:** «правлю схему руками в проде»; не знает про таблицу истории.

### 7. SQL: INNER JOIN vs LEFT JOIN, WHERE vs HAVING. Напиши запрос.
**Уровень:** junior
**Хороший ответ:** INNER JOIN — только совпавшие пары; LEFT JOIN — все строки левой таблицы, несовпавшие поля правой — NULL. WHERE фильтрует строки до группировки, HAVING — группы по агрегатам. Пример: авторы с количеством книг, включая авторов без книг:
```sql
SELECT a.Name, COUNT(b.Id) AS BookCount
FROM Authors a LEFT JOIN Books b ON b.AuthorId = a.Id
GROUP BY a.Id, a.Name
ORDER BY BookCount DESC;
```
**Follow-up:**
- «Почему `COUNT(b.Id)`, а не `COUNT(*)`?» — `COUNT(*)` посчитает строку с NULL как 1.
- «Только авторы с > 2 книгами?» — `HAVING COUNT(b.Id) > 2`.
**Красные флаги:** фильтр по агрегату в WHERE; не знает LEFT JOIN.

### 8. Что такое индекс? Какие минусы?
**Уровень:** junior
**Хороший ответ:** Индекс — отдельная структура (обычно B-дерево), позволяющая искать строки по значению за O(log n) без полного сканирования. Ускоряет WHERE, JOIN, ORDER BY. Минусы: место на диске и замедление INSERT/UPDATE/DELETE — каждый индекс нужно обновлять. Уникальный индекс дополнительно гарантирует уникальность. Индексируют часто фильтруемые столбцы и внешние ключи.
**Глубже (для junior+):** составной индекс работает по левому префиксу (индекс (A, B) помогает фильтру по A, но не по B); covering index; селективность; clustered vs non-clustered (SQL Server).
**Follow-up:**
- «Почему запрос с `LIKE '%abc'` не использует индекс?» — ведущий wildcard, B-дерево не помогает.
**Красные флаги:** «индексы на все колонки — будет быстрее».

### 9. Транзакции: что такое ACID? Нужна ли транзакция вокруг SaveChanges?
**Уровень:** junior
**Хороший ответ:** Транзакция — группа операций «всё или ничего». ACID: атомарность, согласованность, изоляция, долговечность. Один `SaveChanges` уже выполняется в транзакции. Явная (`BeginTransactionAsync` → `CommitAsync`) нужна, когда операция включает несколько `SaveChanges` или «прочитать-проверить-записать» и инвариант должен держаться для всей последовательности.
**Глубже (для junior+):** уровни изоляции (Read Committed по умолчанию в SQL Server/PostgreSQL) и аномалии; на Read Committed «проверил-записал» всё ещё подвержен гонке → Serializable, блокировки или optimistic concurrency.
**Follow-up:**
- «Что произойдёт, если не вызвать Commit?» — при Dispose транзакция откатится.
**Красные флаги:** оборачивает каждый SaveChanges в транзакцию «на всякий случай» и не может объяснить зачем.

### 10. Как решить конфликт одновременного редактирования?
**Уровень:** junior+
**Хороший ответ:** Optimistic concurrency: concurrency token (`[Timestamp] byte[] RowVersion` в SQL Server или `IsConcurrencyToken`). EF добавляет в UPDATE условие на исходное значение токена; если запись изменили, затронуто 0 строк → `DbUpdateConcurrencyException`. Обрабатываем: показываем пользователю конфликт, перечитываем и повторяем или сливаем изменения. Pessimistic — блокировка строки (`SELECT ... FOR UPDATE`), когда конфликты часты.
**Follow-up:**
- «Как это выглядит в REST API?» — ETag/If-Match, ответ 409/412.
**Красные флаги:** «последний записавший выигрывает — норм» без осознания потери данных.

### 11. Зачем ORM? Когда возьмёшь Dapper?
**Уровень:** junior
**Хороший ответ:** ORM убирает рутину: маппинг строк на объекты, генерация INSERT/UPDATE, миграции, типобезопасные LINQ-запросы. Минус — менее прозрачный и не всегда оптимальный SQL. Dapper — micro-ORM: пишешь SQL сам, он только маппит результат; быстрее и полный контроль, но без change tracking и миграций. Часто комбинируют: EF Core для CRUD, Dapper для сложных отчётов.
**Follow-up:**
- «Как защититься от SQL injection в Dapper?» — параметры `@Name`, никакой конкатенации.
**Красные флаги:** «ORM всегда медленный» или «SQL знать не нужно, есть EF».

### 12. Live coding: метод «страница книг автора с фильтром по году»
**Уровень:** junior+
**Задача:** `Task<List<BookDto>> GetPageAsync(int authorId, int? fromYear, int page, int size)` — книги автора, опционально с года fromYear, сортировка по названию, нужная страница, только Id и Title.
**Хороший ответ:**
```csharp
public async Task<List<BookDto>> GetPageAsync(int authorId, int? fromYear, int page, int size, CancellationToken ct = default)
{
    ArgumentOutOfRangeException.ThrowIfLessThan(page, 1);
    ArgumentOutOfRangeException.ThrowIfLessThan(size, 1);

    var query = db.Books.Where(b => b.AuthorId == authorId);
    if (fromYear is { } year)
        query = query.Where(b => b.PublishedYear >= year);

    return await query
        .OrderBy(b => b.Title).ThenBy(b => b.Id)
        .Skip((page - 1) * size).Take(size)
        .Select(b => new BookDto(b.Id, b.Title))
        .ToListAsync(ct);
}
```
Ключевое: IQueryable до конца, условный фильтр, OrderBy до Skip/Take, проекция, CancellationToken.
**Follow-up:**
- «Как вернуть ещё общее количество?» — отдельный `CountAsync` по query до пагинации.
**Красные флаги:** `ToListAsync()` в начале; `Skip(page * size)`; нет сортировки.

### 13. Что выведет код?
**Уровень:** junior+
```csharp
var a1 = await db.Authors.FirstAsync(a => a.Id == 1);
var a2 = await db.Authors.FirstAsync(a => a.Id == 1);
Console.WriteLine(ReferenceEquals(a1, a2));
var a3 = await db.Authors.AsNoTracking().FirstAsync(a => a.Id == 1);
Console.WriteLine(ReferenceEquals(a1, a3));
```
**Хороший ответ:** `True`, затем `False`. Tracking-запросы в одном контексте возвращают тот же экземпляр для той же строки (identity resolution через change tracker), хотя SQL выполняется дважды. AsNoTracking создаёт новый объект.
**Follow-up:**
- «Если между запросами кто-то изменил имя в БД — что будет в a2.Name?» — старое значение: tracked-экземпляр не перезаписывается (нужен `Reload`).
**Красные флаги:** считает, что второй запрос не идёт в БД (путает с `Find`, который сначала смотрит в tracker).
