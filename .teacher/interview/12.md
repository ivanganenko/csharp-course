# Интервью: модуль 12 — Память и Garbage Collector

### 1. Где хранятся value types и reference types?
**Уровень:** junior
**Хороший ответ:** Объекты reference types всегда создаются в managed heap, переменная хранит ссылку. Value type хранится там, где его владелец: локальная переменная — на стеке (или в регистре), поле класса — внутри объекта в куче, элемент массива — в куче. Есть случаи, когда «локальный» value type оказывается в куче: boxing, захват в closure, переменные async-методов и итераторов. Кандидат должен прямо сказать, что «value types всегда на стеке» — упрощение.
**Глубже (для junior+):** спецификация C# не говорит о стеке — это деталь реализации; JIT может хранить переменные в регистрах; `ref struct` (Span) гарантированно не попадает в кучу.
**Follow-up:**
- «Где лежит `int` внутри `List<int>`?» → во внутреннем массиве `int[]` в куче, без boxing.
- «Что происходит при `object o = 5;`?» → boxing: в куче создаётся объект-обёртка с копией значения.
- «А переменная, захваченная лямбдой?» → компилятор переносит её в поле класса-замыкания, то есть в кучу.
**Красные флаги:** «struct всегда на стеке, class всегда в куче» без оговорок; путает ссылку и объект.

### 2. Как работает garbage collector?
**Уровень:** junior
**Хороший ответ:** GC в .NET — tracing, generational, compacting. При сборке он приостанавливает потоки, от roots (стеки, static-поля, регистры, handles) помечает все достижимые объекты, остальные считаются мусором. Затем живые объекты уплотняются, ссылки обновляются. Аллокация дешёвая — сдвиг указателя. Сборка запускается в основном при исчерпании бюджета Gen 0, поэтому её момент недетерминирован.
**Глубже (для junior+):** workstation vs server GC, background GC для Gen 2, card table для ссылок «старый → молодой», POH для pinned-объектов.
**Follow-up:**
- «Что такое root?» → откуда начинается обход: локальные переменные/параметры активных методов, static-поля, регистры, GC handles.
- «Как GC справляется с циклическими ссылками?» → без проблем: если цикл недостижим от roots, он весь мусор (в отличие от reference counting).
**Красные флаги:** «GC удаляет объект, когда счётчик ссылок равен нулю»; «GC срабатывает по таймеру»; «объект удаляется сразу при выходе из метода».

### 3. Что такое поколения GC и зачем они?
**Уровень:** junior
**Хороший ответ:** Куча делится на Gen 0, 1, 2. Новые объекты — в Gen 0; пережившие сборку продвигаются в следующее поколение. Основа — generational hypothesis: большинство объектов умирают молодыми. Поэтому часто собирается только маленький Gen 0 — быстро и с большим «уловом», а Gen 2 (долгоживущие объекты) собирается редко — это full GC.
**Глубже (для junior+):** «mid-life crisis» — объекты, живущие чуть дольше Gen 0, доезжают до Gen 2 и делают full GC частыми; поэтому пулинг и короткоживущие объекты лучше «средних».
**Follow-up:**
- «Что попадает в Gen 2?» → долгоживущие объекты: кэши, singletons, static-данные; а также объекты LOH.
- «Сборка Gen 1 собирает Gen 0?» → да, сборка поколения N включает все младшие.
**Красные флаги:** «поколения — это разные процессы/потоки»; «Gen 0 — самые старые».

### 4. Что такое LOH?
**Уровень:** junior / junior+
**Хороший ответ:** Large Object Heap — куча для объектов от 85 000 байт, обычно больших массивов. Такие объекты логически сразу в Gen 2 и собираются только при full GC. LOH по умолчанию не компактируется, потому что копировать большие блоки дорого, — возможна фрагментация. Практический вывод — не создавать часто большие временные массивы, а переиспользовать их через `ArrayPool<T>`.
**Глубже (для junior+):** `GCSettings.LargeObjectHeapCompactionMode = CompactOnce`; строка длиной > ~42 500 символов тоже уходит в LOH.
**Follow-up:**
- «Какой порог?» → 85 000 байт.
- «Что будет, если каждый запрос выделяет `new byte[1_000_000]`?» → постоянные аллокации в LOH → частые full GC и фрагментация; лечится пулом.
**Красные флаги:** не знает про LOH совсем (для junior допустимо «слышал», но не «никогда»).

### 5. Зачем IDisposable, если есть GC?
**Уровень:** junior
**Хороший ответ:** GC управляет только памятью и в непредсказуемый момент. Внешние ресурсы — файлы, соединения с БД, сокеты, блокировки — ограничены и должны освобождаться сразу. `IDisposable.Dispose()` — детерминированное освобождение, а `using` гарантирует вызов даже при исключении (компилируется в try/finally). Для unmanaged-ресурсов дополнительно может быть финализатор как страховка.
**Follow-up:**
- «Во что компилируется `using`?» → `try { ... } finally { obj?.Dispose(); }`.
- «Освобождает ли Dispose память объекта?» → нет, память объекта по-прежнему освободит GC; Dispose освобождает ресурсы.
**Красные флаги:** «Dispose удаляет объект из памяти»; «Dispose вызывается GC автоматически».

### 6. Расскажите про финализаторы. Почему их стоит избегать?
**Уровень:** junior / junior+
**Хороший ответ:** Финализатор `~T()` вызывается отдельным finalizer thread после того, как GC признал объект мёртвым. Такой объект не освобождается сразу: он попадает в f-reachable очередь, переживает сборку и продвигается в старшее поколение. Порядок и момент финализации не определены, а необработанное исключение в финализаторе роняет процесс. Поэтому финализатор пишут только при прямом владении unmanaged-ресурсом, а лучше используют `SafeHandle`.
**Глубже (для junior+):** finalization queue → f-reachable queue; «воскрешение» объекта; финализатор вызывается даже для частично сконструированного объекта, если конструктор бросил исключение.
**Follow-up:**
- «Можно ли в финализаторе обращаться к другим managed-объектам?» → нет, они могли быть уже финализированы.
- «Гарантирован ли вызов финализатора?» → нет: например, при аварийном завершении процесса.
**Красные флаги:** «финализатор — то же, что деструктор в C++ и вызывается при выходе из области видимости».

### 7. Опишите полный Dispose pattern
**Уровень:** junior / junior+
**Хороший ответ:** `Dispose()` вызывает `Dispose(true)` и `GC.SuppressFinalize(this)`. Финализатор вызывает `Dispose(false)`. В `protected virtual void Dispose(bool disposing)`: если `_disposed` — выходим; если `disposing` — освобождаем managed-ресурсы; в любом случае — unmanaged; ставим `_disposed = true`. Методы после освобождения бросают `ObjectDisposedException`. `virtual` — чтобы наследники добавили своё освобождение и вызвали `base.Dispose(disposing)`.
**Follow-up:**
- «Зачем `GC.SuppressFinalize`?» → убрать объект из finalization queue: ресурсы уже освобождены, лишняя сборка не нужна.
- «Если класс sealed и владеет только managed-ресурсами?» → достаточно простого `Dispose()`, без финализатора и `Dispose(bool)`.
**Красные флаги:** освобождает managed-ресурсы при `disposing == false`; не знает, зачем параметр `disposing`.

### 8. Бывают ли утечки памяти в .NET?
**Уровень:** junior
**Хороший ответ:** Да. GC собирает только недостижимые объекты, а утечка — ненужный объект, на который всё ещё есть ссылка от root. Классика: подписка на событие долгоживущего издателя без отписки — издатель держит подписчика через delegate; static-коллекции и кэши без ограничения размера; неостановленные таймеры; closures, удерживающие большие объекты. Плюс неосвобождённые unmanaged-ресурсы.
**Глубже (для junior+):** диагностика — `dotnet-counters`, `dotnet-gcdump`, dotMemory; анализ «path to root».
**Follow-up:**
- «Как исправить утечку через событие?» → отписка (обычно в Dispose), weak event pattern, не подписываться анонимной лямбдой без сохранения.
- «Почему именно издатель держит подписчика, а не наоборот?» → delegate хранит `Target` — ссылку на объект-подписчик.
**Красные флаги:** «в .NET утечек не бывает, есть же GC».

### 9. Почему не стоит вызывать GC.Collect()?
**Уровень:** junior
**Хороший ответ:** GC сам выбирает момент по статистике аллокаций. Ручной `GC.Collect()` — это full GC с паузой всего приложения, и все живые объекты при этом продвигаются в старшие поколения, где их сбор дороже. Обычно это ухудшает производительность. Оправдано в бенчмарках, тестах на утечки, редких сценариях после разовой обработки больших данных.
**Follow-up:**
- «Освободит ли GC.Collect файл, который не закрыли?» → только если у объекта есть финализатор и после `GC.WaitForPendingFinalizers()`; правильное решение — Dispose.
**Красные флаги:** «вызываю GC.Collect в конце каждого метода, чтобы почистить память».

### 10. Что такое Span&lt;T&gt;? Чем отличается от Memory&lt;T&gt;?
**Уровень:** junior+
**Хороший ответ:** `Span<T>` — `ref struct`, окно на непрерывную память (массив, строка, stackalloc, нативная память) без копирования. Позволяет резать и парсить данные без аллокаций — вместо `Substring`/`Split`. Ограничения: живёт только на стеке — нельзя в поле класса, в лямбду, через `await`, нельзя boxing. `Memory<T>` — обычная struct с тем же смыслом, которую можно хранить в куче и передавать в async-методы; из неё получают `.Span` для работы.
**Follow-up:**
- «Почему такие ограничения?» → Span может указывать на стек; если бы он попал в кучу, ссылка пережила бы кадр.
- «Что такое stackalloc и чем он опасен?» → буфер на стеке без GC; большой размер → `StackOverflowException`, который нельзя перехватить.
**Красные флаги:** «Span копирует массив»; путает Span с List.

### 11. Что выведет этот код?
**Уровень:** junior
```csharp
public class Logger : IDisposable
{
    public void Dispose() => Console.WriteLine("Dispose");
    ~Logger() => Console.WriteLine("Finalizer");
}

using (var log = new Logger())
{
    Console.WriteLine("Work");
}
Console.WriteLine("End");
```
**Хороший ответ:** `Work`, `Dispose`, `End` — гарантированно в этом порядке. «Finalizer» может напечататься позже (или вообще не успеть до завершения процесса), потому что `Dispose()` здесь не вызывает `GC.SuppressFinalize` — это ошибка паттерна. С `SuppressFinalize` финализатор не вызвался бы.
**Follow-up:**
- «Как исправить?» → `Dispose()` → освобождение + `GC.SuppressFinalize(this)`; а если unmanaged-ресурсов нет — убрать финализатор вообще.
**Красные флаги:** уверенно говорит, что «Finalizer» напечатается сразу после «Dispose» или сразу после выхода из using.

### 12. Что выведет этот код?
**Уровень:** junior
```csharp
var publisher = new Publisher();
for (var i = 0; i < 3; i++)
{
    var screen = new Screen(publisher); // в конструкторе: publisher.Changed += OnChanged;
}
GC.Collect();
GC.WaitForPendingFinalizers();
Console.WriteLine(publisher.SubscriberCount);
```
**Хороший ответ:** `3`. Экраны недостижимы из кода, но издатель хранит три delegate с `Target` на каждый экран — они достижимы от root (`publisher`), поэтому GC их не соберёт. Это и есть утечка через события.
**Follow-up:**
- «Как сделать, чтобы было 0?» → `Screen : IDisposable` с отпиской и `using`; или weak events.
**Красные флаги:** «0, ведь мы вызвали GC.Collect».

### 13. Мини live coding: исправьте утечку и аллокации
**Уровень:** junior / junior+
**Задание:** «Есть метод, который вызывается на каждый запрос. Что бы вы улучшили?»
```csharp
public static List<string> RequestLog = new();

public static int SumIds(string csv)
{
    RequestLog.Add(csv);
    var sum = 0;
    foreach (var part in csv.Split(','))
        sum += int.Parse(part);
    return sum;
}
```
**Хороший ответ:** (1) `RequestLog` — static-список без ограничения: растёт вечно → утечка; заменить логированием через `ILogger` или ограниченным буфером. (2) static `List` не потокобезопасен — при параллельных запросах возможна порча данных. (3) `Split` создаёт массив и строку на каждый элемент — в горячем пути переписать на `ReadOnlySpan<char>` + `IndexOf` + `int.Parse(span, ..., CultureInfo.InvariantCulture)`. (4) `int.Parse` без culture/без обработки ошибок — решить, бросать или использовать `TryParse`.
```csharp
public static int SumIds(ReadOnlySpan<char> csv)
{
    var sum = 0;
    while (!csv.IsEmpty)
    {
        var i = csv.IndexOf(',');
        var part = i < 0 ? csv : csv[..i];
        sum += int.Parse(part.Trim(), NumberStyles.Integer, CultureInfo.InvariantCulture);
        csv = i < 0 ? ReadOnlySpan<char>.Empty : csv[(i + 1)..];
    }
    return sum;
}
```
**Follow-up:**
- «Как вы докажете, что стало меньше аллокаций?» → BenchmarkDotNet с `[MemoryDiagnoser]` или `GC.GetAllocatedBytesForCurrentThread`.
**Красные флаги:** не видит проблемы со static-списком; предлагает `GC.Collect()`.

### 14. Что такое WeakReference? Когда её использовать?
**Уровень:** junior+
**Хороший ответ:** Слабая ссылка не удерживает объект от сборки GC; `TryGetTarget` сообщает, жив ли он. Применяется для кэшей «если ещё в памяти — используем, иначе загрузим заново» и в weak event pattern. Недостаток — недетерминированность, поэтому основное средство от утечек — явная отписка и ограниченные кэши.
**Follow-up:**
- «Можно ли на WeakReference строить тесты на утечки?» → можно, но они нестабильны: Debug-сборка продлевает время жизни локальных переменных, нужно выносить создание в отдельный метод и вызывать GC; надёжнее проверять отписку напрямую.
**Красные флаги:** «WeakReference — это ссылка на value type».
