# Интервью: модуль 07 — исключения и IDisposable

### 1. `throw;` vs `throw ex;` vs `throw new X(..., ex)`
**Уровень:** junior
**Хороший ответ:** `throw;` перебрасывает текущее исключение с исходным stack trace. `throw ex;` бросает тот же объект, но stack trace начинается с текущей строки — реальное место ошибки теряется. `throw new X("контекст", ex)` — обёртывание: новое исключение с доменным смыслом, исходное доступно через `InnerException` вместе со своей трассой. Для переброса после логирования — только `throw;`.
**Глубже (для junior+):** `ExceptionDispatchInfo.Capture(ex).Throw()` для переброса в другом месте/потоке (так работает `await`); анализатор CA2200.
**Follow-up:**
- «Зачем вообще ловить и перебрасывать?» → логирование, откат транзакции, добавление контекста.
**Красные флаги:** «разницы нет»; «throw ex лучше, потому что явно».

### 2. Всегда ли выполняется `finally`? Что выведет код?
```csharp
static int Count()
{
    int i = 0;
    try { i = 10; return i; }
    finally { i = 20; Console.Write($"finally {i} "); }
}
Console.WriteLine(Count());
```
**Уровень:** junior
**Хороший ответ:** `finally 20 10`. Возвращаемое значение вычисляется до `finally` (10), изменение `i` после этого не влияет. `finally` выполняется практически всегда — кроме `Environment.FailFast`, `StackOverflowException`, убийства процесса и бесконечного цикла в `try`.
**Follow-up:**
- «А если `i` — поле объекта или ссылка на список?» → изменения объекта будут видны (возвращается ссылка, а не копия объекта).
- «Можно ли написать return в finally?» → нет, ошибка компиляции CS0157.
**Красные флаги:** `finally 20 20`; «finally не выполнится, если есть return».

### 3. Порядок catch и фильтры `when`
**Уровень:** junior
**Хороший ответ:** catch проверяются сверху вниз, выполняется первый совместимый; частные типы — выше общих, иначе ошибка компиляции CS0160. `when` — условие: если false, catch игнорируется. Фильтр вычисляется до раскрутки стека — контекст ошибки сохраняется (полезно при отладке и для дампов).
**Follow-up:**
- «Как залогировать исключение, не поймав его?» → `catch (Exception ex) when (Log(ex))`, где `Log` возвращает false.
**Красные флаги:** не знает про `when`.

### 4. Иерархия исключений. Что бросать в каких случаях?
**Уровень:** junior
**Хороший ответ:** База — `System.Exception`. Для аргументов: `ArgumentNullException`, `ArgumentOutOfRangeException`, `ArgumentException`. Для неправильного состояния объекта — `InvalidOperationException` (и `ObjectDisposedException`). `NotSupportedException` — операция не поддерживается, `NotImplementedException` — заглушка. Сам никогда не бросай `NullReferenceException`, `IndexOutOfRangeException`, `Exception`, `SystemException`.
**Follow-up:**
- «Разница `ArgumentException` и `InvalidOperationException`?» → первое — плохие входные данные; второе — данные нормальные, но объект сейчас не может выполнить операцию (например, `Pop` из пустого стека).
**Красные флаги:** везде `throw new Exception("...")`.

### 5. Когда создавать свои исключения? Как правильно?
**Уровень:** junior
**Хороший ответ:** Когда вызывающему нужно отличить ошибку и/или получить данные (Id, имя поля). Наследоваться от `Exception`, имя с суффиксом `Exception`, конструкторы с message и innerException, неизменяемые свойства. Если хватает стандартного типа — используй его.
**Глубже (для junior+):** сериализационный конструктор больше не нужен (BinaryFormatter устарел); иерархия доменных исключений (`DomainException` → `OrderNotFoundException`) для глобального обработчика в API → HTTP-коды.
**Красные флаги:** «наследую от ApplicationException»; своё исключение на каждый метод.

### 6. Исключения или коды ошибок / Result / Try-pattern?
**Уровень:** junior+
**Хороший ответ:** Исключения — для исключительных ситуаций и нарушений контракта: их нельзя проигнорировать, но они дорогие (stack trace) и не видны в сигнатуре. Try-pattern (`TryParse`, `TryGetValue`) — для ожидаемых частых неудач на горячем пути. Result — для бизнес-ошибок, которые часть логики (валидация, «нет денег»), с цепочками `Map/Bind`. Нельзя использовать исключения для обычного control flow.
**Follow-up:**
- «Насколько исключения дорогие?» → порядка микросекунд на бросок, в тысячи раз дороже return; в цикле на миллион элементов заметно.
**Красные флаги:** «исключения всегда плохо» или «всегда хорошо».

### 7. Что такое `IDisposable` и зачем, если есть GC?
**Уровень:** junior
**Хороший ответ:** GC освобождает только управляемую память и недетерминированно. Внешние ресурсы (соединения, файлы, сокеты, блокировки, таймеры) ограничены и должны освобождаться сразу. `IDisposable.Dispose()` — явное детерминированное освобождение; `using` гарантирует вызов. Финализатор — страховка на случай, если Dispose забыли (только для неуправляемых ресурсов).
**Follow-up:**
- «Какие классы в .NET IDisposable?» → `Stream`, `SqlConnection`, `DbContext`, `HttpResponseMessage`, `Timer`, `CancellationTokenSource`, `SemaphoreSlim`.
- «HttpClient нужно оборачивать в using?» → нет, его переиспользуют (или `IHttpClientFactory`) — иначе исчерпание сокетов.
**Красные флаги:** «Dispose освобождает память объекта»; «GC вызывает Dispose».

### 8. Как работает `using`? Что выведет код?
```csharp
using var a = new Res("A");
using (var b = new Res("B"))
{
    Console.Write("work ");
}
Console.Write("end ");

class Res(string name) : IDisposable { public void Dispose() => Console.Write($"dispose{name} "); }
```
**Уровень:** junior
**Хороший ответ:** `work disposeB end disposeA `. `using` statement вызывает Dispose в конце блока, `using` declaration — в конце области видимости (здесь — в конце top-level кода). Оба разворачиваются в `try/finally`, так что Dispose вызывается и при исключении. Несколько объектов освобождаются в обратном порядке.
**Красные флаги:** считает, что `using var` освобождается сразу после следующей строки.

### 9. Как правильно реализовать `Dispose`? Что такое Dispose pattern?
**Уровень:** junior+
**Хороший ответ:** Для sealed-класса с управляемыми ресурсами: флаг `_disposed`, идемпотентность, освобождение владеемых `IDisposable`-полей, `ObjectDisposedException` при использовании после освобождения, Dispose не бросает. Полный pattern (для наследуемых классов и неуправляемых ресурсов): `public void Dispose() { Dispose(true); GC.SuppressFinalize(this); }`, `protected virtual void Dispose(bool disposing)` — при `disposing == true` освобождаем управляемые ресурсы, всегда — неуправляемые; финализатор вызывает `Dispose(false)`.
**Follow-up:**
- «Зачем SuppressFinalize?» → объект уже освобождён, финализатор не нужен — GC не будет держать объект лишнее поколение.
- «Почему в финализаторе нельзя трогать управляемые поля?» → они могли быть уже финализированы.
**Красные флаги:** финализатор в каждом классе «на всякий случай».

### 10. Можно ли ловить `Exception`? Где обрабатывать исключения в приложении?
**Уровень:** junior
**Хороший ответ:** Ловить `Exception` уместно на границе приложения: глобальный обработчик в ASP.NET Core (`IExceptionHandler`/middleware → ProblemDetails), `Main`, фоновые задачи — для логирования и чтобы не уронить процесс. В бизнес-логике — ловить только то, что умеешь обработать. Пустой catch — антипаттерн: ошибка исчезает, состояние неизвестно.
**Красные флаги:** try/catch(Exception) в каждом методе «для надёжности».

### 11. Что будет с исключением в `finally`? А в `Dispose` внутри `using`?
**Уровень:** junior+
**Хороший ответ:** Если во время обработки одного исключения в `finally` (или в `Dispose`, вызванном из `using`) возникает второе, оно заменяет первое — исходное теряется. Поэтому `Dispose` и код `finally` не должны бросать.
**Красные флаги:** «будут два исключения одновременно» / «AggregateException» (это про Task.WhenAll).

### 12. Live coding: Retry с фильтром по типу
**Уровень:** junior
**Задание интервьюера:** «Напишите метод `T Retry<T>(Func<T> action, int attempts)`, который повторяет `action` при `TimeoutException`, а остальные исключения пробрасывает сразу. После последней неудачной попытки исключение должно уйти наружу с исходным stack trace».
**Хороший ответ:**
```csharp
public static T Retry<T>(Func<T> action, int attempts)
{
    ArgumentNullException.ThrowIfNull(action);
    ArgumentOutOfRangeException.ThrowIfLessThan(attempts, 1);

    for (int attempt = 1; ; attempt++)
    {
        try
        {
            return action();
        }
        catch (TimeoutException) when (attempt < attempts)
        {
            // временная ошибка — пробуем ещё раз (в реальном коде — с задержкой)
        }
    }
}
```
Интервьюер смотрит: guard clauses, фильтр `when` вместо `catch` + `throw ex`, неповторяемые ошибки не перехватываются, нет бесконечного цикла.
**Follow-up:**
- «Добавьте задержку и async» → `async Task<T>`, `await Task.Delay(backoff, ct)`, `CancellationToken`.
- «Почему не повторять все исключения?» → ошибки валидации/баги не исчезнут при повторе; лишняя нагрузка.
**Красные флаги:** `catch (Exception ex) { if (i == attempts) throw ex; }`.

### 13. Что такое guard clauses и fail fast?
**Уровень:** junior
**Хороший ответ:** Проверки аргументов и состояния в начале метода с немедленным исключением. Fail fast — ошибка обнаруживается как можно раньше, рядом с причиной, с понятным сообщением, вместо `NullReferenceException` где-то в глубине. В .NET 6–8: `ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace`, `ArgumentOutOfRangeException.ThrowIfNegative/...`, `ObjectDisposedException.ThrowIf`.
**Красные флаги:** «проверки замедляют код, лучше без них».

### 14. Что выведет код?
```csharp
try
{
    try { throw new InvalidOperationException("inner"); }
    finally { Console.Write("F1 "); }
}
catch (Exception ex) when (Print(ex.Message))
{
    Console.Write("caught ");
}
static bool Print(string m) { Console.Write($"filter:{m} "); return true; }
```
**Уровень:** junior+
**Хороший ответ:** `filter:inner F1 caught `. Фильтр исключения вычисляется на первом проходе, **до** раскрутки стека, поэтому выполняется раньше, чем внутренний `finally`. Затем раскрутка выполняет `finally`, затем тело catch.
**Красные флаги:** `F1 filter:inner caught` — не знает о двухфазной обработке (вполне простительно для junior, но плюс для junior+).
