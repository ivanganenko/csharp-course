## Задача 1. DashboardLoader (WhenAll)

**Обязательно:** сначала создаются все задачи (материализованы через `ToArray`/`ToList`), затем `await Task.WhenAll`; токен передаётся; guard clauses; без `Task.Run`.
**Хорошо бы:** понимание, что `WhenAll` сохраняет порядок; что при нескольких ошибках await бросает первую, остальные — в `Task.Exception`.
**Частые ошибки:**
- `foreach (var id in ids) results.Add(await source.LoadAsync(id))` → последовательно, тест «ворот» падает. Объяснить: время = сумма, а не максимум.
- `Task.Run(() => source.LoadAsync(...))` → лишний поток для IO, может давать нестабильный результат теста. **Почему плохо:** тратит потоки пула, ничего не ускоряя.
- `.Result` после `WhenAll` без `await` (через `.Wait()`) → блокировка потока.
- Без `ToArray()`: `var tasks = ids.Select(...)`; `await Task.WhenAll(tasks)`; потом `tasks.Select(t => t.Result)` → повторное перечисление **создаёт новые задачи** (повторные запросы!). Хороший момент связать с deferred execution.

1. Сколько потоков используется, пока ждём три HTTP-ответа?
2. Как получить ВСЕ исключения, если упало две загрузки?

## Задача 2. OrderImporter (отмена)

**Обязательно:** `ThrowIfCancellationRequested()` перед каждой строкой; токен передаётся в `importOne`; последовательная обработка.
**Хорошо бы:** параметр токена последним; комментарий, почему проверка именно между заказами.
**Частые ошибки:**
- Проверка только в начале метода → отмена посреди импорта не работает (тест «в середине» падает).
- `catch (OperationCanceledException) { return count; }` внутри метода → вызывающий не узнает, что операция отменена; объяснить договорённость: отмена = исключение.
- `importOne(line, CancellationToken.None)` → вложенные операции нельзя прервать.

## Задача 3. Counters

**Обязательно:** приватный `readonly` замок; чтение `Value` тоже синхронизировано (lock или `Volatile.Read`); `TryIncrementUpTo` — проверка и изменение под одним lock; `Interlocked.Increment/Add`.
**Хорошо бы:** `System.Threading.Lock` (.NET 9+); результаты эксперимента с `UnsafeCounter`; идея CAS-цикла через `CompareExchange`.
**Частые ошибки:**
- `lock (this)` → внешний код может заблокироваться на том же объекте → deadlock. 🟡
- В `InterlockedCounter.Add` — `_value += amount` → гонка. 🔴
- `TryIncrementUpTo`: `if (Value < limit) Increment();` → две отдельно атомарные операции не дают атомарности вместе (check-then-act) — тест ловит.
- `volatile int` + `_value++` → «volatile делает потокобезопасным» — нет, volatile только про видимость, не про атомарность.
**Вопросы к студенту при /check:**
1. Почему `count++` не атомарен?
2. Когда lock, а когда Interlocked?

## Задача 4. ThrottledDownloader (SemaphoreSlim)

**Обязательно:** `SemaphoreSlim(max, max)`; `await WaitAsync(token)` **до** `try`; `Release()` в `finally`; все задачи → `WhenAll`; валидация.
**Хорошо бы:** `using` для семафора (освобождается после WhenAll); упоминание `Parallel.ForEachAsync` с `MaxDegreeOfParallelism` как альтернативы.
**Частые ошибки:**
- `semaphore.Wait()` (синхронный) → блокирует потоки пула; при большом числе задач — starvation. 🟡
- `WaitAsync` внутри `try` → если ожидание отменено, `finally` вызовет `Release` без захвата → `SemaphoreFullException` или превышение лимита. 🔴
- `Release` не в `finally` → тест `OneFails_OthersStillRun` зависает (ловится `AsyncGuard`).
- Разбиение на «пачки» по N (`Chunk` + `WhenAll` на каждую) → работает, но медленнее: пачка ждёт самую долгую загрузку. Обсудить как допустимый, но худший вариант.

1. Чем `SemaphoreSlim` отличается от `lock` по привязке к потоку?
2. Почему `WaitAsync` стоит до `try`?

## Задача 5. TimeoutHelper

**Обязательно:** linked CTS; `WaitAsync(timeout, ct)` (или `WhenAny` с `Task.Delay`); при таймауте — отмена токена операции и `TimeoutException`; внешняя отмена → OCE; валидация timeout.
**Хорошо бы:** понимание, что операция продолжает работать в фоне после таймаута; `CancelAsync()`; `using` для CTS.
**Частые ошибки:**
- Только `cts.CancelAfter(timeout)` + `await operation(cts.Token)` → операция, игнорирующая токен, висит вечно (тест ловит).
- `catch (OperationCanceledException) { throw new TimeoutException(); }` без проверки, кто отменил → отмена вызывающим превращается в TimeoutException (тест ловит).
- `Task.WhenAny(task, Task.Delay(timeout))` без отмены `Delay` → таймер живёт до конца timeout — мелочь, но стоит обсудить.
**Вопросы к студенту при /check:**
1. Что происходит с операцией после того, как мы бросили TimeoutException?
2. Зачем linked token?

## Задача 7. ⭐ OrderPipeline (Channel)

**Обязательно:** bounded канал с `FullMode.Wait`; producer завершает writer в `finally` (`TryComplete`); N consumers через `ReadAllAsync`; `ConcurrentQueue`/`ConcurrentBag` или lock для результатов; при ошибке consumer — отмена общего linked-токена; `await` всех задач.
**Хорошо бы:** `SingleWriter = true`; рассуждение о том, какое исключение выйдет наружу из `WhenAll` (отменённые задачи не добавляют исключений); producer тоже в `WhenAll`.
**Частые ошибки:**
- `List<string>.Add` из нескольких consumers → потеря элементов / исключение (тест «ровно один раз» может поймать). 🔴
- Нет отмены при ошибке → producer зависает на `WriteAsync` в полный канал (тест с `capacity = 1` ловит через AsyncGuard).
- `Writer.Complete()` не в `finally` → при отмене consumers ждут вечно.
- `Task.Run` для каждого consumer — допустимо, но не нужно: consumers — async и не держат поток.
- Ожидание только consumers без producer → исключение producer потеряно.
**Вопросы к студенту при /check:**

2. Почему исключение consumer, а не `OperationCanceledException` producer, выходит наружу?
3. Чем `Channel<T>` лучше `BlockingCollection<T>` для async-кода?

## Quiz

1. **Что выведет код?**
   ```csharp
   Console.Write("1");
   var t = PrintAsync();
   Console.Write("3");
   await t;
   Console.Write("5");

   async Task PrintAsync()
   {
       Console.Write("2");
       await Task.Yield();
       Console.Write("4");
   }
   ```
   **Ответ:** `12345`. **Почему:** async-метод выполняется синхронно до первого незавершённого await; `Task.Yield` всегда отпускает управление.

2. **Найди ошибку:**
   ```csharp
   public void OnButtonClick(object s, EventArgs e)
   {
       var user = _api.GetUserAsync(1).Result;
       _label.Text = user.Name;
   }
   ```
   **Ответ:** `.Result` в UI-потоке → deadlock. **Почему:** продолжение внутри `GetUserAsync` ждёт UI-поток, а он заблокирован. Исправление — `async void` обработчик + `await`.

3. **Что выведет код?**
   ```csharp
   var count = 0;
   var tasks = Enumerable.Range(0, 1000).Select(_ => Task.Run(() => count++)).ToArray();
   await Task.WhenAll(tasks);
   Console.WriteLine(count == 1000);
   ```
   **Ответ:** обычно `False` (может случайно быть `True`). **Почему:** `count++` не атомарен, гонка. Нужен `Interlocked.Increment(ref count)`.

4. **Выбор варианта.** Нужно защитить код, внутри которого есть `await _db.SaveChangesAsync()`.
   A) `lock`  B) `SemaphoreSlim(1,1)` + `WaitAsync`  C) `Interlocked`  D) `volatile`
   **Ответ:** B. **Почему:** `await` внутри `lock` запрещён (lock привязан к потоку); Interlocked/volatile не защищают блок кода.

5. **Найди ошибку:**
   ```csharp
   public async void SaveAsync(Order order) => await _repo.SaveAsync(order);
   ```
   **Ответ:** `async void`. **Почему:** вызывающий не может дождаться и поймать исключение; ошибка уронит процесс. Нужно `async Task`.

6. **Сколько времени займёт (примерно)?**
   ```csharp
   var a = Task.Delay(1000);
   var b = Task.Delay(1000);
   await a; await b;
   ```
   **Ответ:** ~1 секунду. **Почему:** обе задачи запущены до первого await; ждём уже идущие операции. Если бы было `await Task.Delay(1000); await Task.Delay(1000);` — 2 секунды.

7. **Что не так?**
   ```csharp
   if (!_cache.ContainsKey(key))
       _cache[key] = await LoadAsync(key);   // _cache — ConcurrentDictionary
   ```
   **Ответ:** check-then-act — два потока могут оба загрузить и записать. **Почему:** потокобезопасность каждой операции не делает атомарной их последовательность; использовать `GetOrAdd` (а для async — кэш `Task`/`Lazy<Task<T>>`).

8. **Выбор варианта.** Нужно посчитать SHA-256 для 10 000 файлов в памяти, загрузив все ядра.
   A) `Task.WhenAll` по async-методам  B) `Parallel.ForEach`  C) `new Thread` на каждый файл  D) `async void`
   **Ответ:** B. **Почему:** CPU-bound работа — нужны потоки по числу ядер; `Parallel` делит работу; `new Thread` × 10 000 — огромный оверхед.
