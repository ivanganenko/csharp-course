# Рубрика модуля 15

> Общий принцип ревью: эндпоинты «тонкие» (привязка → вызов логики → результат), правильные status codes, никакой утечки деталей наружу. Зелёные тесты ≠ принято.

## Задача 1. CRUD-эндпоинты

**Обязательно:** POST → 201 + `Location: /api/tasks/{id}` + тело `TaskResponse`; PUT → 204 / 404; DELETE → 204 / 404; Title и Description триммятся, пустое описание → `null`; наружу отдаётся DTO (`ToResponse()`), а не `TaskItem`.
**Хорошо бы:** общий helper нормализации описания (DRY между Create и Update); `Delete` одним вызовом `repository.Delete(id)` без предварительного `GetById`; в `Update` учесть, что `repository.Update` может вернуть false.

**Частые ошибки**
- POST возвращает `TypedResults.Ok(...)` → тесты упадут, но обсуди *почему* 201: клиент узнаёт адрес созданного ресурса, а прокси/клиенты понимают семантику «создано».
- Возвращают `TaskItem` вместо `TaskResponse` → объясни DTO: контракт API отделён от внутренней модели, иначе любое изменение сущности ломает клиентов; риск over-posting на входе.
- `Delete`: «проверить, потом удалить» → гонка между проверкой и действием (TOCTOU), лишний вызов к хранилищу.
- PUT при отсутствии задачи создаёт её («upsert») → допустимо в REST, но не по нашей спецификации; спроси, как бы это повлияло на идемпотентность.
- Мутируют объект, полученный из `GetById`, и забывают `Update` → в InMemory это копия, изменения потеряются (так же, как без SaveChanges в EF).

## Задача 2. Валидация

**Обязательно:** все правила (Title обязателен, длина после Trim ≤ 100; Description ≤ 1000; Priority 1–5); собираются ВСЕ ошибки; валидация вызывается в Create и Update ДО обращения к репозиторию; ответ — `TypedResults.ValidationProblem(errors)`.
**Хорошо бы:** константы вместо магических чисел; relational pattern `priority is < Min or > Max`; понятные сообщения.

**Частые ошибки**
- `return` на первой ошибке → клиенту придётся отправлять форму много раз; UX хуже.
- `title.Length` без Trim → строка из 100 символов + пробелы считается невалидной, хотя сохраним мы 100 символов.
- `BadRequest("текст")` вместо ValidationProblem → нестандартный формат, фронтенд не сможет привязать ошибку к полю.
- Валидация после `GetById` в Update → лишняя работа; обсуди порядок проверок (дешёвые и не зависящие от состояния — первыми).

## Задача 3. Middleware X-Request-Id

**Обязательно:** заголовок ставится ДО `await _next(context)`; входящий id проверяется `IsValidIncomingId` (ASCII буквы/цифры, `-`, `_`, длина ≤ 64); иначе `Guid.NewGuid().ToString("N")`; `context.TraceIdentifier = id`; `_next` вызывается всегда.
**Хорошо бы:** `char.IsAsciiLetterOrDigit`; logging scope с RequestId; понимание, что middleware — фактически singleton.

**Частые ошибки**
- Заголовок после `next` → `InvalidOperationException: headers are read-only` на ответах с телом. Объясни `Response.OnStarting`.
- `char.IsLetterOrDigit` → пропустит кириллицу и прочий Unicode (тест «идентификатор» упадёт). Почему важно: значение идёт в заголовки и логи — log injection, мусор.
- Внедрение scoped-сервиса в конструктор middleware → captive dependency; scoped-сервисы берут параметрами `InvokeAsync`.
- Забыли `await` перед `_next(context)` → middleware завершится раньше обработки, scope/логи сломаются.

## Задача 5. Глобальная обработка ошибок

**Обязательно:** маппинг 404/409/500 через switch по типу (конкретные типы раньше общего); для 500 нет `Detail`; ответ через `TypedResults.Problem(...).ExecuteAsync` (или `IProblemDetailsService`) с `application/problem+json`; `return true`.
**Хорошо бы:** логирование 5xx как Error с исключением, 4xx — Warning; `traceId` в extensions; `StatusCodes.Status404NotFound` вместо магических чисел.

**Частые ошибки**
- `Detail = exception.Message` для всех → тест на секрет упадёт; объясни утечку (строка подключения, SQL, пути).
- `context.Response.WriteAsync(exception.ToString())` → stack trace наружу.
- Логирование 404 как Error → алерты «пожар» на каждую опечатку клиента; логи теряют сигнал.
- `return false` после записи ответа → middleware попробует следующий обработчик/дефолт.

## Задача 6 ⭐. Фильтрация и пагинация

**Обязательно:** Validate (Status/Page/PageSize, maxPageSize из options); Apply: фильтр статуса без учёта регистра, поиск `OrdinalIgnoreCase` по Title или Description (с null-проверкой), сортировка Priority desc + ThenBy Id, TotalCount до Skip/Take, `Skip((page-1)*pageSize).Take(pageSize)`; эндпоинт тонкий, дефолты из `IOptions<TaskTrackerOptions>`.
**Хорошо бы:** одна материализация (`ToList`) перед Count и страницей; `ArgumentOutOfRangeException.ThrowIfLessThan` в Apply; константы статусов.

**Частые ошибки**
- `Skip(page * pageSize)` → off-by-one, первая страница пропущена.
- Нет `ThenBy(Id)` → порядок равных элементов не гарантирован (особенно в БД), элементы «прыгают» между страницами.
- `ToLower().Contains(...)` → культурозависимо и лишние аллокации; `Contains(term, StringComparison.OrdinalIgnoreCase)`.
- `t.Description.Contains` без null-проверки → NullReferenceException.
- Двойное перечисление (Count по IEnumerable, потом Skip/Take) → фильтр выполняется дважды; в EF это два запроса (что нормально), в LINQ to Objects — лишняя работа.
- Хардкод `50` вместо options.

## Quiz

1. **Что выведет код?**
   ```csharp
   app.Use(async (ctx, next) => { Console.Write("A"); await next(ctx); Console.Write("B"); });
   app.Use(async (ctx, next) => { Console.Write("C"); await next(ctx); Console.Write("D"); });
   app.Run(ctx => { Console.Write("E"); return Task.CompletedTask; });
   ```
   → `ACEDB`. Почему: запрос идёт вглубь по порядку регистрации, после терминального `Run` управление возвращается в обратном порядке.

2. **Найди ошибку:**
   ```csharp
   builder.Services.AddScoped<AppDbContext>();
   builder.Services.AddSingleton<PriceCache>(); // public PriceCache(AppDbContext db)
   ```
   → captive dependency: Singleton захватывает Scoped `DbContext` навсегда; в Development — исключение при старте. Почему плохо: один контекст на все запросы, гонки, устаревшие данные.

3. **Выбор:** какой код вернуть, если пользователь пытается завершить уже завершённую задачу? A) 200 B) 400 C) 404 D) 409 → **D** (конфликт с текущим состоянием ресурса; запрос синтаксически корректен, поэтому не 400).

4. **Что будет?**
   ```csharp
   app.Use(async (ctx, next) =>
   {
       await next(ctx);
       ctx.Response.Headers["X-Time"] = "42";
   });
   app.MapGet("/", () => "hello");
   ```
   → `InvalidOperationException` (headers are read-only): ответ уже начал отправляться. Почему: заголовки уходят до тела; решение — ставить до `next` или `Response.OnStarting`.

5. **Выбор:** где лучше хранить пароль к БД для продакшена? A) appsettings.json B) appsettings.Production.json в git C) переменные окружения / хранилище секретов D) константа в коде → **C**. Почему: всё, что в git, считается скомпрометированным; конфигурация с поздним приоритетом перекрывает файл.

6. **Что вернёт эндпоинт?** `app.MapPost("/items", (Item item) => item);` для запроса без тела → 400 (не удалось привязать обязательный body-параметр). Почему: model binding проверяет обязательный параметр до вызова обработчика.

7. **Найди ошибку:**
   ```csharp
   logger.LogInformation($"User {userId} logged in");
   ```
   → интерполяция вместо шаблона: теряется структурированное поле `userId`, строка собирается даже при выключенном уровне. Правильно: `LogInformation("User {UserId} logged in", userId)`.

8. **Выбор:** что из этого НЕ идемпотентно? A) GET /tasks/1 B) PUT /tasks/1 C) DELETE /tasks/1 D) POST /tasks → **D**. Почему: каждый POST создаёт новый ресурс; поэтому при retry POST нужны idempotency keys.
