# Рубрика модуля 17

> Главное правило ревью рефакторинга: характеризационные тесты не изменены (`git diff -- modules/17*/starter/Module17.Tests`) и зелёные. Второе — история коммитов: маленькие шаги, каждый зелёный. Если студент сделал всё одним коммитом — обсуди, почему это рискованно.

## Задача 1 🧪. Запахи и нарушения SOLID

**Обязательно (минимум 6 пунктов с последствиями):**
- SRP: `Process` делает всё — валидация, цены, скидки, доставка, нумерация, уведомление, сохранение, логирование.
- OCP: `switch` по типу доставки и `if/else` по уровню клиента — каждое новое правило = правка метода.
- DIP: статический `LegacyProductCatalog` и `new SmtpEmailClient()` внутри — нельзя подменить, тест «шлёт письма».
- Магические числа: 0.05, 0.10, 20000, 5000, 350, 250, 60, 900, 500.
- `Console.WriteLine` вместо `ILogger`; `DateTime.Now` в логе (недетерминированность).
- Длинный метод, конкатенация строк, `ContainsKey` + индексатор (двойной поиск) вместо `TryGetValue`.
- Нельзя протестировать скидку без каталога, доставку — без всего заказа.
**Хорошо бы:** замечает, что дата заказа передаётся в запросе (поэтому правило воскресенья тестируемо); понимает, почему характеризационные тесты используют только фасад.

**Частые ошибки:** перечисляет принципы без последствий («нарушен SRP» — и всё) → проси «к чему это приведёт на практике?». Предлагает сразу «переписать с нуля» → объясни риски (потеря неочевидного поведения: округление AwayFromZero, граница ≥ 5000, номер не тратится при ошибке).

## Задача 2. Strategy доставки

**Обязательно:** четыре класса с той же логикой и константами (граница курьера `>=`, `Math.Ceiling(Math.Max(0, w - 1))`, экспресс `> 5`, воскресенье → `InvalidOperationException`); реестр со `StringComparer.OrdinalIgnoreCase`, `Trim`, `ArgumentException` для пустого/неизвестного кода и дубликатов, `ArgumentNullException` для null.
**Хорошо бы:** `Dictionary.TryAdd` для дубликатов; `ArgumentNullException.ThrowIfNull(context)`; реестр уже используется в `OrderProcessor`.

**Частые ошибки**
- `ToLower()` без культуры → в турецкой локали «I» ломается; `ToLowerInvariant`/`OrdinalIgnoreCase`.
- Реестр через `switch` внутри `Get` → OCP не достигнут, просто перенесли switch.
- `DateTime.Now.DayOfWeek` вместо `context.OrderDate` → недетерминированный тест.
- Экспресс-проверка веса `>= 5` → тест на границе упадёт; обсуди важность границ из спецификации.

## Задача 3. Скидки: Strategy + Decorator

**Обязательно:** ставки через switch expression или словарь, bulk `>= 20000` (включительно), `Math.Round(..., 2, MidpointRounding.AwayFromZero)`, отрицательный subtotal → `ArgumentOutOfRangeException`; декоратор хранит `inner`, проверяет аргументы, возвращает `Math.Min`.
**Хорошо бы:** константы; `ThrowIfNegative`; декоратор `sealed`, поля `readonly`.

**Частые ошибки**
- `Math.Round(x, 2)` (по умолчанию ToEven) → 29.98 вместо 29.99. Объясни банковское округление и почему legacy-поведение надо сохранить (бухгалтерия сверяет суммы).
- `double` вместо `decimal` → погрешности (модуль 02).
- Декоратор наследуется от `TierDiscountPolicy` вместо композиции → работает только с одной стратегией; разбери «композиция vs наследование».

**Вопросы к студенту при /check**

2. Где в .NET встречается Decorator?

## Задача 4. Builder

**Обязательно:** fluent (каждый метод возвращает `this`); слияние SKU с сохранением порядка; немедленные проверки аргументов; `InvalidOperationException` в `Build` для отсутствующих клиента/товаров/даты; `Build` копирует строки (`ToArray()`/новый список); `pickup` и `Regular` по умолчанию.
**Хорошо бы:** `record with` для изменения количества; `ThrowIfNullOrWhiteSpace`, `ThrowIfNegativeOrZero`.

**Частые ошибки**
- `Lines = _lines` (тот же список) → тест независимости упадёт; объясни aliasing и почему `IReadOnlyList` не защищает от изменения через исходную ссылку.
- `Dictionary<string,int>` для строк → порядок не гарантирован контрактом (в текущей реализации обычно сохраняется, но полагаться нельзя).
- `DateOnly` по умолчанию `default` (0001-01-01) вместо проверки «не задана» → используй `DateOnly?`.

## Задача 5. Adapter

**Обязательно:** хранит `LegacyMailGateway` из конструктора (null → `ArgumentNullException`); тема — константа; тело `"<p>" + WebUtility.HtmlEncode(message) + "</p>"`; код ≠ 0 → `NotificationException` с кодом в сообщении.
**Хорошо бы:** сравнение с `LegacyMailGateway.Ok`, а не с `0`; форматирование кода с `InvariantCulture`.

**Частые ошибки**
- Без экранирования → тест с `<b>` упадёт; объясни HTML-инъекцию.
- Наследование от `LegacyMailGateway` (class adapter) — класс sealed; и даже если бы нет — композиция гибче.
- Игнорирование кода возврата → «тихие» потери писем.

## Задача 6 ⭐. OrderProcessor по DIP

**Обязательно:** все 5 зависимостей через конструктор с `ThrowIfNull`; конструктор без параметров — `: this(...)` со стандартными реализациями; нет `static`-каталога и `new` инфраструктуры внутри `Process`; порядок шагов сохранён (номер берётся после всех проверок и расчётов; при ошибке нет сохранения и уведомления); все тесты модуля зелёные; характеризационные тесты не изменены.
**Хорошо бы:** `Process` читается как список шагов (выделены приватные методы); сообщение с `InvariantCulture`; `sealed`, `readonly` поля; осмысленная история коммитов.

**Частые ошибки**
- Номер заказа берётся до расчёта доставки → тест «неудачный заказ не тратит номер» упадёт. Отличный повод обсудить побочные эффекты и порядок операций.
- Уведомление до сохранения: обсуди, что лучше при сбое (письмо о заказе, которого нет, vs сохранённый заказ без письма; outbox pattern — для любопытных).
- Конструктор без параметров создаёт зависимости, но не через `this(...)` → дублирование логики инициализации.
- Интерфейс `IDeliveryMethodRegistry` «ради DIP» — допустимо, но спроси, нужен ли он (YAGNI); реестр — чистая логика без инфраструктуры.
- Оставили `Console.WriteLine` в `Process` — предложи `ILogger<OrderProcessor>` как ещё одну зависимость.

## Quiz

1. **Какой принцип нарушен?**
   ```csharp
   public class Bird { public virtual void Fly() { } }
   public class Penguin : Bird { public override void Fly() => throw new NotSupportedException(); }
   ```
   → LSP (код для `Bird` сломается на `Penguin`). Почему: наследование по «является в жизни», а не по поведению; исправление — `IFlyingBird` отдельно.

2. **Какой принцип нарушен?**
   ```csharp
   public class InvoiceService
   {
       public void Send(Invoice i) { var pdf = new PdfGenerator().Create(i); new SmtpClient("smtp.local").Send(pdf); }
   }
   ```
   → DIP (и тестируемость): `new` инфраструктуры внутри; нельзя подменить ни генератор, ни почту.

3. **Выбор:** чем DI отличается от DIP? A) это одно и то же B) DIP — принцип, DI — техника его реализации C) DI — паттерн GoF D) DIP — контейнер → **B**.

4. **Что выведет код?**
   ```csharp
   IDiscountPolicy p = new CappedDiscountPolicy(new CappedDiscountPolicy(new TierDiscountPolicy(), 500m), 300m);
   Console.WriteLine(p.CalculateDiscount(CustomerTier.Gold, 10000m));
   ```
   → `300`. Почему: Gold 10% = 1000 → внутренний кап 500 → внешний кап 300. Декораторы вкладываются.

5. **Найди проблему:**
   ```csharp
   public sealed class Config
   {
       public static Config Instance = new Config();
       public string ConnectionString { get; set; } = "";
   }
   ```
   → публичное изменяемое статическое поле: глобальное состояние, любой может заменить `Instance` или строку; нельзя подменить в тестах. Через DI + Options pattern.

6. **Выбор паттерна:** нужно добавить кэширование к существующему `IProductCatalog`, не меняя его. A) Adapter B) Decorator C) Builder D) Singleton → **B**.

7. **Выбор паттерна:** SDK платёжной системы имеет метод `Charge(int cents, string cur)`, а у нас `IPaymentGateway.PayAsync(Money amount)`. → **Adapter**.

8. **Правда или ложь:** «по SOLID на каждый класс нужен интерфейс». → Ложь. Почему: абстракции нужны на швах (инфраструктура, точки расширения, подмена в тестах); интерфейс на каждый DTO и утилиту — лишняя сложность (KISS/YAGNI).
