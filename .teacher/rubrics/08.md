# Рубрика модуля 08

## Задача 1. SimpleStack<T>

**Обязательно:**
- Хранение в `T[]` + счётчик `_count`; без `Stack<T>`/`List<T>` внутри.
- Рост массива удвоением (с обработкой capacity = 0 — иначе `0 * 2 = 0` и бесконечное «расширение» в ноль → `IndexOutOfRangeException`).
- `Pop`/`Peek` на пустом стеке → `InvalidOperationException`; `TryPop` без исключений, `out` = `default`.
- Валидация `capacity` (`ArgumentOutOfRangeException.ThrowIfNegative`).

**Хорошо бы:**
- Обнулять ячейку в `Pop` и `Array.Clear` в `Clear` (освобождение ссылок для GC).
- `[MaybeNullWhen(false)]` на `out`-параметре.
- Общий приватный `ThrowIfEmpty()` вместо дублирования проверок.
- Enumerator через `yield return`; продвинуто — поле `_version` и `InvalidOperationException` при изменении во время `foreach` (как в BCL).

**Частые ошибки** → как реагировать и **почему** это плохо:
- Рост на +1 (`new T[_items.Length + 1]`) → спроси сложность 1000 Push-ей. **Почему:** каждое расширение копирует весь массив, в сумме O(n²); удвоение даёт амортизированную O(1).
- `Pop` не обнуляет ячейку → «а когда GC соберёт объект, который мы сняли со стека?». **Почему:** массив продолжает держать ссылку — утечка памяти в долгоживущих коллекциях (связь с модулем 12).
- Перебор в `GetEnumerator` от 0 до `_count` → тест порядка упадёт; обсуди, что стек перебирается в порядке Pop.
- Использование `object[]` → «что будет для SimpleStack<int>?». **Почему:** boxing каждого элемента — теряется весь смысл generics.
- Бросает `Exception` или `IndexOutOfRangeException` из-за обращения к `_items[-1]` вместо осознанного `InvalidOperationException`. **Почему:** тип исключения — часть контракта API; утечка деталей реализации.

**Вопросы к студенту при /check:**

2. Зачем есть и `Pop`, и `TryPop`? Когда какой использовать?
3. Почему `SimpleStack<int>` не делает boxing, а `Stack` из .NET 1.0 (необобщённый) — делает?

## Задача 2. GenericAlgorithms

**Обязательно:**
- `Max`: `ThrowIfNull`, пусто → `InvalidOperationException`, один проход, сравнение через `CompareTo`.
- `Clamp`: проверка `min > max` → именно `ArgumentException`, корректные границы (включительно).
- `Swap` через `ref` (tuple swap или временная переменная).
- `CountDefaults` через `EqualityComparer<T>.Default`.
- `CreateMany`: `ThrowIfNegative`, `new T()` в цикле, `List<T>` с capacity.

**Хорошо бы:**
- В `Max` — работа через enumerator, а не `items.Count()`/`items.First()` + повторный foreach (двойное перечисление).
- `new List<T>(count)` — заданная capacity.

**Частые ошибки:**
- `Max` через `items.First()` и затем `foreach` → **Почему плохо:** две итерации; для ленивой последовательности (yield, LINQ-запрос, чтение файла) — двойная работа или разные данные. Подводка к multiple enumeration (модуль 11).
- `Max` с начальным значением `default(T)` или `int.MinValue` → для отрицательных чисел/дат даст неверный ответ, для пустой последовательности — не бросит исключение.
- `CountDefaults` с `item.Equals(default)` → NRE для `null`-элементов; с `object.Equals(item, default)` → работает, но boxing для value types. Спроси, чем отличается.
- Использование LINQ (`items.Max()`) → задача про алгоритм; попроси написать руками и сравнить.

**Вопросы к студенту при /check:**
1. Что произойдёт, если убрать `where T : IComparable<T>` из `Max`? Какая ошибка компилятора?
2. Почему `EqualityComparer<T>.Default` не делает boxing для `int`?
3. Как вызвать `CreateMany` — почему тип нужно указать явно (`CreateMany<StringBuilder>(3)`)?

## Задача 3. InMemoryRepository<T>

**Обязательно:**
- `Dictionary<int, T>` для хранения; `TryAdd` или `ContainsKey` для дубликатов → `InvalidOperationException`.
- `GetById` → `null` для отсутствующего (через `TryGetValue`/`GetValueOrDefault`).
- `GetAll` — копия, отсортированная по Id.
- `Update` не добавляет новую сущность.
- `ThrowIfNull` в `Add`/`Update`.

**Хорошо бы:**
- `TryAdd` (один поиск вместо двух).
- Поле `readonly`.

**Частые ошибки:**
- `List<T>` + линейный поиск → **Почему плохо:** O(n) на каждый GetById; спроси, что будет при 1 млн записей.
- `GetAll` возвращает `_items.Values` без сортировки → порядок Dictionary не гарантирован (после удалений порядок «плывёт»). Тест может пройти случайно — обсуди обязательно.
- `GetAll` возвращает внутренний список → внешний код может изменить состояние репозитория (нарушение инкапсуляции).
- `Update` через `_items[entity.Id] = entity` без проверки → добавляет новую сущность, тест упадёт.

**Вопросы к студенту при /check:**
1. Что даёт constraint `IEntity`? А `class`?
2. Почему порядок перечисления `Dictionary` нельзя считать гарантированным?
3. Как бы ты сделал репозиторий для сущностей с ключом `Guid`? (Ответ: второй параметр типа `TKey`, `IEntity<TKey>`.)

## Задача 4. Cache<TKey, TValue>

**Обязательно:**
- `Dictionary<TKey, TValue>` внутри, индексатор в `Set`.
- `TryGet` через `TryGetValue`, корректные `Hits`/`Misses`.
- `GetOrAdd`: `ThrowIfNull(factory)` сразу, factory вызывается только при промахе, результат сохраняется.
- `Hits`/`Misses` — `{ get; private set; }`.

**Хорошо бы:**
- `GetOrAdd` переиспользует `TryGet` (статистика в одном месте).
- `[MaybeNullWhen(false)]` на out-параметре.

**Частые ошибки:**
- `ContainsKey` + индексатор → двойной поиск; не баг, но спроси «сколько раз считается хэш?».
- Проверка `factory` только в ветке промаха → ошибка проявляется «иногда»; **почему плохо:** fail fast — ошибку программиста лучше обнаружить сразу.
- Публичные сеттеры `Hits`/`Misses` → внешний код может «подкрутить» статистику.
- `Set` через `Add` → `ArgumentException` при перезаписи.

1. Почему фабрика, а не значение? (Ответ: значение может быть дорогим — запрос к API/БД; фабрика вызывается только при промахе — lazy.)
2. Потокобезопасен ли этот кэш? Что использовать в многопоточном коде? (`ConcurrentDictionary` — модуль 13.)

## Задача 5. Исследование (без тестов)

**Проверь в ответах студента:**

## Задача 6. ⭐ Вариантность

**Обязательно:**
- `interface IMessageSource<out T>`, `interface IMessageHandler<in T>`.
- `QueueMessageSource<T>` копирует вход (`new Queue<T>(messages)` или `ToList`), `Next` → `null` по окончании без исключения.
- `LoggingHandler`: `GetType().Name`, а не `nameof(Message)` или `typeof(T)`.
- `Drain`: проверка аргументов, цикл до `null`, подсчёт.

**Хорошо бы:**
- `Queue<T>.TryDequeue`; `while (source.Next() is { } message)`.
- `Log` наружу как `IReadOnlyList<string>`.

**Частые ошибки:**
- Перепутаны `in` и `out` → компилятор подскажет (CS1961). Попроси объяснить ошибку своими словами — это лучший момент для понимания.
- Попытка объявить `class QueueMessageSource<out T>` → CS1960; объясни, что вариантность только у интерфейсов/делегатов.
- Хранение исходного `IEnumerable<T>` без копирования → тест `CopiesInput` упадёт; ещё и многократное перечисление.
- `message.GetType().ToString()` → полное имя с namespace, тест упадёт.

## Quiz

1. **Что выведет код?**
   ```csharp
   class Counter<T> { public static int Value; }
   Counter<int>.Value = 5;
   Counter<long>.Value = 7;
   Console.WriteLine(Counter<int>.Value + Counter<long>.Value + Counter<int>.Value);
   ```
   **Ответ:** `17`. **Почему:** `Counter<int>` и `Counter<long>` — разные закрытые типы с отдельными static-полями: 5 + 7 + 5.

2. **Найди ошибку:**
   ```csharp
   static bool Contains<T>(T[] items, T value)
   {
       foreach (var item in items)
           if (item == value) return true;
       return false;
   }
   ```
   **Ответ:** CS0019 — оператор `==` не определён для неограниченного `T`. **Почему:** операторы — static-методы, компилятор не знает, есть ли они у `T`. Исправление: `EqualityComparer<T>.Default.Equals(item, value)`.

3. **Скомпилируется ли?**
   ```csharp
   IEnumerable<object> a = new List<string>();
   List<object> b = new List<string>();
   IEnumerable<object> c = new List<int>();
   ```
   **Ответ:** первая строка — да (covariance `IEnumerable<out T>`); вторая — нет (`List<T>` инвариантен); третья — нет (вариантность только для reference types, `int` — value type).

4. **Выбери верный порядок constraints:**
   A) `where T : new(), class, IEntity` B) `where T : class, IEntity, new()` C) `where T : IEntity, class, new()`
   **Ответ:** B. **Почему:** `class`/`struct` — первым, `new()` — последним, интерфейсы/базовый класс — между ними.

5. **Что выведет код?**
   ```csharp
   object[] arr = new string[2];
   try { arr[0] = 1; Console.WriteLine("ok"); }
   catch (ArrayTypeMismatchException) { Console.WriteLine("mismatch"); }
   ```
   **Ответ:** `mismatch`. **Почему:** ковариантность массивов небезопасна: компилятор пропускает, CLR проверяет тип при записи.

6. **Что выведет код?**
   ```csharp
   static T Def<T>() => default!;
   Console.WriteLine(Def<int>());
   Console.WriteLine(Def<string>() is null);
   Console.WriteLine(Def<bool>());
   ```
   **Ответ:** `0`, `True`, `False`. **Почему:** `default(T)` — нулевое значение типа: 0, null, false.

7. **Какой constraint нужен, чтобы метод `T Create<T>() => new T();` скомпилировался?** A) `class` B) `struct` C) `new()` D) никакой
   **Ответ:** C (или `struct`, которое подразумевает конструктор по умолчанию — но канонический ответ `new()`). **Почему:** компилятор должен быть уверен, что у `T` есть доступный конструктор без параметров.

8. **Скомпилируется ли и почему?**
   ```csharp
   Action<object> log = o => Console.WriteLine(o);
   Action<string> logString = log;
   Func<string> getText = () => "hi";
   Func<object> getObject = getText;
   ```
   **Ответ:** да, обе строки присваивания. **Почему:** `Action<in T>` контравариантен (обработчик object справится со string), `Func<out TResult>` ковариантен (string — это object).
