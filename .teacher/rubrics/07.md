# Рубрика модуля 07

## Задача 1. ValidationException + RegistrationValidator

**Обязательно:**
- `ValidationException : Exception`, цепочка конструкторов `: this(...)`, `base(message, innerException)`, get-only `PropertyName`, проверка propertyName.
- `ArgumentNullException.ThrowIfNull(request)` в обоих методах.
- Правила вынесены в private-методы и **не дублируются** между `Validate` и `GetErrors`.
- `nameof(RegistrationRequest.Username)` или константы вместо «магических строк» по коду.

**Хорошо бы:** `char.IsAsciiLetterOrDigit`; сообщения об ошибках, понятные пользователю; `sealed` не обязателен (исключения часто наследуют), но обсуди.
**Частые ошибки** → реакция и **почему**:
- Наследуется от `ApplicationException` → устаревшая рекомендация, Microsoft советует `Exception`.
- Нет конструктора с `innerException` → нельзя обернуть причину.
- Правила скопированы в двух методах → разойдутся при первом изменении.
- `char.IsLetterOrDigit` → пропускает кириллицу (тест `"анна"`).
- Email через Regex на 200 символов → обсуди KISS; для собеседования — достаточно простой проверки, реальная валидация — отправка письма.

2. Что вернёт `ex.ToString()` и почему в логах его лучше, чем `ex.Message`?
3. Когда ты выберешь `GetErrors` вместо `Validate`?

## Задача 2. AppConfig

**Обязательно:**
- `Dictionary` с `StringComparer.OrdinalIgnoreCase`; хранится номер строки для каждого ключа.
- Split по `'\n'` + `Trim()`; `IndexOf('=')` для первого `=`; проверки пустого ключа и дубликатов (`TryAdd`).
- `GetInt` с `catch ... when (ex is FormatException or OverflowException)` и `throw new ConfigParseException(..., ex)`.
- `TryGetInt` без try/catch, через `int.TryParse` с `InvariantCulture`.
- `KeyNotFoundException` для отсутствующего ключа.

**Хорошо бы:** private-конструктор (создание только через `Parse`); общий `GetEntry`.
**Частые ошибки:**
- `catch (Exception)` в `GetInt` → поймает и то, что не должен (например, NRE из бага).
- `throw new ConfigParseException(...)` без `ex` → потеряна причина.
- `TryGetInt` через `try { GetInt } catch { return false; }` → Try-pattern, реализованный исключениями, теряет весь смысл (производительность).
- `Split('=')` → ломает значения с `=`.
- `int.Parse` без культуры → обсуди, хотя для целых обычно безопасно (знак минуса в некоторых культурах отличается).

**Вопросы к студенту при /check:**
1. Зачем `ConfigParseException` хранит номер строки и inner exception?
2. Почему для `TryGetInt` нельзя просто обернуть `GetInt` в try/catch?
3. Что делает фильтр `when`, если условие ложно?

## Задача 3. Исследование throw / finally

**Обязательно:** показаны три трассы; объяснено, что `throw ex` теряет `Level3`; вывод задачи с `finally`: `try`, `catch`, `finally`, `1`; исключение из `finally` заменяет исходное.

## Задача 4. DatabaseConnection

**Обязательно:**
- Валидация до `OnOpened`; флаг `_disposed`; идемпотентный `Dispose`; `ObjectDisposedException.ThrowIf`.
- `RunCommands`: проверка `commands` до открытия, `using`.
- `Transfer`: два `using` → обратный порядок закрытия.

**Хорошо бы:** `using var` (declaration); `sealed` и комментарий, почему не нужен полный Dispose pattern.
**Частые ошибки:**
- Ручной `connection.Dispose()` в конце метода без `try/finally` → при исключении утечка (тест `RunCommands_Failure` ловит).
- `try { ... } catch { connection.Dispose(); throw; }` + Dispose после → дублирование; `using`/`finally` проще.
- `Dispose` вызывает `OnClosed` каждый раз → OpenConnections уходит в минус.
- Финализатор «на всякий случай» → не нужен для управляемых ресурсов, замедляет GC.

**Вопросы к студенту при /check:**
1. Во что разворачивается `using var`?
2. В каком порядке закрываются ресурсы при нескольких `using`? Почему так правильно?
3. Когда нужен финализатор и `Dispose(bool)`?

## Задача 5. Retry

**Обязательно:** guard clauses; цикл попыток; исключение пробрасывается **тем же объектом** (`throw;` или фильтр `when`); non-transient — без повторов; `onRetry` вызывается только перед повтором.
**Хорошо бы:** фильтр `when (attempt < maxAttempts && ...)` без явного `throw`; `isTransient?.Invoke(ex) ?? true`.
**Частые ошибки:**
- `throw ex;` → тест проходит (`Assert.Same` — тот же объект!), но stack trace испорчен. Обязательно обсудить: тест не ловит это, а code review — должен.
- Сохраняет `lastException` и после цикла `throw lastException;` → та же проблема со stack trace; лучше `ExceptionDispatchInfo.Capture(ex).Throw()` или фильтр.
- Ловит исключения из `onRetry`/`isTransient` и повторяет → обсудить.
- `catch (Exception)` с последующей проверкой `if (!isTransient(ex)) throw;` → корректно, но фильтр чище.

**Вопросы к студенту при /check:**
1. Почему фильтр `when` позволяет вообще не писать `throw` на последней попытке?
2. Что изменится в stack trace при `throw ex;`, хотя `Assert.Same` проходит?
3. Как сделать async-версию с задержкой и отменой?

## Задача 6. Result<T> ⭐

**Обязательно:** private-конструктор; фабрики `Success`/`Failure` с валидацией ошибки; `Value`/`Error` бросают `InvalidOperationException` при неправильном доступе; `Map`/`Bind` не вызывают функцию при неудаче; `AgeParser` без исключений, через `TryParse` + `InvariantCulture`.
**Хорошо бы:** неизменяемость (readonly-поля); `ToString`; понимание railway-oriented programming; сравнение с `Nullable<T>`/Try-pattern.
**Частые ошибки:**
- Публичный конструктор / изменяемые свойства → можно создать «успех с ошибкой».
- `Value` возвращает `default` при неудаче → тихий баг (0 вместо ошибки).
- `AgeParser` через `int.Parse` в try/catch → противоречит смыслу задачи.
- `Bind` реализован как `Map(...)` с возвратом `Result<Result<T>>` → не скомпилируется по сигнатуре, но обсуди разницу.

**Вопросы к студенту при /check:**
1. Map vs Bind — в чём разница?
2. Когда исключения всё равно лучше Result?
3. Почему `Value` при неудаче бросает исключение — это противоречие?

## Quiz

1. **Что выведет код?**
   ```csharp
   try { Console.Write("A"); throw new InvalidOperationException(); }
   catch (ArgumentException) { Console.Write("B"); }
   catch (Exception) { Console.Write("C"); }
   finally { Console.Write("D"); }
   ```
   **Ответ:** `ACD`. **Почему:** `InvalidOperationException` не наследник `ArgumentException`; подходит `catch (Exception)`; `finally` всегда.

2. **Найди ошибку:**
   ```csharp
   try { Load(); }
   catch (Exception ex) { Log(ex); }
   catch (IOException ex) { Retry(); }
   ```
   **Ответ:** ошибка компиляции CS0160: второй catch недостижим. **Почему:** `IOException` — наследник `Exception`, первый catch поймает всё. Частные типы — выше.

3. **Что выведет код?**
   ```csharp
   static string F() { try { return "try"; } finally { Console.Write("finally "); } }
   Console.WriteLine(F());
   ```
   **Ответ:** `finally try`. **Почему:** `finally` выполняется до фактического выхода из метода, а вывод результата — после.

4. **Выбор варианта.** Как правильно перебросить исключение после логирования? A) `throw ex;` B) `throw;` C) `throw new Exception(ex.Message);` D) `return;`
   **Ответ:** B. **Почему:** сохраняет исходный stack trace; A теряет трассу; C теряет тип и трассу (нет inner); D глотает ошибку.

5. **Что выведет код?**
   ```csharp
   using (var r = new Res("1"))
   using (var s = new Res("2"))
   {
       Console.Write("body ");
   }
   class Res(string n) : IDisposable { public void Dispose() => Console.Write($"d{n} "); }
   ```
   **Ответ:** `body d2 d1`. **Почему:** вложенные `using` → вложенные `try/finally`, освобождение в обратном порядке.

6. **Найди проблему:**
   ```csharp
   var conn = new SqlConnection(cs);
   conn.Open();
   var count = Query(conn);
   conn.Dispose();
   ```
   **Ответ:** если `Query` бросит исключение, `Dispose` не вызовется — утечка соединения. **Почему:** нужен `using`/`try-finally`.

7. **Что выведет код?**
   ```csharp
   try { throw new FormatException("bad"); }
   catch (Exception ex) when (ex is ArgumentException) { Console.Write("arg"); }
   catch (Exception ex) when (ex.Message == "bad") { Console.Write("bad"); }
   ```
   **Ответ:** `bad`. **Почему:** первый фильтр false → catch пропускается; второй фильтр true.

8. **Выбор варианта.** Пользователь ввёл возраст в форме. Что лучше для разбора? A) `int.Parse` в try/catch B) `int.TryParse` C) `Convert.ToInt32` D) `(int)input`
   **Ответ:** B. **Почему:** некорректный ввод — ожидаемая ситуация, Try-pattern не использует исключения (быстрее и яснее); D не скомпилируется для string.
