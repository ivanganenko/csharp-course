# Рубрика модуля 12

## Задача 1. ReportWriter: полный Dispose pattern

**Обязательно:**
- `Dispose()` вызывает `Dispose(true)` и `GC.SuppressFinalize(this)`.
- `protected virtual void Dispose(bool disposing)`; при `disposing == false` не трогает `_stream`.
- Финализатор `~ReportWriter() => Dispose(false);` добавлен.
- Флаг `_disposed` — повторный вызов ничего не делает; `WriteLine` после Dispose бросает `ObjectDisposedException`.

**Хорошо бы:**
- `ObjectDisposedException.ThrowIf(_disposed, this)` вместо ручного `if/throw`.
- Комментарий/ответ, что в реальном коде вместо `IntPtr`+финализатора берут `SafeHandle`.
- `_disposed = true` выставляется в конце `Dispose(bool)` (или в начале — главное, чтобы не было повторного освобождения).

**Частые ошибки:**
- `_stream.Dispose()` вне `if (disposing)` → объяснить: в финализаторе поток мог быть уже финализирован, порядок финализации не определён; в реальных классах это даёт редкие, невоспроизводимые падения.
- Нет `GC.SuppressFinalize` → тесты пройдут, но объект после Dispose всё равно попадёт в очередь финализации, переживёт сборку и продвинется в Gen 1/2. Спросить: «что будет со временем жизни объекта?»
- Финализатор с логикой, которая может бросить исключение → исключение в finalizer thread роняет процесс.
- Метод `Dispose(bool)` сделан `public` или не `virtual` → наследник не встроится в цепочку освобождения.
- Флаг проверяется только в `Dispose()`, а не в `Dispose(bool)` → путь «финализатор + Dispose» освобождает handle дважды (тест `DisposeFalseThenDispose_...` это ловит).

**Вопросы к студенту при /check:**
1. Почему финализатор вызывает именно `Dispose(false)`?
2. Зачем `GC.SuppressFinalize` и что произойдёт без него?
3. Когда в своём классе тебе вообще НЕ нужен финализатор?

## Задача 2. StockTicker / PriceWidget: утечка через события

**Обязательно:**
- `SubscriberCount => PriceChanged?.GetInvocationList().Length ?? 0`.
- `Publish` валидирует symbol и вызывает событие через `?.Invoke(this, args)`.
- Виджет подписывается методом (или сохранённым в поле delegate) и отписывается тем же delegate в `Dispose`.
- Фильтр по своему symbol.

**Хорошо бы:**
- Флаг `_disposed` (идемпотентность явно, а не «случайно работает, потому что `-=` повторно ничего не делает»).
- Guard clauses: `ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace`.
- Свойства с `private set`, а не публичные поля.

**Частые ошибки:**
- Подписка лямбдой `ticker.PriceChanged += (s, e) => ...` без сохранения → отписаться невозможно, тест `Dispose_Unsubscribes_NoLeak` падает. Объяснить: каждая лямбда — новый экземпляр delegate; `-=` ищет равный delegate (тот же метод и Target).
- `if (PriceChanged != null) PriceChanged(this, e)` → работает, но в многопоточном коде возможна гонка между проверкой и вызовом; `?.Invoke` читает поле один раз.
- Попытка проверить утечку через `GC.Collect()` и `WeakReference` в своих экспериментах — обсудить, почему такие тесты нестабильны (Debug-сборка продлевает жизнь локальных переменных, JIT, tiered compilation).

**Вопросы к студенту при /check:**
1. Почему утечка возникает только когда издатель живёт дольше подписчика?
2. Как бы ты искал такую утечку в работающем сервисе?

## Задача 3. SpanParser

**Обязательно:**
- Нет `Substring`, `Split`, `ToString()`, `new string` внутри методов.
- `int.Parse(span, NumberStyles.Integer, CultureInfo.InvariantCulture)` (или эквивалент с InvariantCulture).
- `TryParseKeyValue` присваивает `key`/`value` на всех путях; режет по первому `=`.
- Корректные граничные случаи: пустая строка, хвостовая запятая, `[]`.

**Хорошо бы:**
- Один проход без вложенных циклов; `CountWords` — O(n) через флаг «внутри слова».
- `checked` для суммы или осознанный ответ, почему переполнение не проверяется.
- Использование `IsWhiteSpace()`, `IsEmpty`, диапазонов `[..i]`.

**Частые ошибки:**
- `line.ToString().Split(',')` «потому что так проще» → вся суть задачи потеряна: аллокация строки + массива + N строк. Спросить, сколько объектов создаётся.
- `int.Parse(part)` без culture → в задаче целые числа, разницы почти нет, но привычка опасна для дробных чисел (`1,5` vs `1.5` на русской локали Windows).
- `CountWords` через `text.ToString().Split(' ', RemoveEmptyEntries)` → не учитывает `\t`, `\n` и аллоцирует.
- В `TryParseKeyValue` при `false` не сбрасывают уже присвоенный `key` → тест `Invalid_ReturnsFalseAndEmptyParts` для `" = value"` падает.

**Вопросы к студенту при /check:**
1. Почему `Span<T>` — `ref struct` и что из этого следует?
2. Когда ты выбрал бы `Memory<T>` вместо `Span<T>`?

## Задача 4. StreamChecksum + ArrayPool

**Обязательно:**
- `Rent` до `try`, `Return` в `finally`.
- Суммирование только первых `read` байт; чтение не больше `bufferSize` или `buffer.Length` — но цикл по `read`.
- Сумма в `long`.
- Валидация аргументов.

**Хорошо бы:**
- `ArgumentOutOfRangeException.ThrowIfNegativeOrZero(bufferSize)`.
- Понимание, что `Return(buffer, clearArray: true)` нужен для секретных данных.

**Частые ошибки:**
- `for (i = 0; i < buffer.Length; i++)` → тест с «мусорным» пулом падает; объяснить, что настоящий `ArrayPool.Shared` тоже отдаёт массивы степени двойки и с прошлыми данными.
- `Return` после цикла без `finally` → при исключении буфер не вернётся; тест `StreamThrows_BufferIsStillReturned` ловит.
- `Rent` внутри цикла → смысл пула теряется.

## Задача 5. Исследование: string vs StringBuilder (без тестов)

**Обязательно:** таблица с результатами для `+=`, `StringBuilder`, `new string`; вывод о квадратичном росте аллокаций у `+=`; запуск в Release.

**Хорошо бы:** замечание о прогреве (JIT), о попадании больших строк в LOH (Gen 2 сборки), эффект начальной ёмкости `StringBuilder(N)` (меньше перевыделений внутреннего буфера).

**Частые ошибки:** замер в Debug; выводы по одному запуску «время в мс» вместо аллокаций; вывод «StringBuilder всегда быстрее» (для 2–3 конкатенаций `+` или интерполяция лучше и читабельнее).

## Задача 6. ⭐ SimpleObjectPool&lt;T&gt;

**Обязательно:**
- Все операции со стеком и проверка размера — под одним `lock`.
- `Rent` LIFO; создание через factory, `CreatedCount` увеличивается потокобезопасно.
- `Return`: `reset` → проверка `maxRetained` → push.
- Валидация аргументов.

**Хорошо бы:**
- `factory()` и `reset` вызываются вне `lock`.
- `System.Threading.Lock` (.NET 9+) или `private readonly object _sync = new();` — не `lock(this)`.
- Ответ, почему `ConcurrentBag`/`ConcurrentStack` тоже подходят, но с `ConcurrentStack` проверка «Count < max, затем Push» неатомарна (может немного превысить лимит).

**Частые ошибки:**
- `lock (this)` → внешний код может заблокироваться на том же объекте; объяснить, почему замок должен быть приватным.
- Проверка `Count < max` вне lock, а `Push` внутри → гонка check-then-act.
- `CreatedCount++` без синхронизации → потерянные инкременты (тест может не поймать, но на review — 🔴).
- `Return` не вызывает `reset` или вызывает после того, как объект уже положен в пул → другой поток может получить «грязный» объект.

**Вопросы к студенту при /check:**
1. Что произойдёт, если вызывающий код вернёт в пул один объект дважды? Как это можно защитить?
2. Почему пул — это компромисс, а не бесплатное ускорение?

## Quiz

1. **Что выведет код?**
   ```csharp
   var a = new byte[1000];
   var b = new byte[100_000];
   Console.WriteLine($"{GC.GetGeneration(a)} {GC.GetGeneration(b)}");
   ```
   **Ответ:** `0 2`. **Почему:** массив ≥ 85 000 байт выделяется в LOH, который логически относится к Gen 2.

2. **Где лежит поле `Price`?**
   ```csharp
   struct Money { public decimal Amount; }
   class Product { public Money Price; }
   var p = new Product();
   ```
   A) на стеке  B) в куче внутри объекта Product  C) в отдельном объекте в куче
   **Ответ:** B. **Почему:** value type хранится внутри владельца; владелец — объект класса в куче. Отдельного объекта (C) нет — это был бы boxing.

3. **Найди ошибку:**
   ```csharp
   protected virtual void Dispose(bool disposing)
   {
       _connection.Dispose();
       NativeMethods.Free(_ptr);
   }
   ```
   **Ответ:** нет проверки `disposing` (managed `_connection` освобождается и из финализатора) и нет флага `_disposed` (двойное освобождение `_ptr`). **Почему:** в финализаторе `_connection` может быть уже финализирован; двойной `Free` — повреждение нативной памяти.

4. **Что выведет код?**
   ```csharp
   var ticker = new StockTicker();
   EventHandler<PriceChangedEventArgs> h1 = (s, e) => Console.Write("A");
   ticker.PriceChanged += h1;
   ticker.PriceChanged += (s, e) => Console.Write("B");
   ticker.PriceChanged -= (s, e) => Console.Write("B");
   ticker.PriceChanged -= h1;
   ticker.Publish("ACME", 1m);
   ```
   **Ответ:** `B`. **Почему:** отписка лямбдой создаёт новый delegate, не равный подписанному; `h1` отписан корректно, т.к. это та же ссылка.

5. **Выбор варианта.** Класс хранит только `HttpClient` и `StreamWriter`. Что нужно реализовать?
   A) полный Dispose pattern с финализатором  B) простой `Dispose()`, вызывающий их Dispose  C) только финализатор  D) ничего
   **Ответ:** B (если класс владеет ими). **Почему:** unmanaged-ресурсов напрямую нет — они спрятаны внутри этих классов, у которых свои механизмы освобождения; финализатор только замедлит сборку.

6. **Найди ошибку:**
   ```csharp
   public static class UserCache
   {
       private static readonly Dictionary<int, UserProfile> _cache = new();
       public static UserProfile Get(int id)
       {
           if (!_cache.TryGetValue(id, out var p)) { p = Load(id); _cache[id] = p; }
           return p;
       }
   }
   ```
   **Ответ:** неограниченный static-кэш — утечка памяти (и `Dictionary` не потокобезопасен). **Почему:** static — root на всё время жизни; кэш растёт с каждым новым id. Нужен размер/срок жизни (`MemoryCache` с лимитом, LRU) и `ConcurrentDictionary` или lock.

7. **Что не так?**
   ```csharp
   Span<char> buffer = stackalloc char[length];
   ```
   где `length` приходит из запроса пользователя.
   **Ответ:** неограниченный `stackalloc` — пользователь может передать большое число → `StackOverflowException`, который нельзя перехватить (процесс падает). **Почему:** стек ~1 МБ. Правильно: `length <= 256 ? stackalloc char[length] : new char[length]` (или ArrayPool).

8. **Почему не скомпилируется?**
   ```csharp
   class LineReader
   {
       private ReadOnlySpan<char> _current;
   }
   ```
   **Ответ:** `ReadOnlySpan<T>` — `ref struct`, его нельзя хранить в поле класса. **Почему:** span может указывать на стек; поле класса пережило бы кадр стека. Решение: `ReadOnlyMemory<char>` или `ref struct LineReader`.
